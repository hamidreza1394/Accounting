## قالب اجباری ADR جدید
هر ADR از D-020 به بعد باید این بخش‌ها را داشته باشد: شماره و عنوان، وضعیت، تاریخ، زمینه و مسئله، تصمیم، گزینه‌های بررسی‌شده و دلایل رد، پیامدهای مثبت و منفی، آثار امنیتی و داده‌ای، نحوه مهاجرت، معیار پذیرش و روش تأیید، مراجع. ADRهای D-001..D-019 با قالب کوتاه قدیمی نوشته شده‌اند و بازنویسی نمی‌شوند.

## D-001 — Razor Pages حفظ می‌شود
**وضعیت:** جزئاً منسوخ با D-011 (2026-10-20). صفحات Razor موجود — به‌ویژه صفحه ورود — حفظ می‌شوند، اما رابط کاربری جدید طبق نیازمندی صریح کارفرما با React ساخته می‌شود.

رابط وب موجود بر اساس ASP.NET Core Razor Pages است؛ مهاجرت به MVC، Blazor یا SPA بدون نیازمندی مشخص انجام نمی‌شود.

## D-002 — Modular Monolith به‌جای Microservices
**وضعیت:** پذیرفته‌شده برای شروع.

فعلاً یک برنامه قابل استقرار با مرزهای مسئولیت روشن انتخاب می‌شود. Microservices فقط در صورت نیاز مستقل به مقیاس‌دهی، استقرار یا مالکیت داده بررسی می‌شود.

## D-003 — .NET 9 برای درخواست فعلی
**وضعیت:** منسوخ با D-007 (پروژه اکنون `net10.0` است).

درخواست فعلی صریحاً .NET 9 است؛ بنابراین پروژه به `net9.0` تنظیم شده. در تاریخ این بازبینی، پایان پشتیبانی آن در نوامبر 2026 نزدیک است؛ برای پروژه جدید، .NET 10 LTS انتخاب آینده‌نگرانه‌تری است. تصمیم مهاجرت باید پیش از استقرار تولید بازبینی شود.

## D-004 — مدیریت مرکزی NuGet
**وضعیت:** پذیرفته‌شده.

نسخه پکیج‌ها در `Directory.Packages.props` تعریف می‌شود تا نسخه‌های EF Core و ASP.NET Core هماهنگ بمانند و اختلاف نسخه کاهش یابد.

## D-005 — تغییرات مرحله‌ای، نه بازنویسی یک‌باره
**وضعیت:** پذیرفته‌شده.

به دلیل حجم کد موجود و نبود تست کافی، جابه‌جایی سراسری پوشه‌ها و تغییر namespaceها پیش از ایجاد تست‌های رفتار انجام نمی‌شود. مرزهای معماری به‌تدریج و با PRهای کوچک ایجاد خواهند شد.

## D-006 — الگوها به‌صورت انتخابی
**وضعیت:** پذیرفته‌شده.

هیچ الگوی طراحی یا پارادایمی صرفاً برای داشتن نام آن وارد پروژه نمی‌شود؛ کاربرد باید مسئله‌ای واقعی را حل کند و پیچیدگی را توجیه کند.


## D-007 — .NET 10 LTS
**وضعیت:** پذیرفته‌شده برای شاخه مهاجرت.

به‌دلیل پایان پشتیبانی .NET 9 در 10 نوامبر 2026، هدف چارچوب و بسته‌های EF Core/ASP.NET Core به .NET 10 منتقل می‌شوند. توسعه رسمی `net10.0` نیازمند Visual Studio 2026 نسخه 18.0 یا بالاتر است؛ Visual Studio 2022 برای این هدف رسمی کافی نیست. پذیرش نهایی منوط به CI سبز و رفع خطاهای سازگاری است.

## D-008 — اتصال SQL Server از Configuration
**وضعیت:** پذیرفته‌شده.

Connection String از `ConnectionStrings:ConnectionString` خوانده می‌شود. توسعه محلی می‌تواند از Windows Integrated Authentication استفاده کند؛ استقرار مشتری/ابر با متغیر محیطی `ConnectionStrings__ConnectionString` یا Secret Store انجام می‌شود. هیچ credential واقعی در Git قرار نمی‌گیرد.

## D-009 — هویت مرکزی و عضویت چندشرکتی
**وضعیت:** مدل داده اولیه پذیرفته‌شده؛ جریان احراز هویت هنوز در حال مهاجرت.

هر شخص یک حساب مرکزی دارد و دسترسی به شرکت‌ها از طریق عضویت مستقل و نقش scoped به همان شرکت تعریف می‌شود. کلاس `UserCompanyMembership.UserId` در این مرحله scalar باقی مانده تا پیش از جایگزینی Login قدیمی با ASP.NET Core Identity، وابستگی نادرست به مدل کاربر فعلی ایجاد نشود. این مدل به‌تنهایی جداسازی امن Tenant را فعال نمی‌کند.

**توضیح 2026-10-21:** عبارت «حساب مرکزی» به‌معنای یک سطر در جدول `Users` در هر محیط اجرایی (یک محیط ابری یا یک نصب اختصاصی) است و به‌معنای SSO یا حساب مشترک بین سرور فروشنده و نصب‌های مشتری نیست. جزئیات و مرز هویت‌ها در D-029. در کد فعلی `UserCompanyMemberships.UserId` کلید خارجی به `Users` ندارد (فقط به `Companies` و `CompanyRoles` کلید خارجی دارد؛ `Infrastructure/Persistence/Migrations/20251017120000_InitialCreate.cs`) و جایگزینی ورود قدیمی با ASP.NET Core Identity کامل هنوز انجام نشده است؛ فقط هش رمز با `PasswordHasher<Domain.User>` انجام می‌شود (`Server/Infrastructure/Security/PasswordHashService.cs`).


## D-010 — First-run database configuration
**وضعیت:** پیاده‌سازی اولیه در PR، نیازمند تأیید CI و آزمون SQL Server.

اگر Connection String صریح از Configuration Providers موجود نباشد، برنامه از فایل محلی رمزنگاری‌شده با ASP.NET Core Data Protection استفاده می‌کند و در نبود آن صفحه راه‌اندازی را نمایش می‌دهد. در ویندوز کلیدهای Data Protection با DPAPI محافظت می‌شوند؛ در Unix مجوز فایل/پوشه محدود می‌شود. تنظیمات صریح User Secrets/Environment بر فایل محلی مقدم‌اند. دیتابیس تازه/خالی با Migrationها مقداردهی می‌شود؛ schema موجود به‌صورت خودکار تغییر نمی‌کند تا دیتابیس‌های قدیمی مبتنی بر `EnsureCreated()` ناخواسته خراب نشوند.


## D-011 — رابط کاربری جدید با React + TypeScript + Vite + Tailwind، مهاجرت تدریجی
**وضعیت:** پذیرفته‌شده (2026-10-20). جایگزین بخشی از D-001.

کارفرما React + TypeScript + Vite را هدف Frontend تعیین کرده است. مهاجرت تدریجی است: کلاینت در `ClientApp/` ساخته و در `Server/wwwroot/app` Build می‌شود و سرور آن را در `/app` سرو می‌کند. صفحه ورود Razor، صفحات مدیریت Razor و داشبورد Razor (`/`) فعلاً باقی می‌مانند و مسیر بازگشت هستند. ورود به React فقط پس از پوشش تست رفتار فعلی و مقایسه منتقل می‌شود. منطق کسب‌وکار فقط در Backend است؛ کلاینت فقط داده را از API نمایش می‌دهد. Router، State Manager یا کتابخانه UI اضافه نشده‌اند چون هنوز یک صفحه وجود دارد (YAGNI).

## D-012 — API هم‌مبدأ با Cookie و Anti-forgery؛ بدون Bearer token و CORS
**وضعیت:** پذیرفته‌شده (2026-10-20).

API نسخه 1 در `/api/v1` روی همان میزبان سرو می‌شود و با همان Cookie از نوع HttpOnly صفحه ورود احراز هویت می‌شود؛ بنابراین توکنی در دسترس JavaScript یا `localStorage` قرار نمی‌گیرد و CORS لازم نیست (فعال نشده است). درخواست‌های تغییردهنده توکن Anti-forgery را در هدر `X-XSRF-TOKEN` می‌فرستند و سمت سرور با `IAntiforgery` بررسی می‌شوند. برای مسیرهای `/api` پاسخ 401/403 به‌جای Redirect به صفحه ورود برگردانده می‌شود. اگر روزی کلاینت روی Origin دیگری (مثلاً موبایل) لازم شد، مدل توکن جداگانه باید با ADR جدید طراحی شود.

## D-013 — تعیین Tenant در سمت سرور از عضویت فعال در دیتابیس
**وضعیت:** پذیرفته‌شده (2026-10-20).

شناسه شرکت در Route یا بدنه فقط «درخواست» است. `Infrastructure.Tenancy.CompanyAccessService` در هر درخواست عضویت فعال کاربر فعال، شرکت فعال و نقش فعال همان شرکت را از دیتابیس بررسی می‌کند. Claimهای `TenantId` دیگر در Cookie صادر نمی‌شوند (لغو عضویت باید فوراً اثر کند) و به‌جای آن `NameIdentifier` (شناسه کاربر) صادر می‌شود. شرکت غیرمجاز و شرکت ناموجود هر دو 404 می‌گیرند.

**EF Core Global Query Filter فعلاً اضافه نشد:** تنها مصرف‌کنندگان داده Tenant در این مرحله یک سرویس و یک Endpoint هستند که فیلتر صریح دارند، و جریان ورود (`AuthenticationService`) عمداً عضویت‌های همه شرکت‌ها را می‌خواند؛ فیلتر سراسری بدون مدل «Tenant جاری» برای درخواست‌های بدون شرکت (ورود، Jobها، عملیات سیستمی) رفتار پنهان ایجاد می‌کرد. با اضافه‌شدن نخستین ماژول حسابداری (سند/حساب) فیلتر سراسری به‌عنوان لایه دوم دفاعی همراه با سیاست صریح `IgnoreQueryFilters` برای عملیات سیستمی اضافه شود.


## D-014 — اعتبارسنجی مجدد Cookie در هر درخواست
**وضعیت:** پذیرفته‌شده (2026-10-20).

Cookie خودکفاست و بدون بررسی مجدد تا انقضا معتبر می‌ماند. `Infrastructure.Security.SessionValidator` در `OnValidatePrincipal` برای هر درخواست حساب را با یک جست‌وجوی کلید اصلی می‌خواند و نشست را در این حالت‌ها پایان می‌دهد: حساب حذف/غیرفعال شده، یا «مهر اعتبارنامه» (SHA-256 هش ذخیره‌شده رمز) تغییر کرده است. برای حساب زیرساختی، نام کاربری و مقدار پیکربندی‌شده بررسی می‌شود. ستون جدیدی (SecurityStamp) اضافه نشد چون همان هش ذخیره‌شده رمز تغییر اعتبارنامه را نشان می‌دهد و تغییر Schema لازم نبود. پیامد: پس از استقرار، نشست‌های صادرشده پیش از این نسخه (بدون مهر) یک‌بار باطل می‌شوند و کاربر دوباره وارد می‌شود. هزینه: یک Query کلید اصلی برای هر درخواست احرازشده.

## D-015 — CSP مرحله‌ای
**وضعیت:** پذیرفته‌شده (2026-10-20).

`/app` (بدون اسکریپت/سبک inline) سیاست سخت‌گیرانه اجباری بدون `unsafe-inline`/`unsafe-eval` دارد؛ `/api` سیاست `default-src 'none'`. صفحات Razor هنوز اسکریپت/سبک inline دارند؛ بنابراین فقط سیاست پایه بی‌خطر (`object-src`، `base-uri`، `form-action`، `frame-ancestors`) اجباری است و سیاست سخت‌گیرانه به‌صورت `Content-Security-Policy-Report-Only` ارسال می‌شود. با `SecurityHeaders:EnforceRazorContentSecurityPolicy=true` پس از پاک‌سازی inlineها اجباری می‌شود. Nonce/Hash اضافه نشد تا اسکریپت‌های قدیمی بدون بازبینی «مجاز» نشوند.

## D-016 — انتشار قطعی همراه کلاینت React

CI همین اسکریپت را اجرا و سرور منتشرشده را با `scripts/smoke-published-app.sh` آزمایش می‌کند. Workflow جداگانه ساخته نشد؛ Job `publish` به همان `dotnet.yml` اضافه شد.


## D-017 — اعتماد صریح به Reverse Proxy و محدودیت میزبان
**وضعیت:** پذیرفته‌شده (2026-10-20).

`X-Forwarded-For` و `X-Forwarded-Proto` فقط از آدرس‌ها یا شبکه‌های فهرست‌شده در `ReverseProxy` پذیرفته می‌شوند. پیش‌فرض هیچ است، حتی loopback، برخلاف پیش‌فرض فریم‌ورک. `X-Forwarded-Host` پذیرفته نمی‌شود و میزبان با `AllowedHosts` محدود می‌شود. ورودی نامعتبر برنامه را متوقف می‌کند. برای `*` در `AllowedHosts` و نبود پیکربندی Proxy، بیرون از Development هشدار شروع برنامه ثبت می‌شود و مقدار فرضی تحمیل نمی‌شود (دامنه نهایی تعیین نشده است). جزئیات در `docs/DEPLOYMENT.md`.

## D-020 — مشتری تجاری، شرکت حسابداری و نصب: سه مفهوم مستقل
- **وضعیت:** تصمیم `Accepted` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** در کد فعلی `Company` هم «شرکت حسابداری» و هم مرز Tenant است (`Domain/Company.cs`؛ D-009، D-013). هیچ مفهومی برای خریدار نرم‌افزار، نمونه نصب یا لایسنس وجود ندارد: جست‌وجوی `License|CustomerAccount|ModuleDefinition|Entitlement` در `.cs`/`.cshtml`/`.ts`/`.tsx` نتیجه‌ای نداشت. یکی‌گرفتن این مفاهیم، فروش چندشرکتی و مدیریت چند نصب را بعداً دشوار می‌کند.
- **تصمیم:**
  1. `CustomerAccount` (خریدار)، `Installation` (نمونه نصب‌شده، ابری یا اختصاصی) و `Company` (شرکت حسابداری و Tenant فعلی) سه مفهوم مستقل‌اند.
  2. یک مشتری می‌تواند چند شرکت و چند نصب داشته باشد (مثلاً یک نصب اختصاصی و یک محیط آزمایشی).
  3. `Company` فعلی تغییر نمی‌کند و مستقیماً به لایسنس وصل نمی‌شود. سقف تعداد شرکت، یک محدودیت تجاری صریح در لایسنس است؛ نه شرط پراکنده در کد. این سقف هنگام ایجاد شرکت بررسی می‌شود (D-022).
  4. `CustomerAccount` و `Installation` به دیتابیس فروشنده تعلق دارند. در دیتابیس نصب مشتری فقط هویت محلی نصب و لایسنس‌های واردشده نگهداری می‌شود (D-021).
- **گزینه‌های ردشده:** (الف) یکی‌گرفتن مشتری و `Company`: فروش چندشرکتی را غیرممکن می‌کند. (ب) افزودن `CustomerId` به `Company` در دیتابیس نصب اختصاصی: داده تجاری فروشنده وارد دیتابیس مشتری می‌شود و مرز اعتماد D-021 را می‌شکند. (ج) یکی‌گرفتن نصب و لایسنس: تمدید و تعویض سخت‌افزار را به سند جدید وابسته می‌کند.
- **پیامدها:** (+) فروش، تمدید و گزارش‌گیری چندمشتری ممکن می‌شود. (−) رابطه دقیق `Company` با مشتری در نسخه ابری هنوز باید طراحی شود (`NeedsApproval`، بخش «پرسش‌های باز» در `docs/LICENSING_DATA_MODEL.md`).
- **آثار امنیتی و داده‌ای:** جدول یا ستون جدیدی در دیتابیس نصب مشتری برای مشتری فروشنده ایجاد نمی‌شود. داده مالی مشتری هرگز در دیتابیس فروشنده نیست.
- **نحوه مهاجرت:** در این مرحله هیچ Migration یا تغییر کدی انجام نمی‌شود. مدل‌های جدید به‌صورت افزایشی و در Migrationهای کوچک جداگانه اضافه می‌شوند (پس از تأیید ERD).
- **معیار پذیرش و تأیید:** ERD نهایی در `docs/LICENSING_DATA_MODEL.md` تأیید شود؛ یک مشتری با دو شرکت و دو نصب در تست مدل قابل نمایش باشد؛ هیچ ستون یا FK از `Companies` به جداول فروشنده وجود نداشته باشد.
- **مراجع:** `docs/LICENSING_DATA_MODEL.md`، `docs/PRODUCT_REQUIREMENTS.md`، D-009، D-013، D-021.

## D-021 — دو مدل استقرار با هسته مشترک و سامانه فروشنده جدا
- **وضعیت:** تصمیم `Accepted` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** محصول باید هم در فضای ابری فروشنده و هم به‌صورت نصب اختصاصی روی سرور مشتری، حتی بدون اینترنت، کار کند، بدون اینکه دو محصول جدا نگهداری شود. پنل صدور لایسنس نباید همراه بسته مشتری حمل شود.
- **تصمیم:**
  1. منطق حسابداری، Tenant و مجوزدهی عملیاتی (هسته) بین ابر و نصب اختصاصی مشترک است.
  2. **سامانه مرکزی فروشنده** (Vendor Control Plane: ثبت مشتری، قرارداد، کاتالوگ زیرسیستم‌ها، صدور و تمدید لایسنس، ممیزی) یک **Host، دیتابیس و هویت مدیران جدا** دارد و در بسته نصب مشتری قرار نمی‌گیرد. نباید دسترسی پیش‌فرض به دیتابیس مالی مشتریان داشته باشد.
  3. یک کتابخانه مشترک `Licensing.Contracts` (نام پیشنهادی) قالب فایل لایسنس و درخواست، اعتبارسنجی امضا با کلید عمومی و قرارداد کاربردی پرسش «چه زیرسیستم‌ها و سقف‌هایی مجازند؟» را نگه می‌دارد. کد صدور و کلید خصوصی در آن نیست.
  4. در ابر، پاسخ این پرسش می‌تواند از دیتابیس مرکزی بیاید؛ در نصب اختصاصی از فایل امضاشده محلی. هر دو پشت یک قرارداد کاربردی‌اند؛ هیچ‌کدام به دیگری وابسته نیست.
  5. این تصمیم D-002 را نقض نمی‌کند: هسته حسابداری همچنان یک Modular Monolith است و Microservices معرفی نمی‌شود؛ فقط ابزار فروشنده یک برنامه استقرارپذیر جداگانه است.
- **گزینه‌های ردشده:** (الف) نگه‌داشتن پنل فروشنده داخل همان پروژه `Server`: بسته مشتری کد صدور و مسیرهای مدیریتی فروشنده را می‌برد و جداسازی مرز امنیتی به یک فلگ پیکربندی وابسته می‌شود؛ (ب) Microservices کامل: بدون نیاز مستقل مقیاس‌پذیری، مطابق D-002 رد می‌شود؛ (ج) نسخه ابری و نسخه اختصاصی با کد جدا: هزینه نگهداری دو محصول.
- **پیامدها:** (+) مرز اعتماد روشن؛ نصب مشتری فاقد کد صدور. (−) یک برنامه و یک دیتابیس عملیاتی اضافه (فروشنده)؛ هزینه نگهداری قرارداد مشترک و نسخه‌بندی فرمت.
- **آثار امنیتی و داده‌ای:** کلید خصوصی صدور فقط در محیط امن فروشنده است (D-024). مدیر فروشنده و مدیر مشتری دو هویت و دو دامنه اختیار متفاوت‌اند (D-029).
- **نحوه مهاجرت:** کد جدید در پروژه‌های جدید (`Licensing.Contracts`، میزبان فروشنده) اضافه می‌شود؛ `Server` فعلی فقط به `Licensing.Contracts` وابسته می‌شود. اتصال به مسیر درخواست‌ها پس از تأیید ERD و قرارداد لایسنس و با تست.
- **معیار پذیرش و تأیید:** بسته منتشرشده مشتری (خروجی `scripts/publish.sh`) هیچ مرجعی به پروژه فروشنده و هیچ کلید خصوصی ندارد (تست ایستا روی خروجی Publish)؛ `Licensing.Contracts` به `Server` یا EF Core وابسته نیست.
- **مراجع:** D-002، D-020، D-024، D-029، `docs/LICENSING.md`، `docs/ARCHITECTURE.md`.

## D-022 — لایسنس دائمی و مدت‌دار؛ مفاهیم تفکیک‌شده و سقف‌ها
- **وضعیت:** تصمیم `Accepted` (نوع‌ها)؛ جزئیات مشخص‌شده در «پرسش‌ها» `NeedsApproval` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** نصب اختصاصی هم لایسنس دائمی و هم مدت‌دار می‌خواهد. اگر «حق استفاده»، «پشتیبانی» و «حق دریافت به‌روزرسانی» یک مفهوم فرض شوند، پایان قرارداد پشتیبانی می‌تواند به‌اشتباه نرم‌افزار خریداری‌شده را قفل کند.
- **تصمیم:**
  1. نوع لایسنس (`Perpetual`/`Term`)، بازه اعتبار، دوره پشتیبانی، حق دریافت به‌روزرسانی، زیرسیستم‌های خریداری‌شده و سقف‌ها (حداقل: حداکثر تعداد شرکت) مفاهیم مستقل‌اند؛ حتی اگر در بسته اولیه با هم فروخته شوند.
  2. در لایسنس دائمی، پایان تاریخ پشتیبانی یا به‌روزرسانی حق استفاده را از بین نمی‌برد.
  3. لایسنس مدت‌دار تاریخ شروع، تاریخ پایان و سیاست تمدید صریح دارد؛ تمدید با صدور فایل جدید انجام می‌شود (D-023).
  4. صدور، تغییر، تمدید، تعلیق و ابطال هر لایسنس رخداد ممیزی دارد و تاریخچه مجوزهای قبلی حذف نمی‌شود.
  5. محدودیت تعداد شرکت هنگام ایجاد شرکت و بر اساس لایسنس معتبر سمت سرور بررسی می‌شود. نتیجه پایین‌آمدن سقف زیر تعداد شرکت‌های موجود (مثلاً پس از تمدید با سقف کمتر): شرکت‌های موجود و داده آن‌ها حذف نمی‌شوند؛ ایجاد شرکت جدید مجاز نیست.
- **گزینه‌های ردشده:** (الف) یک تاریخ «اعتبار» برای همه چیز؛ (ب) محدودکردن لایسنس به یک `Company`؛ (ج) پراکنده‌کردن بررسی سقف در Controller/PageModelها.
- **پیامدها:** (+) انعطاف تجاری، رفتار قابل پیش‌بینی پایان قرارداد. (−) فیلدهای بیشتر و قواعد اعتبارسنجی پیچیده‌تر.
- **آثار امنیتی و داده‌ای:** تغییر یا انقضای لایسنس هیچ‌وقت داده حسابداری را حذف یا تغییر نمی‌دهد (D-026).
- **نحوه مهاجرت:** هیچ تغییر در داده موجود. فیلدهای لایسنس فقط در مدل جدید (`docs/LICENSING_DATA_MODEL.md`) آمده‌اند.
- **معیار پذیرش و تأیید:** تست قاعده‌ای: لایسنس دائمی با `supportUntil` گذشته معتبر است؛ لایسنس مدت‌دار گذشته نامعتبر است؛ ایجاد شرکت بالاتر از سقف رد می‌شود و شرکت‌های موجود دست‌نخورده می‌مانند.
- **پرسش‌ها (`NeedsApproval`):** آیا سقف تعداد کاربر هم فروخته می‌شود؟ آیا «حق دریافت به‌روزرسانی» در نرم‌افزار اعمال می‌شود یا فقط در کانال توزیع نسخه؟ ماژول‌ها برای کل نصب‌اند یا هر شرکت جدا (پیش‌فرض این ADR: کل نصب)؟
- **مراجع:** `docs/LICENSING.md`، `docs/PRODUCT_REQUIREMENTS.md`.

## D-023 — فعال‌سازی و تمدید آفلاین با فایل درخواست و پاسخ امضاشده
- **وضعیت:** تصمیم `Accepted` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** نصب کاملاً آفلاین نمی‌تواند با سرور فروشنده تماس بگیرد. فروشنده نمی‌تواند در لحظه وضعیت لایسنس را بداند یا آن را ابطال کند.
- **تصمیم:** گردش کار استاندارد:
  1. نصب شناسه پایدار و جفت‌کلید مخصوص خود را می‌سازد؛ کلید خصوصی نصب در همان نصب می‌ماند.
  2. نصب یک **فایل درخواست** می‌سازد: شناسه نصب، کلید عمومی/اثرانگشت آن، نسخه محصول، مرجع مشتری و `requestId` یکتا (nonce). اطلاعات محرمانه غیرضروری ندارد.
  3. فروشنده در سامانه مرکزی مشتری، قرارداد، تعداد شرکت، نوع لایسنس و زیرسیستم‌ها را بررسی می‌کند.
  4. سرویس صدور با کلید خصوصی فروشنده یک **فایل پاسخ (لایسنس) امضاشده** می‌سازد که به `installationId` و `requestId` وابسته است.
  5. نصب فایل را وارد می‌کند، امضا، شناسه نصب، `requestId`، تاریخ‌ها، شماره ترتیب و محدوده را بررسی و در سوابق (`SecurityAuditEvent`) ثبت می‌کند.
  6. در زمان اجرا، هر قابلیت سمت سرور از لایسنس معتبر محلی استفاده می‌کند؛ پنهان‌کردن منو در React فقط بازتاب آن است.
  7. تعلیق یا ابطال در سامانه مرکزی فوراً روی نصب بدون ارتباط اثر نمی‌گذارد؛ فقط با ورود فایل جدید یا برقراری ارتباط مجدد اعمال می‌شود. این محدودیت باید در قرارداد با مشتری و طراحی محصول پذیرفته شود.
- **گزینه‌های ردشده:** (الف) دریافت دستی فایل مجوز بدون درخواست قبلی نصب: اثبات تعلق به یک نصب مشخص ندارد؛ (ب) فراخوانی اینترنتی همیشگی: با شرط «کاملاً آفلاین» ناسازگار است؛ (ج) کلید مشترک (HMAC): راز باید داخل برنامه مشتری باشد.
- **پیامدها:** (+) اعتبارسنجی آفلاین و بدون اینترنت. (−) ابطال فوری ممکن نیست؛ تمدید باید پیش از انقضا دستی انجام شود.
- **آثار امنیتی و داده‌ای:** فایل درخواست و پاسخ نباید داده مالی یا رمز داشته باشند. جزئیات تهدیدها: `docs/LICENSING_THREAT_MODEL.md`.
- **نحوه مهاجرت:** نصب‌های فعلی لایسنس ندارند (D-028)؛ دوره گذار و صدور لایسنس اولیه `NeedsApproval`.
- **معیار پذیرش و تأیید:** تست‌های پذیرش: فایل دستکاری‌شده، امضای نامعتبر، فایل نصب دیگر، `requestId` تکراری و شماره ترتیب قدیمی رد می‌شوند؛ نصب پس از Restart و بدون اینترنت همچنان لایسنس معتبر را تأیید می‌کند.
- **مراجع:** D-021، D-024، `docs/LICENSING.md`، `docs/LICENSING_WORKFLOWS.md`، `docs/LICENSING_THREAT_MODEL.md`.

## D-024 — قالب فایل لایسنس و رمزنگاری
- **وضعیت:** `Proposed` (نیازمند تأیید کارفرما و نمونه اولیه) | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** فایل JSON یا متنی ساده به‌تنهایی لایسنس معتبر نیست؛ باید از نظر رمزنگاری قابل تأیید باشد و ابهام بازسریال‌سازی نداشته باشد.
- **تصمیم پیشنهادی:**
  1. پوشش (Envelope) شامل `formatVersion`، `kid` (شناسه کلید امضا)، **بایت‌های دقیق Payload** و امضا. امضا روی همان بایت‌های ذخیره‌شده است؛ Payload پس از بازسریال‌سازی JSON اعتبارسنجی نمی‌شود.
  2. الگوریتم پیشنهادی: ECDSA با منحنی P-256 و SHA-256 (در .NET موجود است). سازگاری روی پلتفرم‌های هدف باید با یک نمونه اولیه تأیید شود؛ جایگزین: RSA-PSS با کلید حداقل 3072 بیت.
  3. شماره ترتیب (`sequence`) یکنواخت برای هر نصب؛ نصب لایسنسی با شماره ترتیب کمتر از لایسنس فعلی را رد می‌کند (جلوگیری از جایگزینی با لایسنس قدیمی‌تر).
  4. نصب فهرست کلیدهای عمومی مورد اعتماد را با `kid` و بازه اعتبار نگه می‌دارد تا چرخش کلید ممکن باشد.
  5. کلید خصوصی صدور هرگز در Git، برنامه، بسته نصب یا دیتابیس نصب مشتری نیست؛ در Secret Store یا ماژول امنیتی سخت‌افزاری محیط فروشنده نگه‌داری می‌شود.
  6. نسخه‌های قالب (`formatVersion`) قابل ارتقا و سازگار با عقب هستند.
- **گزینه‌های ردشده:** (الف) هش SHA-256 دامنه (روش `ActivationKeys` فعلی): راز ندارد و هر کسی می‌تواند آن را بسازد (D-028)؛ (ب) HMAC با کلید مشترک: کلید باید داخل برنامه مشتری باشد؛ (ج) JSON امضاشده با بازسریال‌سازی: خطر ابهام.
- **پیامدها:** (+) تأیید آفلاین و رمزنگاری‌شده. (−) مدیریت کلید و چرخش آن بار عملیاتی دارد؛ امنیت لایسنس آفلاین مطلق نیست (`docs/LICENSING_THREAT_MODEL.md`).
- **آثار امنیتی و داده‌ای:** امنیت به محرمانگی کلید خصوصی صدور بستگی دارد؛ افشای آن نیازمند چرخش کلید و صدور دوباره است.
- **نحوه مهاجرت:** پس از تأیید، `Licensing.Contracts` با تست‌های بردار تست (test vectors) ساخته می‌شود.
- **معیار پذیرش و تأیید:** تست‌های امضای معتبر/نامعتبر/دستکاری/`kid` ناشناخته/نسخه قالب ناشناخته؛ اسکن Git برای نبود هرگونه کلید خصوصی.
- **مراجع:** D-021، D-023، `docs/LICENSING.md`.

## D-025 — مجوز تجاری ماژول مستقل از مجوز عملیاتی کاربر
- **وضعیت:** تصمیم `Accepted`؛ نگاشت `ModuleCode` به مجوزها `Proposed` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** خرید یک زیرسیستم (مثلاً انبار) نباید به همه کاربران حق ثبت و حذف سند انبار بدهد. در کد فعلی `PermissionDefinition` و `CompanyRolePermission` وجود دارند ولی در `Server/` هیچ بررسی مجوز عملیاتی مصرف نمی‌شود (جست‌وجوی `PermissionDefinitions|CompanyRolePermissions|RolePermissions` در `Server/` نتیجه‌ای نداشت)؛ فقط دسترسی به شرکت با `CompanyAccessService` بررسی می‌شود. `PermissionDefinition` ستون یا نگاشتی به زیرسیستم ندارد.
- **تصمیم:** هر درخواست سمت سرور با ترکیب این شرط‌ها مجاز می‌شود (همه باید برقرار باشند):
  1. هویت: حساب فعال و نشست معتبر (D-014).
  2. محدوده: عضویت فعال در شرکت (D-013) و دسترسی به سال مالی/دوره مربوط.
  3. مجوز تجاری: لایسنس معتبر و زیرسیستم (`ModuleCode`) فعال برای قابلیت درخواست‌شده.
  4. مجوز عملیاتی: نقش شرکتی کاربر مجوز مشاهده/ثبت/ویرایش/حذف/تأیید همان قابلیت را دارد (`PermissionDefinition` + `CompanyRolePermission`).
  5. وضعیت دوره مالی: Closed/Archived طبق قواعد حسابداری ثبت را محدود می‌کند.
  فعال‌بودن لایسنس به‌تنهایی به‌معنی مجاز بودن همه عملیات نیست. بررسی نهایی در API است؛ React فقط وضعیت را بازتاب می‌دهد.
- **پیشنهاد (`Proposed`):** کدهای پایدار زیرسیستم (`finance`، `sales`، `inventory`، `treasury` به‌عنوان مثال؛ فهرست نهایی `NeedsApproval`) و کد مجوز به شکل `<module>.<resource>.<action>` (مثلاً `inventory.voucher.create`). نگاشت مجوز به زیرسیستم یا با ستون `ModuleCode` در `PermissionDefinition` یا با کاتالوگ ثابت در کد؛ انتخاب `NeedsApproval`. تغییر عنوان نمایشی نباید کد را تغییر دهد.
- **گزینه‌های ردشده:** (الف) استفاده از لایسنس به‌عنوان مجوز کاربر؛ (ب) بررسی فقط در UI؛ (ج) کد مجوز بر اساس عنوان فارسی.
- **پیامدها:** (+) تفکیک روشن حق استفاده مشتری و اختیار کاربر. (−) هر Endpoint حسابداری باید هر دو بررسی را انجام دهد؛ نیاز به یک نقطه مشترک سمت سرور (مثلاً سیاست Authorization).
- **آثار امنیتی و داده‌ای:** افزودن `ModuleCode` تغییر Schema است و نیازمند Migration بازبینی‌شده است؛ در این مأموریت انجام نشده.
- **نحوه مهاجرت:** در Migration افزایشی کوچک با مقدار پیش‌فرض/Backfill بازبینی‌شده؛ پس از تأیید.
- **معیار پذیرش و تأیید:** تست‌های ماتریسی: کاربر بدون مجوز عملیاتی با لایسنس معتبر رد می‌شود؛ کاربر دارای مجوز بدون لایسنس زیرسیستم رد می‌شود؛ فراخوانی مستقیم URL زیرسیستم غیرمجاز رد می‌شود؛ عضویت/نقش/کاربر غیرفعال رد می‌شود.
- **مراجع:** D-013، D-014، `docs/LICENSING_DATA_MODEL.md`، `docs/PRODUCT_REQUIREMENTS.md`.

## D-026 — رفتار انقضا، حالت محدودشده و حفظ داده
- **وضعیت:** اصل `Accepted`؛ جزئیات (مدت دوره ارفاق، فهرست دقیق قابلیت‌های محدودشده، سیاست ساعت) `NeedsApproval` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** اسناد مالی باید همیشه در دسترس صاحب آن‌ها باشند. قفل‌شدن کامل یا از دست رفتن داده پس از انقضا یا خطای لایسنس برای نرم‌افزار حسابداری پذیرفتنی نیست.
- **تصمیم:**
  1. انقضا، تعلیق، ابطال یا تغییر لایسنس هرگز داده مالی را حذف یا تغییر نمی‌دهد.
  2. پس از پایان اعتبار لایسنس مدت‌دار و دوره ارفاق، نصب وارد «حالت محدودشده» می‌شود: ورود، مشاهده، گزارش‌گیری، **خروجی‌گرفتن، پشتیبان‌گیری** و ورود فایل لایسنس مجاز می‌ماند؛ ثبت، ویرایش و تأیید در زیرسیستم‌های مشمول مسدود می‌شود.
  3. دوره ارفاق پیش‌فرض ۳۰ ‌روز و قابل تنظیم است (`NeedsApproval`: عدد نهایی). هشدار پیش از انقضا نمایش داده می‌شود (عدد `NeedsApproval`).
  4. لایسنس دائمی با پایان پشتیبانی یا حق به‌روزرسانی محدود نمی‌شود (D-022).
  5. به‌روزرسانی ساعت سیستم نصب آفلاین قابل دستکاری است. نرم‌افزار آخرین زمان مشاهده‌شده را ثبت و عقب‌گرد آشکار را تشخیص و ثبت می‌کند؛ سیاست واکنش `NeedsApproval`. ادعای مصونیت مطلق نمی‌شود.
- **گزینه‌های ردشده:** (الف) قفل کامل پس از انقضا؛ (ب) حذف یا رمزگذاری داده؛ (ج) ادامه کامل کار بدون هیچ محدودیت.
- **پیامدها:** (+) اعتماد مشتری و رعایت نگهداری اسناد. (−) فروشنده نمی‌تواند با قفل کامل فشار بیاورد؛ باید قرارداد و تمدید مدیریت شود.
- **آثار امنیتی و داده‌ای:** حالت محدودشده باید سمت سرور اعمال شود. خروجی‌گرفتن نباید بتواند به مسیر دورزدن لایسنس برای ثبت تبدیل شود.
- **نحوه مهاجرت:** نبود لایسنس در نصب‌های فعلی نباید ناگهان آن‌ها را محدود کند؛ دوره گذار با D-028 هماهنگ می‌شود.
- **معیار پذیرش و تأیید:** تست: پس از انقضا و ارفاق، ثبت سند رد و گزارش/خروجی موفق؛ هیچ ردیف داده حذف نمی‌شود؛ تغییر ساعت به عقب ثبت می‌شود.
- **مراجع:** D-022، `docs/LICENSING.md`.

## D-027 — انتقال، بازیابی و کپی نصب؛ حدود کنترل آفلاین
- **وضعیت:** `Proposed` و `NeedsApproval` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-21
- **زمینه و مسئله:** تعویض سخت‌افزار، بازیابی از Backup و کپی ماشین مجازی نباید مشتری قانونی را قفل کند. همچنین جلوگیری قطعی از کپی کامل یک ماشین مجازی در محیط کاملاً آفلاین ممکن نیست.
- **تصمیم پیشنهادی:**
  1. شناسه نصب پایدار است و به MAC Address یا یک قطعه سخت‌افزاری مطلق وابسته نیست مگر نیاز واقعی و تأییدشده کارفرما.

  1. **دو بخش با مرز امنیتی مستقل.** (الف) نرم‌افزار حسابداری (`Server`): قابل نصب نزد مشتری و در ابر؛ عملیات عادی به اتصال دائمی یا سامانه مرکزی وابسته نیست؛ DB حسابداری و هویت کاربران مشتری مستقل از فروشنده است؛ اعتبار لایسنس سمت سرور نصب‌شده بررسی می‌شود؛ دسترسی کاربر به شرکت‌ها علاوه بر لایسنس با عضویت و مجوز کنترل می‌شود (D-013، D-025). (ب) سامانه مرکزی فروشنده: مشتریان تجاری، محصولات، زیرسیستم‌ها، قراردادها، لایسنس‌ها، نصب‌ها، فعال‌سازی‌ها، تمدیدها و تاریخچه؛ Host، دیتابیس و هویت مدیران مستقل (D-021، D-029).

## D-042 — فعال‌سازی آنلاین و آفلاین با قالب و اعتبارسنج مشترک؛ تماس آنلاین اختیاری
- **وضعیت:** `Proposed` + `NeedsApproval` (OD-09 در `docs/LICENSING_OPEN_DECISIONS.md`) | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-24
- **زمینه و مسئله:** D-023 فقط مسیر آفلاین (فایل درخواست/پاسخ) را تصمیم گرفته و «اتصال اینترنتی همیشگی» را رد کرده است؛ فعال‌سازی/تمدید آنلاین تصمیم نشده است. مالک محصول می‌خواهد هر دو روش ترجیحاً قالب و منطق اعتبارسنجی مشترک داشته باشند و عملیات عادی حسابداری هرگز وابستهٔ سامانه مرکزی نباشد.
- **تصمیم پیشنهادی:**
  1. یک نوع `ActivationRequest` و یک `LicenseEnvelope` (`formatVersion`، `kid`، بایت‌های دقیق Payload، امضا؛ D-024) برای هر دو کانال. کانال فقط حمل است؛ اعتماد از امضا می‌آید، نه از TLS یا مسیر دریافت. یک اعتبارسنج در `Licensing.Contracts`.
  2. کانال آنلاین: نصب، بایت‌های همان درخواست را (با اقدام مدیر یا، اختیاری، زمان‌بندی‌شده) به Endpoint فروشنده می‌فرستد و پاکت را برمی‌گرداند؛ نصب آن را دقیقاً مثل ورود فایل محلی اعتبارسنجی می‌کند. شکست = بدون تغییر وضعیت لایسنس فعلی.
  3. فهرست مجاز فیلدهای درخواست (Allowlist) در قرارداد ثابت و با آزمون محافظت می‌شود: `installationId`، اثرانگشت کلید عمومی، نسخهٔ برنامه، `requestId`، `sequence` فعلی، مرجع مشتری مات (اختیاری). **داده حسابداری، کاربر، شرکت یا اسرار ارسال نمی‌شود.**
  4. **اولین فعال‌سازی نصب جدید:** اثبات تملک کلید به‌تنهایی حق‌دار بودن را ثابت نمی‌کند. اولین درخواست یک نصب باید یا (الف) با کد ثبت‌نام یک‌بارمصرف، منقضی‌شونده و وابسته به قرارداد که فروشنده جدا به مشتری می‌دهد همراه باشد (کد پس از اولین مصرف باطل می‌شود و Bearer دائمی نیست)، یا (ب) در صف تأیید دستی فروشنده بماند. بدون این‌ها درخواست رد/معلق می‌شود.
  4-ب. کنترل‌های Endpoint فروشنده: اثبات تملک کلید (درخواست با کلید خصوصی نصب امضا شود، نه راز مشترک)؛ `requestId` یک‌بارمصرف؛ `sequence` یکنواخت؛ Rate Limit به ازای `installationId` و IP؛ پاسخ خطای یکنواخت (بدون شمارش‌پذیری شناسه‌ها)؛ سقف اندازهٔ بدنه؛ ثبت ممیزی هر درخواست.
  5. هیچ عملیات عادی حسابداری سامانه مرکزی را صدا نمی‌زند؛ خطای شبکه هرگز وضعیت لایسنس را عوض نمی‌کند؛ تماس دوره‌ای اجباری وجود ندارد (OD-09 پیشنهاد (ب): اختیاری با یادآوری).
  6. نصب ابریِ مدیریت‌شده توسط فروشنده می‌تواند پاسخ «چه چیزی مجاز است؟» را از دیتابیس مرکزی بگیرد (D-021 بند ۴) ولی پشت همان قرارداد کاربردی و با کش؛ نه فراخوانی از راه دور برای هر درخواست.
- **گزینه‌های ردشده:** قالب جدا برای آنلاین و آفلاین (دو اعتبارسنج، دو سطح حمله)؛ کلید فعال‌سازی Bearer (`Rejected`: قابل جعل/نشت مانند Activation قدیمی)؛ تماس اجباری همیشگی (`Rejected`: D-023 ب).
- **پیامدها:** (+) یک مسیر اعتبارسنجی؛ تجربهٔ آنلاین بدون کاهش امنیت آفلاین. (−) Endpoint عمومی فروشنده سطح حملهٔ جدید است و باید Rate Limit/ممیزی داشته باشد.
- **آثار امنیتی و داده‌ای:** Replay، شمارش شناسه‌ها، DoS، افشای فراداده؛ بدون داده مالی.
- **نحوه مهاجرت:** هیچ در این مرحله. پیاده‌سازی پس از `Licensing.Contracts` (L1) و سامانهٔ مرکزی (L2).
- **معیار پذیرش و تأیید:** آزمون: همان پاکت با ورود فایل و کانال آنلاین به یک نتیجه می‌رسد؛ فیلد خارج از Allowlist رد می‌شود؛ `requestId` تکراری رد می‌شود؛ قطع شبکه لایسنس معتبر موجود را تغییر نمی‌دهد.
- **مراجع:** D-021، D-023، D-024، `docs/LICENSING_WORKFLOWS.md` بخش ۸.

## D-043 — هویت، MFA، تفکیک وظایف مدیران مرکزی و ممیزی مقاوم در برابر دست‌کاری

- **زمینه و مسئله:** D-029 هویت مدیر فروشنده را از هویت‌های دیگر جدا می‌داند ولی الزامات آن را تعیین نکرده است. شواهد وضع فعلی: حساب Master نصب یک راز مشترک در پیکربندی است و MFA ندارد (جست‌وجوی MFA/TOTP/Authenticator در `Server` و `Domain` نتیجه‌ای نداشت)؛ ممیزی فعلی `SecurityAuditEvent` (`Domain/SecurityAuditEvent.cs`، `Infrastructure/Persistence/Configurations/SecurityAuditEventConfiguration.cs`) جدول معمولی قابل ویرایش/حذف است، بدون زنجیرهٔ درستی؛ برای ممیزی صدور و ابطال لایسنس کافی نیست.

  1. **ساخت اولیه (OD-14):** ویزارد اولین اجرا پس از راه‌اندازی دیتابیس با توکن یک‌بارمصرف (الگوی D-010) و/یا فرمان اپراتور. مشخصات توکن: فقط روی کنسول سرور یا فایل با مجوز مالک‌تنها (0600/ACL)، ذخیرهٔ هش‌شده، انقضای کوتاه، مصرف در همان تراکنش ساخت؛ شرط بازبودن ویزارد «نشانگر دائمی راه‌اندازی‌نشده» است، نه صرفاً نبود `Company` (نصب‌های موجود ممکن است شرکتی نداشته باشند)؛ Rate Limit روی تلاش‌ها؛ در یک تراکنش و idempotent: اولین `Company`، مجموعهٔ نقش‌های پیش‌فرض و مجوزها، اولین `FiscalPeriod`، اولین کاربر با عضویت مدیر کل شرکت. بدون رمز ثابت مشترک (D-029 بند ۵). شرکت ساخته‌شده توسط ویزارد `CustomerBoundaryId = null` می‌گیرد (fail-closed، D-038)؛ تخصیص مرز فقط با Endpoint اپراتور D-038 انجام می‌شود. این قابلیت داده تجاری فروشنده را وارد نصب نمی‌کند.
  2. **حالت اعمال:** `Licensing:EnforcementMode = Off | Observe | Enforce`. `Observe`: ارزیابی و ممیزی بدون هیچ محدودیت. `Enforce` فقط پس از (الف) انتشار نسخه‌ای که مالک اعلام کند، (ب) صدور لایسنس اولیه برای مشتریان موجود. نصب بدون لایسنس در `Off`/`Observe` هرگز Restricted نمی‌شود. **محدودیت صادقانه:** اگر حالت فقط یک تنظیم محلی باشد، مشتری می‌تواند همیشه `Off` بماند؛ بنابراین از نسخهٔ اعمال به بعد، `Enforce` حداقل ثابت در کد همان نسخه است و پایین‌آوردنش فقط با لایسنس امضاشده (فیلد سیاست در Payload) ممکن است، نه با پیکربندی. این خطر برای نسخه‌های پیش از آن و نسخه‌های قدیمی همچنان باقی است (T28). `Off`/`Observe` فقط گذار زمان‌دار پیش از نسخهٔ اعمال است و الگوی ردشدهٔ D-021(الف) (مرز وابسته به فلگ پیکربندی) را دائمی نمی‌کند.
  3. **ایجاد اولین شرکت در حالت `Missing`:** مجاز (راه‌اندازی اولیه نباید به لایسنس گره بخورد)؛ سقف `maxCompanies` پس از وجود لایسنس اعمال می‌شود (D-022 بند ۵).
  4. **مهاجرت:** فقط افزایشی و آزمون‌پذیر، در مراحل بعد؛ هیچ Migration در فاز صفر. نسخه‌های قدیمی‌ای که کنترل لایسنس ندارند با نرم‌افزار قابل الزام نیستند؛ سیاست قراردادی (OD-10).
  5. **ممنوعیت‌ها:** انتقال داده حسابداری به سامانه مرکزی؛ هر حذف یا تغییر داده مشتری هنگام انقضا، انتقال، اصلاح یا ابطال لایسنس (D-026).
  6. **حذف کد مرده Activation (D-028)** در PR جدا و پس از تأیید؛ در همان PR، `ApplicationSettings.ActivationKeys` و ارجاع‌های `appsettings*.json` و `.env.example` پاک شوند.
- **گزینه‌های ردشده:** SQL دستی برای مشتری؛ فایل تدارک امضاشدهٔ فروشنده حاوی داده شرکت (`Rejected`: داده مشتری را به قالب لایسنس وصل می‌کند)؛ اعمال ناگهانی لایسنس (`Rejected`: D-026).
- **پیامدها:** (+) نصب تازه و نصب موجود هر دو مسیر روشن دارند. (−) قابلیت جدیدِ ویزارد دامنهٔ اضافه است و باید با مالک تأیید شود.
- **آثار امنیتی و داده‌ای:** توکن یک‌بارمصرف، محدودیت نرخ و ممیزی؛ تراکنشی؛ بدون رمز پیش‌فرض.
- **نحوه مهاجرت و بازگشت:** سوییچ `EnforcementMode` بازگشت سریع را ممکن می‌کند؛ بدون حذف داده.
- **معیار پذیرش و تأیید:** آزمون: نصب تازه بدون لایسنس شرکت اول را می‌سازد؛ نصب موجود با `Observe` رفتارش تغییر نمی‌کند؛ `Enforce` بدون لایسنس معتبر به `Restricted` می‌رود ولی هیچ ردیف داده‌ای حذف نمی‌شود؛ ویزارد دوم‌بار اجرا نمی‌شود.

## D-045 — تصمیم نهایی OD-01، OD-02 و OD-12 برای هستهٔ قرارداد لایسنس
- **وضعیت:** `Accepted` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-25
- **تصمیم‌های تأییدشدهٔ مالک محصول:**
  1. **مرز تجاری و فنی (OD-01):** حق/قرارداد تجاری در سطح `CustomerAccount` در سامانهٔ فروشنده نگهداری می‌شود؛ هر `Installation` یک لایسنس فنی امضاشدهٔ مستقل دارد. `Company` مستقیماً به رکورد تجاری لایسنس وصل نمی‌شود.
  2. **سقف‌ها و زیرسیستم‌ها (OD-02):** نسخهٔ اول Payload شامل `maxCompanies` و فهرست کدهای پایدار زیرسیستم‌هاست: `finance`, `sales`, `inventory`, `treasury`. سقف `maxUsers` به بعد موکول است (`Deferred`)، نه اینکه در نسخهٔ اول با مقدار ضمنی یا ساختار مبهم پشتیبانی شود. سقف تعداد نصب در سامانهٔ فروشنده پیگیری می‌شود و ادعای اعمال آفلاین آن در نصب مشتری نداریم.
  3. **امضای دیجیتال (OD-12):** ECDSA روی منحنی P-256 با SHA-256؛ امضا به قالب IEEE P1363 ثابت با طول دقیق 64 بایت رمزگذاری می‌شود. امضا روی بایت‌های دقیق Payload است؛ اعتبارسنجی نباید JSON را مجدداً سریال‌سازی و سپس امضا را روی خروجی جدید بررسی کند. بردارهای آزمون باید روی Linux و Windows اجرا شوند.
- **قیود امنیتی و پیاده‌سازی:** کلید خصوصی صدور فقط در مرز امن فروشنده باقی می‌ماند؛ در Git، CI، بستهٔ مشتری، دیتابیس مشتری یا گزارش قرار نمی‌گیرد. اعتبارسنج نصب فقط به کلید عمومی اعتماد می‌کند. فرمت/نسخهٔ ناشناخته، طول امضای نادرست، Payload دست‌کاری‌شده و امضای نامعتبر باید fail-closed رد شوند.
- **دامنهٔ این تصمیم:** فقط قرارداد و قواعد رمزنگاری L1 را باز می‌کند. سامانهٔ مرکزی، نگهداری/چرخش کلید (OD-07)، MFA/تفکیک وظایف (OD-11)، انقضا/مهلت ارفاق، سیاست ساعت، Migration و Enforcement هنوز تصمیم/کار مستقل دارند. هیچ Schema یا Migration با این ADR مجاز نمی‌شود.
- **پیامدها:** L1 می‌تواند ساخت `Licensing.Contracts` و آزمون‌های قطعی را آغاز کند. تا زمانی که قرارداد و بردارها روی هر دو سیستم‌عامل تأیید نشده‌اند، سازگاری Windows/Linux `NotVerified` می‌ماند.
- **رابطه با ADR قبلی:** D-045 تصمیم انتخاب الگوریتم OD-12 را بر پیشنهاد قبلی D-024 مقدم می‌کند؛ سایر موضوعات D-024 که در این ADR پوشش داده نشده‌اند باید جداگانه بررسی شوند.
- **مراجع:** Issue #80; `LICENSING_OPEN_DECISIONS.md` OD-01/02/12; `LICENSING.md` sections 4–7.


## D-046 — امنیت و عملیات سامانهٔ مرکزی فروشنده
- **وضعیت:** `Accepted` | پیاده‌سازی `NotImplemented`
- **تاریخ:** 2026-10-25
- **تصمیم صریح مالک محصول:** پیشنهادهای OD-07، OD-09 و OD-11 تأیید شدند؛ سامانه از ابتدا باید چندمدیره و آمادهٔ کنترل دو نفره برای عملیات پرخطر باشد.
- **OD-07 — حفاظت و چرخش کلید:**
  1. کلید ریشهٔ اعتماد آفلاین و جدا از مسیر روزمرهٔ صدور نگهداری می‌شود؛ کلید عمومی ریشه در اعتبارسنج مشتری به‌عنوان لنگر اعتماد تعبیه می‌شود.
  2. کلیدهای صدور با شناسهٔ `kid` و بازهٔ اعتبار مستقل و قابل چرخش‌اند. عملیات امضا از طریق abstraction محدود `SigningKeyProvider` انجام می‌شود؛ برنامهٔ فروشنده حق دریافت/export کلید خصوصی را ندارد.
  3. محیط Production از KMS/HSM دارای مجوز «فقط امضا» استفاده می‌کند؛ KMS انتخاب پیش‌فرض عملیاتی است و پیاده‌سازی provider به فروشندهٔ خاص گره نمی‌خورد. HSM گزینهٔ معادل برای محیط‌های بدون KMS است. کلید نرم‌افزاری فقط برای توسعه با کلید آزمایشی غیرتولیدی مجاز است، نه fallback خودکار Production.
  4. امضا در GitHub Actions، مخزن، دیتابیس، log یا بستهٔ مشتری انجام/ذخیره نمی‌شود. چرخش کلید باید شامل انتشار بستهٔ اعتماد امضاشده با ریشه، هم‌پوشانی دورهٔ اعتبار، آزمون بازیابی و رویهٔ ابطال/جایگزینی باشد؛ افشای کلید، رخداد امنیتی و نیازمند چرخش اضطراری است.
- **OD-09 — ارتباط آنلاین:** تماس نصب مشتری با فروشنده اختیاری است. هیچ heartbeat یا اتصال دوره‌ای اجباری و هیچ وابستگی شبکه‌ای برای عملیات حسابداری عادی وجود ندارد. فعال‌سازی/تمدید آنلاین فقط یک مسیر کمکی است که از همان قرارداد و اعتبارسنج آفلاین استفاده می‌کند، ضد-Replay و Rate Limit دارد، و هیچ دادهٔ حسابداری ارسال نمی‌کند. قطع اینترنت به‌خودی‌خود لایسنس معتبر را نامعتبر نمی‌کند؛ قواعد انقضای قراردادی مستقل از دسترس‌پذیری شبکه‌اند.
- **OD-11 — هویت مدیران و تفکیک وظایف:**
  1. MFA برای تمام حساب‌های انسانی مرکزی اجباری است؛ Passkey/WebAuthn روش ترجیحی و TOTP روش جایگزین است. پیامک عامل دوم قابل قبول نیست. حساب‌های سرویس غیرتعاملی هویت و مجوز محدود جداگانه دارند.
  2. RBAC با حداقل دسترسی و نقش‌های جدا برای مشاهده، مدیریت مشتری/قرارداد، صدور، تأیید، ابطال، امنیت و عملیات کلید پیاده می‌شود؛ دسترسی‌ها در سمت سرور بررسی می‌شوند و نقش UI کافی نیست.
  3. عملیات پرخطر از الگوی maker-checker استفاده می‌کند: صادرکننده نمی‌تواند درخواست خودش را تأیید کند. این قاعده حداقل برای صدور/تغییر لایسنس دائمی، ابطال/تعلیق، تغییر سقف/زیرسیستم قرارداد، فعال‌سازی یا چرخش کلید، تغییر سیاست امنیتی و عملیات بازیابی اضطراری اعمال می‌شود. ثبت درخواست، تأیید، اجرا و نتیجه در ممیزی غیرقابل‌دست‌کاری ثبت می‌شود.
  4. پیش از Production باید دست‌کم دو مدیر واجد شرایط و مسیر بازیابی کنترل‌شده وجود داشته باشد؛ نبود تأییدکنندهٔ دوم نباید به دورزدن بی‌صدا منجر شود. حساب break-glass فقط برای بازیابی اضطراری، با حفاظت قوی، اعلان فوری، ثبت ممیزی و بازبینی پس از رخداد است؛ استفادهٔ روزمره ممنوع است.
- **مرز این ADR:** انتخاب سرویس‌دهنده/محصول KMS، جزئیات استقرار، سیاست نگهداری رویدادها و طرح بازیابی باید در پیکربندی/راهنمای استقرار و Issueهای اجرایی تثبیت شوند. هیچ کلید واقعی، Secret، Schema/Migration، endpoint یا Enforcement صرفاً با این ADR ایجاد نمی‌شود.
- **پیامدها:** طراحی L2 باید از ابتدا provider-agnostic برای امضا، چندمدیره، MFA اجباری، تأیید مستقل و ممیزی مقاوم در برابر دست‌کاری باشد. آزمون‌های منفی برای دورزدن maker-checker، MFA، مجوزهای نقش و دست‌کاری ممیزی معیار پذیرش‌اند.
- **مراجع:** Issue #83؛ `LICENSING_OPEN_DECISIONS.md` OD-07/09/11؛ D-041..D-045.

Passkey/WebAuthn ترجیح دارد و TOTP جایگزین است؛ SMS پذیرفته نیست. فقط APIهای پشتیبانی‌شدهٔ پلتفرم و کتابخانه‌های نگهداری‌شده استفاده می‌شوند؛ پیاده‌سازی رمزنگاری/پروتکل احراز هویت سفارشی ممنوع است. قبل از انتخاب کتابخانه یا فعال‌سازی Passkey باید سازگاری واقعی .NET 10 و تست Integration تأیید شود.
  4. **Bootstrap کنترل‌شده:** راه‌اندازی نخستین مدیر فقط از مسیر اپراتوری یک‌بارمصرف/محدود و با Secret خارج از مخزن انجام می‌شود؛ endpoint ثبت‌نام عمومی وجود ندارد. bootstrap باید idempotent، ممیزی‌شده و پس از استفاده غیرقابل‌استفادهٔ مجدد باشد. وضعیت آمادگی Production وقتی کمتر از دو مدیر فعالِ واجد MFA وجود دارد fail-closed است؛ در نبود تأییدکنندهٔ دوم، عملیات پرخطر اجرا نمی‌شود.
  5. **Maker-checker:** درخواست عملیات حساس، تأیید مستقل و اجرای آن سه مرحلهٔ صریح و ممیزی‌شده‌اند. درخواست‌کننده نمی‌تواند تأییدکنندهٔ همان درخواست باشد؛ بررسی این قاعده فقط در UI نیست و در سرویس کاربردی/پایگاه داده و تست‌های منفی اعمال می‌شود. درخواست تکراری، تأیید هم‌زمان و اجرای مجدد باید idempotency/concurrency کنترل داشته باشند.
  6. **ممیزی قابل‌کشف:** رخدادهای حساس در دفتر ممیزی با زنجیرهٔ هش/پیوند به رخداد قبلی ثبت می‌شوند؛ دسترسی برنامه به رخدادهای ثبت‌شده محدود به درج است. چون زنجیرهٔ هش در همان دیتابیس به‌تنهایی دستکاری توسط DBA را ناممکن نمی‌کند، طرح باید اعتبارسنجی زنجیره و export/checkpoint دوره‌ای به مقصدی با مجوز مستقل را مشخص کند. رمز، توکن، کلید خصوصی و داده مالی در رخدادها ثبت نمی‌شود.
  7. **امضا و KMS:** لایهٔ کاربردی فقط عملیات Sign را از `SigningKeyProvider` می‌خواهد و کلید خصوصی را دریافت یا export نمی‌کند. محیط Production در نبود KMS/HSM آماده باید fail-closed شود؛ fallback به فایل کلید یا کلید نرم‌افزاری ممنوع است. انتخاب محصول KMS/HSM، روش بازیابی، alerting و runbook تا تعیین محیط استقرار باز می‌ماند.
  8. **انتشار و تست:** Vendor در Solution/Workflow قابل آزمون مستقل نگهداری می‌شود؛ تست‌های Integration از SQL Server واقعی استفاده می‌کنند. گاردهای جداسازی باید ثابت کنند کد Vendor وارد بستهٔ مشتری نشده و هیچ Migration روی دیتابیس مشتری ایجاد نشده است.
- **گزینه‌های ردشده:** استفاده از دیتابیس/Identity مشتری؛ ثبت‌نام عمومی مدیر؛ حساب مدیر پیش‌فرض؛ fallback کلید نرم‌افزاری در Production؛ اتکا به مخفی‌کردن دکمه در UI برای maker-checker؛ ادعای «ممیزی غیرقابل‌تغییر» صرفاً به‌دلیل hash chain داخل همان دیتابیس.
- **پیامدها:** مرز امنیتی و استقرار روشن‌تر و چندمدیره از ابتدا؛ در عوض، عملیات bootstrap، بازیابی و ممیزی نیازمند Runbook و تست عملیاتی است. تا زمانی که ADR بازبینی و پذیرفته نشده، این موارد پیشنهادند.
- **مواردی که هنوز نیازمند تعیین محیط/تصمیم جدا هستند:** ارائه‌دهندهٔ KMS/HSM؛ جزئیات runbook بازیابی و break-glass؛ سیاست نگهداری/آرشیو ممیزی و مقصد مستقل checkpoint؛ تنظیمات نهایی محیط Production.
