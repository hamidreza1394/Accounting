# آمادگی مقیاس‌پذیری و کاربران هم‌زمان ابری

- **Issue:** [#49](https://github.com/hamidreza1394/Accounting/issues/49)
- **تاریخ ممیزی:** 2026-10-22
- **مبنای مستندات:** شاخه `main` و فایل‌های خوانده‌شده از مخزن GitHub در تاریخ بالا؛ هر یافته باید با commit واقعی شاخه کاری Agent پیاده‌ساز دوباره بررسی شود.
- **وضعیت کلی:** `NotVerified` برای ظرفیت ۱۰۰ کاربر هم‌زمان. در این ممیزی آزمون بار اجرا نشده و نباید ادعای آمادگی بار یا SLA مطرح شود.

## 1. هدف و تعریف ظرفیت

هدف محصول این است که حداقل 100 کاربر مجازی هم‌زمان بتوانند سناریوهای نماینده استفاده از برنامه را اجرا کنند، بدون خطای کنترل‌نشده، نقض صحت مالی یا نشت اطلاعات میان مشتریان. «کاربر واردشده»، «کاربر مجازی فعال در آزمون» و «درخواست هم‌زمان در حال اجرا» سه مفهوم متفاوت‌اند؛ گزارش آزمون باید مدل بار، نرخ ورود درخواست، think time، مدت آزمون و تعداد کاربران را مشخص کند.

معیار اولیه پیشنهادی برای عملیات معمول غیرسنگین:
- 100 کاربر مجازی هم‌زمان در سناریوی بار ترکیبی.
- هدف اولیه p95 حداکثر 2 ثانیه برای عملیات معمول منتخب، نه همه گزارش‌ها و نه یک SLA تضمین‌شده.
- خطاهای HTTP غیرمنتظره کمتر از 1% در بازه پایدار آزمون؛ خطاهای مورد انتظار مانند 401/403/validation باید جدا گزارش شوند.
- بدون نقض invariant مالی، دوباره‌ثبت‌شدن عملیات، نشت tenant یا خطای unhandled.
- آزمون افزایشی 150/200 کاربر برای پیدا کردن نقطه افت؛ آزمون soak جداگانه برای نشتی منابع.
این اعداد هدف آزمون‌اند و با اندازه‌گیری و تأیید مالک قابل تنظیم‌اند، نه ادعای عملکرد فعلی.

## 2. معماری فعلی مشاهده‌شده

- Modular Monolith؛ یک میزبان ASP.NET Core در `Server`، نه معماری microservices.
- هدف چارچوب `.NET 10 / C# 14`، EF Core 10 و SQL Server؛ نسخه‌های NuGet از `Directory.Packages.props` مدیریت می‌شوند.
- صفحات موجود Razor Pages، API هم‌مبدأ زیر `/api/v1` و کلاینت React + TypeScript + Vite در `ClientApp` با خروجی `Server/wwwroot/app`.
- لایه‌های Domain، Application (در حال حاضر اسکلت/مهاجرت تدریجی)، Infrastructure.Persistence و Server. مستندات معماری تصریح می‌کنند که Clean Architecture هنوز کامل نیست و برخی PageModelها مستقیم به Persistence وابسته‌اند.
- دسترسی شرکت باید از `Infrastructure.Tenancy.CompanyAccessService` و عضویت فعال تعیین شود. به TenantId/شناسه شرکت ارسالی کلاینت یا Claim قابل‌تغییر اعتماد نشود؛ تصمیم D-013 را با فیلتر عمومی جایگزین نکن.
- Cookie هم‌مبدأ و Anti-forgery برای عملیات تغییردهنده، Rate Limiting ورود و تنظیمات Forwarded Headers برای Proxyهای صریحاً مورد اعتماد وجود دارد.
- CI گزارش‌شده در `docs/PROJECT_STATUS.md` شامل Build، تست .NET، تست کلاینت، E2E و اسکن NuGet است؛ این شواهد به‌خودی‌خود آزمون ظرفیت نیستند.

## 3. یافته‌های ممیزی

### شواهد مثبت موجود

1. قواعد Async I/O و انتقال CancellationToken در `AGENTS.md` آمده‌اند و نمونه‌های API از CancellationToken استفاده می‌کنند.
2. Rate Limiting و پیکربندی Reverse Proxy در کد ثبت شده‌اند. طبق `docs/DEPLOYMENT.md`، محدودیت‌ها فعلاً به‌ازای هر نمونه هستند.
3. تست‌های Unit/Integration و CI با SQL Server موقت وجود دارند؛ تست‌های صحت/امنیت فعلی جایگزین آزمون بار نیستند.
4. راهبرد امنیت tenant، Cookie/Anti-forgery و جلوگیری از اعتماد به شناسه ارسالی کلاینت مستند است.
5. معماری Modular Monolith امکان افزایش منابع و در صورت اثبات نیاز، اجرای چند نمونه Web را بدون مهاجرت فوری به microservices می‌دهد.

### مواردی که هنوز «نقص اثبات‌شده» نیستند

- ظرفیت Connection Pool، تعداد اتصال SQL، deadlock rate، CPU/RAM، latency و تعداد queryها از روی سورس به‌تنهایی قابل تعیین نیستند؛ با تنظیمات محیط و اندازه‌گیری بررسی شوند.
- نبود Redis، message broker، Kubernetes، cache توزیع‌شده یا microservices به‌خودی‌خود نقص نیست. این‌ها فقط با نیاز واقعی و ADR مطرح شوند.
- وجود async/await در بخشی از کد اثبات نمی‌کند تمام مسیرها async، بدون contention یا سریع‌اند.
- افزودن چند نمونه برنامه به‌تنهایی high availability ایجاد نمی‌کند؛ خرابی میزبان، دیتابیس و شبکه باید جدا تحلیل شود.

## 4. برنامه آزمون مورد نیاز

### سناریوهای بار

1. ورود و دریافت context/فهرست شرکت‌های مجاز.
2. خواندن فهرست‌ها با صفحه‌بندی و جست‌وجو.
3. درخواست‌های خواندنی ترکیبی با think time واقع‌گرایانه.
4. عملیات نوشتن فقط روی endpoint واقعی و مجاز؛ در صورت نبود ماژول حسابداری، این محدودیت صریح ثبت شود و endpoint مصنوعی جایگزین آزمون مالی نشود.
5. گزارش‌گیری در حجم نماینده، پس از پیاده‌سازی گزارش واقعی.
6. رقابت چند کاربر روی یک شرکت/منبع مشترک و هم‌زمانی میان چند tenant.
7. تست 100 کاربر، افزایش تدریجی تا 150/200، و soak حداقل 30 دقیقه برای یافتن رشد تدریجی مصرف منابع. مدت و بار نهایی با هزینه محیط تنظیم شود.

### خروجی‌های الزامی

- commit SHA، نسخه برنامه، ابزار و نسخه آن، مشخصات VM/container، CPU/RAM، سیستم‌عامل، SQL Server edition/version و محل دیتابیس.
- مدل بار: کاربران مجازی، نرخ درخواست، think time، ramp-up، duration، تعداد iteration و سناریوها.
- p50/p95/p99، throughput، نرخ خطا، timeout، 429، 5xx، CPU/RAM، GC/ThreadPool، latency و waitهای SQL، تعداد اتصال فعال/منتظر و deadlock.
- شمارش و صحت داده‌های پیش/پس آزمون؛ تأیید عدم تکرار عملیات و عدم دسترسی cross-tenant.
- bottleneckهای مشاهده‌شده، فرضیه‌ها، تغییر پیشنهادی، نتایج قبل/بعد و محدودیت‌های اندازه‌گیری.

### ایمنی اجرای آزمون

- فقط محیط isolated/staging با داده مصنوعی و مجوز صریح؛ هرگز بار 100 کاربر را روی Production بدون تأیید اجرا نکن.
- بار را تدریجی افزایش بده و سقف هزینه/منابع و شرط توقف مشخص کن.
- از حساب‌ها و داده‌های واقعی مشتری استفاده نکن؛ از ایجاد/حذف داده مالی واقعی اجتناب شود.
- آزمون‌های نوشتن باید idempotent یا با cleanup/fixture ایمن باشند و اثرات جانبی بیرونی نداشته باشند.

## 5. راهبرد پیاده‌سازی

1. ابتدا ابزار/فایل‌های موجود و CI را دوباره بررسی کن؛ از افزودن dependency جدید بدون دلیل خودداری کن.
2. ابزار load test را انتخاب و دلیل آن را در همین سند یا ADR ثبت کن. ابزار می‌تواند خارج از runtime برنامه باشد.
3. آزمون‌های baseline برای endpointهای واقعی موجود اضافه کن و نتایج را گزارش کن؛ ماژول‌های حسابداری پیاده‌نشده را «تست‌شده» معرفی نکن.
4. فقط گلوگاه اثبات‌شده را اصلاح کن. هر اصلاح با regression test و اندازه‌گیری قبل/بعد همراه باشد.
5. بهبود SQL، ایندکس، projection، paging، async/cancellation و طول عمر DbContext را موردی انجام بده.
6. قبل از اجرای چند نمونه، state محلی، Cookie/Data Protection keys، فایل موقت، rate limits، health checks، graceful shutdown و استقرار را بررسی کن.
7. تصمیم درباره cache توزیع‌شده، rate limiting توزیع‌شده، queue یا زیرساخت چندنمونه‌ای تنها با شواهد و ADR؛ از over-engineering اجتناب کن.
8. پس از تغییرات، Build/Test کامل، E2E، بررسی migration (در صورت تغییر مدل)، تست امنیتی مرتبط و آزمون بار تکراری انجام بده.

## 6. وضعیت فعلی و معیار ادعا

- ظرفیت 100 کاربر هم‌زمان: `NotVerified`.
- ظرفیت 200 کاربر: `NotVerified`.
- پایداری multi-instance: `NotVerified`؛ تعداد نمونه‌ها و محیط واقعی نامشخص است.
- صحت رقابت عملیات حسابداری: `NotImplemented/NotVerified`؛ ماژول‌های حسابداری هنوز وجود ندارند.
- CI سبز به‌تنهایی معیار آمادگی بار یا دسترس‌پذیری Production نیست.

هر تغییر وضعیت به `Verified` باید به گزارش آزمون واقعی، commit SHA و محیط قابل بازتولید ارجاع دهد.
