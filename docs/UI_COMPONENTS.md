# استاندارد رابط کاربری فرانو — shadcn/ui

## وضعیت

- تصمیم معماری: پذیرفته‌شده برای رابط React جدید در `ClientApp`.
- وضعیت پیاده‌سازی: CLI رسمی `shadcn@4.22.1` در `devDependencies` پین شده؛ `Button` و `Card` از CLI تولید و در مخزن نگهداری می‌شوند؛ وابستگی‌ها و `package-lock.json` با npm هماهنگ‌اند. این تغییر از Button در retry خطا و از Card در پنل اطلاعات شرکت/دوره مالی استفاده می‌کند. CI نهایی این تغییر باید همه تست‌ها را دوباره اجرا کند.
- مبنای primitives: Base UI (`@base-ui/react`) با سبک `base-nova`؛ RTL در `components.json` فعال است.
- تابع ادغام کلاس‌ها از بستهٔ رسمی `cn` استفاده می‌کند (`src/lib/utils.ts` آن را re-export می‌کند). بسته‌های بلااستفاده `clsx` و `tailwind-merge` نگه داشته نشده‌اند.
- دامنه: فقط کلاینت React؛ صفحات Razor قدیمی را بدون نیازمندی مستقل بازنویسی نکنید.

## اصول انتخاب‌شده

1. **Source-owned components:** کامپوننت‌های shadcn/ui باید در مخزن و زیر `ClientApp/src/components/ui` نگهداری شوند؛ این پروژه یک UI runtime خارجی یا hosted service نیست.
2. **پشته موجود را ارتقا ندهید صرفاً برای shadcn:** مبنا React 19، TypeScript strict، Vite و Tailwind CSS v4 است. نسخه‌های موجود را حفظ کنید مگر CI/سازگاری رسمی دلیلی برای تغییر نشان دهد.
3. **RTL فارسی از ابتدا:** پیکربندی shadcn باید RTL را فعال کند؛ از کلاس‌های منطقی CSS/Tailwind، جهت صحیح برای portalها و اصلاح جهت آیکون‌های جهت‌دار استفاده کنید. وجود `dir="rtl"` روی سند به‌تنهایی همهٔ popover/dialog/tooltipها را تضمین نمی‌کند.
4. **Offline-first:** در runtime هیچ CSS، JavaScript، فونت یا آیکونی از CDN یا اینترنت بارگیری نشود. کد کامپوننت‌ها و وابستگی‌های runtime باید در npm lockfile ثبت و در build bundle شوند.
5. **استفاده هدفمند:** فقط کامپوننت‌های موردنیاز را اضافه کنید؛ از `add --all` و تغییر گستردهٔ ظاهر بدون نیازمندی خودداری کنید. UI موجود را یک‌باره بازنویسی نکنید.
6. **طراحی مالی حرفه‌ای:** رنگ‌ها و توکن‌های طراحی باید با هویت سرمه‌ای/طلایی فرانو، خوانایی اعداد مالی، وضعیت‌های هشدار/خطا و تراکم اطلاعات ERP سازگار باشند. رنگ به‌تنهایی نباید وضعیت را منتقل کند.
7. **دسترس‌پذیری:** صفحه‌کلید، focus قابل مشاهده، labelهای واقعی، نام accessible، کنتراست و رفتار dialog/menu/combobox باید بررسی شوند.
8. **امنیت:** کامپوننت UI جایگزین authorization سمت سرور، validation، anti-forgery یا کنترل tenant نیست. اطلاعات محرمانه در DOM، log یا storage مرورگر ذخیره نشود.

## مسیر و قراردادهای پیشنهادی

- پیکربندی: `ClientApp/components.json`
- کامپوننت‌های تولیدشده/سفارشی: `ClientApp/src/components/ui/`
- توابع کمکی کلاس‌ها: `ClientApp/src/lib/utils.ts` (re-export از بستهٔ `cn`)
- استایل اصلی: `ClientApp/src/styles/index.css`
- تست‌ها: Vitest + Testing Library؛ تست تعاملی برای کامپوننت‌های مهم و تست RTL برای رفتارهای جهت‌دار.
- آیکون‌ها: مجموعهٔ محلی بسته‌بندی‌شده؛ استفاده از URL خارجی ممنوع.
- نسخه‌ها: تغییر `package.json` و `package-lock.json` باید با هم و با `npm ci` معتبر انجام شود.

## فرآیند افزودن کامپوننت

1. مشخص کنید کدام صفحه/جریان واقعاً به کامپوننت نیاز دارد.
2. نسخهٔ CLI و peer dependencyها را از مستندات رسمی و package metadata بررسی کنید؛ نسخهٔ preview را وارد Production نکنید.
3. CLI پین‌شده را با `npx shadcn add <component> --yes` اجرا کنید؛ فقط کامپوننت‌های لازم را اضافه کنید و diff تولیدشده را بازبینی کنید.
4. `npm ci`، `npm run typecheck`، `npm test`، `npm run build` و `npm run check:offline` را اجرا کنید.
5. رفتار RTL، صفحه‌کلید، responsive، ظاهر فارسی و نبود درخواست خارجی را بررسی کنید.
6. در صورت تغییر توکن‌ها یا قراردادها همین سند و `docs/DECISIONS.md` را به‌روز کنید.

## قواعد طراحی، سرعت و ویژوال برای همهٔ Agentها

برای نرم‌افزار حسابداری سه چیز هم‌وزن‌اند: کیفیت طراحی، سرعت بارگذاری و ویژوال‌های داده. این قواعد برای هر Agent و توسعه‌دهنده (Claude، Codex، Copilot، Cursor و انسان) در هر کار روی `ClientApp` الزامی است.

### تمایز بصری تب‌ها
- تب‌های Workspace و تب‌های داخلی فرم‌ها باید از نظر رنگ پس‌زمینه، متن و نشانگر فعال به‌وضوح قابل تشخیص باشند؛ تب فعال از رنگ سرمه‌ای با متن روشن و تأکید طلایی استفاده کند و تب‌های غیرفعال سطح آبی/خاکستری ملایم با متن خوانا داشته باشند.
- وضعیت‌های Dirty، Saving و Error علاوه بر رنگ، با نشانگر/آیکون و متن دسترس‌پذیر اعلام شوند؛ رنگ به‌تنهایی معنا نرساند. کنتراست، focus قابل مشاهده، RTL و کاهش حرکت رعایت شود.
- این قاعده باید با توکن‌های موجود فرانو اجرا شود و به کتابخانه یا وابستگی جدید نیاز ندارد.

### کیفیت طراحی
- پیش از کدنویسی هر صفحه، یک جهت بصری روشن را در یک جمله بنویسید و آن را به هویت فرانو (سرمه‌ای/طلایی، دقت، اعتماد، فارسی/RTL) گره بزنید. صفحهٔ شبیه قالب عمومی یا «ساخته‌شده با هوش مصنوعی» پذیرفته نیست.
- داخل برنامه (فرم، دفتر، گزارش، تنظیمات) وضوح، خوانایی و کارایی بر جلوه مقدم است: ارقام هم‌تراز با ارقام جدولی، رنگ فقط برای داده و وضعیت، عنوان روشن صفحه، حاشیه‌های برابر، بدون فضای خالی تصادفی.
- جهت بصری پررنگ فقط برای ورود، صفحهٔ معرفی، حالت‌های خالی، آغاز به کار (onboarding) و سرصفحهٔ داشبورد مجاز است.
- فقط از کامپوننت‌های shadcn/ui و توکن‌های `src/styles/index.css` استفاده کنید؛ رنگ دلخواه (hex) یا سیستم طراحی دوم ممنوع است. ابتدا کامپوننت‌های موجود را بخوانید و گسترش دهید.
- حرکت و انیمیشن فقط برای نشان‌دادن تغییر وضعیت و با رعایت `prefers-reduced-motion`؛ در صفحات ورود داده بدون حرکت اضافی.

### سرعت (با عدد، نه حدس)
- پیش از ساخت صفحه، وضعیت فعلی را اندازه بگیرید و سقف حجم/زمان را در Issue بنویسید. این سند عدد ثابتی تعیین نمی‌کند، چون مبنای فعلی هنوز اندازه‌گیری نشده است.
- هر تغییر UI گزارش می‌دهد: اندازهٔ باندل از خروجی `npm run build` (پیش و پس)، و در صورت امکان LCP، CLS و زمان رسیدن اولین داده در مرورگر واقعی. عددی که اندازه‌گیری نشده با عبارت «اندازه‌گیری نشد» ثبت شود.
- کدسپلیت برای صفحه‌ها و بخش‌های سنگین (نمودار، جدول بزرگ)؛ اسکلت بارگذاری (skeleton) به جای صفحهٔ پر از اسپینر؛ چیدمان پایدار بدون CLS؛ مجازی‌سازی جدول‌های بلند؛ debounce جست‌وجو؛ صفحه‌بندی و کش خواندن API؛ به‌روزرسانی خوش‌بینانه فقط جایی که سرور می‌تواند ایمن رد کند.
- هر داده‌نما حالت‌های بارگذاری، خالی، خطا همراه تلاش مجدد و جزئی را دارد.
- وابستگی سنگین یا جدید بدون توجیه و تأیید ممنوع است.

### ویژوال‌های داده
- ویژوال بومی محصول مقدم است: نمودار، sparkline، کاشی KPI، جدول با نوار درون‌خطی و حالت‌های خالی معنادار؛ عکس استوک ممنوع است.
- نمودار: دسترس‌پذیر (فقط با رنگ معنا نرسد)، سازگار با RTL، ارقام فارسی، واحد پول مشخص (ریال یا تومان) و سبک برای زمان بارگذاری. پیش از ساخت نمودار، راهنمای `dataviz` (در صورت در دسترس بودن) را بخوانید.
- تصویر و ایلاستریشن فقط محلی و بهینه (SVG یا WebP) با مجوز ثبت‌شده؛ منبع بیرونی ممنوع (قانون محلی‌سازی پایین).

### غیرقابل‌مذاکره
- WCAG 2.1 AA، مسیر کامل صفحه‌کلید، RTL کامل با ویژگی‌های منطقی (`ms-`، `me-`، `ps-`، `pe-`)، آیکون‌های جهت‌دار آینه‌شده، ارقام/کد لاتین/مبلغ جدا با `dir="ltr"` یا `<bdi>`، و نمایش همیشگی شرکت و سال مالی جاری.
- بررسی در سه عرض ۳۶۰، ۷۶۸ و ۱۲۸۰ پیکسل، با RTL و فقط صفحه‌کلید؛ سه مشکل برتر را رفع کنید (تا سه دور).

### رفتار Agent
- اگر درخواستی صفحهٔ عمومی/قالبی یا کند تولید می‌کند، هشدار بدهید و جهت هدفمندتر پیشنهاد کنید.
- پیش از افزودن وابستگی، منبع تصویر یا انحراف از استانداردهای shadcn/RTL، توجیه کنید و بپرسید.
- پایان هر کار UI را با این چهار مورد ببندید: اعداد اندازه‌گیری‌شده، آنچه رد شد، آنچه بررسی نشد، و ریسک‌های بصری/دسترس‌پذیری/سرعت.

## کتابخانه‌ها، KendoReact، پیوت و مهارت ui-ux-pro-max (خلاصه)

جزئیات، جدول‌ها و شروط در [`docs/UI_LIBRARIES.md`](UI_LIBRARIES.md) است. خلاصهٔ تصمیم‌ها (D-049، D-050): جدول و گرید: TanStack Table v8 + TanStack Virtual با کامپوننت‌های جدول shadcn؛ فهرست‌های ساده: گرید رایگان KendoReact با شرط (بدون هیچ قابلیت پولی، یک گرید در هر صفحه)؛ نمودار: نمودارهای shadcn (Recharts)؛ تاریخ شمسی: `Calendar` shadcn با `react-day-picker/persian` (ذخیره ISO، نمایش از `src/lib/date.ts`)؛ پیوت: ابتدا جمع‌زدن در SQL سمت سرور و نمایش با TanStack، پیوت آزاد فقط با نیاز واقعی و ADR.

**پیش از انتخاب یا افزودن هر کتابخانهٔ جدول، نمودار، تاریخ یا پیوت، یا اجرای مهارت `ui-ux-pro-max`، `docs/UI_LIBRARIES.md` را بخوان.**

**ممنوع مگر با ADR و تأیید صریح مالک:** بخش‌های پولی KendoReact/Telerik (از جمله PivotGrid)، AG Grid Enterprise، ApexCharts، هر کتابخانهٔ UI یا سیستم طراحی دوم که با shadcn/Tailwind رقابت کند، و هر وابستگی یا منبع تصویر جدید بدون توجیه.

## قانون محلی‌سازی کامل دارایی‌ها (آفلاین)

هدف: قطع اینترنت نباید اجرای برنامه را مختل کند. این قانون برای همهٔ Agentها و توسعه‌دهندگان الزامی است و قاعدهٔ «بدون CDN» در `AGENTS.md` بخش ۲ را برای کامپوننت‌ها و کتابخانه‌های UI دقیق‌تر می‌کند.

1. هر کامپوننت، کتابخانه، فونت، آیکون، تصویر یا داده‌ٔ کمکی **ابتدا دانلود و داخل پروژه قرار می‌گیرد** و فقط از مسیر محلی خوانده می‌شود. لینک به صفحه یا سرویس بیرونی برای بارگیری در زمان اجرا ممنوع است.
2. موارد ممنوع در زمان اجرا: `<script src="https://…">`، `<link href="https://…">`، `@import url(http…)`، `import("https://…")`، فراخوانی `fetch` برای فونت/آیکون/تصویر/نقشه، تصویر hotlink، `iframe` بیرونی و فونت یا ابزار تحلیلی میزبانی‌شده در بیرون.
3. محل و روش نگهداری هر نوع دارایی:

   | نوع | محل در مخزن | روش |
   |---|---|---|
   | کامپوننت shadcn/ui | `ClientApp/src/components/ui/` | CLI پین‌شده؛ کد تولیدشده در مخزن commit می‌شود |
   | کتابخانهٔ npm (جدول، نمودار، تقویم و …) | `ClientApp/package.json` با نسخهٔ دقیق + `package-lock.json` | Vite آن را داخل بستهٔ ساخته‌شدهٔ `Server/wwwroot/app` قرار می‌دهد |
   | فونت | `Server/wwwroot/fonts/` (مثل Vazirmatn) | فایل محلی و `@font-face` محلی |
   | آیکون | `lucide-react` (بسته‌بندی‌شده) یا SVG محلی | URL بیرونی ممنوع |
   | تصویر و ایلاستریشن | فایل محلی و بهینه (SVG یا WebP) | مجوز و منبع ثبت شود |
   | دارایی صفحات Razor | `Server/wwwroot/lib/` (LibMan) | فایل‌های واقعی در مخزن؛ تغییر فقط `libman.json` کافی نیست |

4. برای هر دارایی یا کتابخانهٔ جدید، نام، نسخهٔ دقیق، مجوز و منبع اصلی در توضیح PR و در صورت ماندگار بودن در همین سند ثبت می‌شود.
5. راستی‌آزمایی: `npm run check:offline`، `python3 scripts/check_static_assets.py` و بررسی تب Network مرورگر (بدون هیچ درخواست خارجی). نتیجهٔ واقعی گزارش می‌شود؛ اجرا نشده «اجرا نشد» ثبت می‌شود.
6. **محدودیت‌های صادقانه:**
   - `check:offline` یک اسکن ایستا روی خروجی build است؛ آدرسی که در زمان اجرا ساخته شود را نمی‌بیند (جزئیات در `docs/TESTING.md`). قبولی آن شاهد است، نه تضمین.
   - `Server/wwwroot/app` خروجی build است و در Git نگهداری نمی‌شود. قطع اینترنت اجرای نسخهٔ build/publish‌شده را مختل نمی‌کند، ولی ساخت تازه با `npm ci` به رجیستری npm یا یک کش/آینهٔ محلی نیاز دارد. ساخت کاملاً آفلاین (آینهٔ npm یا ذخیرهٔ tarballها) هنوز تصمیم نشده است: `NeedsApproval` / `NotImplemented`.

## کامپوننت‌های مشترک مدیریتی و روتر درون‌پروژه‌ای (Issue #461)

- کامپوننت‌های `ClientApp/src/components/ui/` که سورس‌محور، RTL و بدون وابستگی جدید هستند: `FormField` (همراه `Input`، `Select`، `Textarea`)، `FormSection`، `ConfirmDialog` (محدودسازی focus، Escape، بازگشت focus، جلوگیری از ارسال دوباره)، `Tabs` (WAI-ARIA، جهت فلش‌ها در RTL)، `StatusBadge` (آیکون و متن؛ بر پایهٔ `Badge`)، `DataTable` (نمایشی و سرور-محور: مرتب‌سازی، اسکلت بارگذاری، حالت خالی/خطا، صفحه‌بندی) و `Breadcrumb`. حالت‌های بارگذاری، خالی و خطا از `Feedback.tsx` استفاده می‌کنند.
- تاریخ‌ها فقط با `src/lib/format.ts` (`formatDate`/`formatDateTime`، روی `lib/date.ts`) نمایش داده می‌شوند.
- روتر: `src/lib/router.tsx` یک روتر کوچک مبتنی بر History API زیر `/app/` است (`RouterProvider`، `Link`، `useNavigate`، `useLocation`، `useParams`، مسیرهای lazy). دلیل: جلوگیری از افزودن وابستگی بدون ADR و تأیید مالک (D-011). اگر نیازها رشد کرد (layout تو در تو، loader، حالت جست‌وجو در URL) این تصمیم بازبینی شود.
- `src/lib/permissions.ts` فقط تلمیح UI است و مرجع تصمیم سرور است (D-064)؛ با وجود `GET /me/permissions` به فهرست سرور تغییر می‌کند.

### مسیریابی و صفحات مدیریت کاربران (Issue #462)

- `RouterProvider` در `AppShell` قرار دارد و مسیرهای `/app/admin/users` و `/app/admin/users/:id` از `AppRoutes.tsx` به‌صورت lazy بارگذاری می‌شوند؛ دسترسی مسیر با `can(session, 'admin.users.view')` فقط راهنمای UI است و سرور مرجع نهایی است (D-064).
- `useSearchParams` در `lib/router.tsx`: وضعیت فهرست (`q`, `status`, `sort`, `dir`, `page`, `pageSize`) در URL نگه داشته می‌شود؛ مقادیر پیش‌فرض حذف و مقادیر نامعتبر به پیش‌فرض برمی‌گردند. جست‌وجو (debounce) با replace و سایر تغییرها با push ثبت می‌شوند.
- پس از تغییر مسیر، Focus به `h1` صفحه منتقل می‌شود؛ `useDocumentTitle` عنوان تب را برای صفحات دارای داده پویا تنظیم می‌کند.
- `scripts/offline-check.mjs` اکنون chunkهای lazy را درست resolve می‌کند (آزمون رگرسیون دارد).

### Workspace چندتب (Issue #444، مرحله ۱ — PR 4)

### قرارداد چرخهٔ عمر تب (برای همهٔ فرم‌ها و زیرسیستم‌ها)

هر تب کاری دقیقاً یکی از چهار وضعیت را دارد:

| وضعیت | معنی |
|---|---|
| `Clean` | بدون تغییر ذخیره‌نشده |
| `Dirty` | داده‌های فرم نسبت به آخرین حالت ذخیره‌شدهٔ سرور تغییر واقعی کرده‌اند |
| `Saving` | عملیات ذخیره در حال اجراست |
| `Error` | ذخیره ناموفق بوده یا وضعیت ذخیره نامشخص است (از جمله قطع ارتباط یا پاسخ نامعتبر) |

انتقال‌های مجاز و قواعد (الزامی):

1. `Clean → Dirty` فقط با **تغییر واقعی داده‌های فرم** نسبت به مقدار پایهٔ نرمال‌شده؛ صرف باز شدن فرم، فوکوس یا کلیک کاربر تغییر وضعیت نمی‌دهد. بازگرداندن مقدارها به حالت اول دوباره `Clean` می‌کند.
2. `Dirty → Saving` با شروع ذخیره. در `Saving` بستن تب، تغییر زمینه و ارسال دوباره (double submit) **ممنوع** است.
3. `Saving → Clean` **فقط پس از تأیید موفق سرور** (پاسخ موفق همان درخواست). تا آن زمان خوش‌بینانه Clean نشود.
4. `Saving → Error` هنگام شکست، timeout یا قطع ارتباط. **ذخیرهٔ ناموفق وضعیت Dirty را پاک نمی‌کند**؛ داده‌های فرم از دست نمی‌رود و کاربر می‌تواند دوباره تلاش یا لغو کند. وضعیت نامشخص ذخیره (مثلاً قطع ارتباط پس از ارسال) `Error` است، نه `Clean`.
5. `Error → Saving` با تلاش مجدد؛ `Error|Dirty → Clean` با «لغو تغییرات» (بازگشت به مقدار پایه) یا ذخیرهٔ موفق.
6. فرم **مشاهده‌ای** (بدون ورودی قابل ویرایش) و فرم ذخیره‌شده (`Clean`) بدون هشدار بسته می‌شود.
7. فرم جدید یا ویرایش‌شده تا تعیین تکلیف (`Dirty`/`Error`) بدون هشدار بسته نمی‌شود؛ `Saving` اصلاً بسته نمی‌شود.
