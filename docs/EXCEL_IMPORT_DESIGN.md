## ۱. مسئله و اهداف

کاربران برای شروع کار (اشخاص، کالاها، و در آینده اطلاعات پرونده‌ها و اسناد) از فایل‌های Excel با ساختار آزاد و ستون‌های متفاوت استفاده می‌کنند. ثبت مستقیم این داده‌ها بدون ساختار میانی سه خطر دارد: ثبت ناقص یا مبهم، از دست رفتن شناسه‌های متنی (صفر ابتدایی، ارقام بلند)، و ورود داده به شرکت یا مرز اشتباه.

**اهداف (برگرفته از ۱۵ توافق مالک؛ بند ۱ ADR D-106):**
- یک Canonical Schema داخلی استاندارد؛ تطبیق Sheet/ستون‌های فایل با فیلدهای آن؛ پیشنهاد Mapping بر اساس نام ستون؛ اصلاح Mapping توسط کاربر پیش از تأیید؛ نگهداری Mapping تأییدشده برای استفادهٔ مجدد؛ تشخیص تغییر ساختار فایل.
- اعتبارسنجی کامل پیش از ثبت، Preview با علت خطا، منع ثبت ناقص/مبهم، حفظ شناسه‌های متنی، خطا با شمارهٔ ردیف و نام فیلد.
- موتوری که به Party/Product محدود نباشد و زیرسیستم‌های مختلف بتوانند از آن استفاده کنند.

## ۲. دامنه و خارج از دامنه

**در دامنهٔ این طراحی:** مفهوم و قرارداد موتور خنثی، الگوریتم پیشنهاد Mapping، اعتبارسنجی، Preview، سیاست امنیت فایل، سیاست ثبت، تعارض‌ها و تصمیم‌های باز، مراحل و PRهای آینده.

**خارج از دامنه (این PR و این سند):** هر کد؛ افزودن Package؛ Entity/جدول/Migration/Tenant Entity؛ API و UI؛ Sidebar؛ Excel پروندهٔ واردات (شاخهٔ جدا پس از تثبیت S3-2..S3-4)؛ خروجی Excel (گزارش خطا) به‌جز اشاره به ریسک Formula Injection؛ فرمت‌های `.xls`/`.xlsm`/`.csv` در نسخهٔ اول؛ مهاجرت داده تاریخی؛ هرگونه ادعای عدد مالی تجمیعی (AGENTS.md بخش ۵.۳).

## ۳. واژگان

| واژه | معنی |
|---|---|
| Target Schema | تعریف فیلدهای مقصد که **مصرف‌کننده** (مثلاً زیرسیستم طرف‌حساب) می‌دهد؛ شامل کلید فیلد، نوع، اجباری/اختیاری، Alias، علامت «شناسه متنی»، اعتبارسنج‌ها (EXC-3) |
| Canonical Schema | مجموعهٔ استاندارد داخلی فیلدهای مقصد که فایل به آن نگاشت می‌شود؛ در این طراحی هر Target Schema مصرف‌کننده، یک نمونه از آن است (توافق ۱) |
| Parser | مؤلفه‌ای که فایل را می‌خواند و سلول‌ها را به مدل ساده تبدیل می‌کند؛ جدا از موتور (EXC-4) |
| موتور (Engine) | مؤلفهٔ خالص پیشنهاد Mapping، اعتبارسنجی، تشخیص تکراری و ساخت نتیجهٔ Preview؛ بدون ثبت (EXC-1) |
| Mapping | نگاشت «ستون/Sheet فایل ← فیلد Canonical» |
| اثر انگشت سرستون | امضای نرمال‌شدهٔ فهرست عنوان ستون‌های یک Sheet برای تشخیص تغییر ساختار |
| شناسه متنی | فیلدی مانند HS Code، GTIN، IRC که باید رشته بماند و صفر ابتدایی آن حفظ شود |
| مصرف‌کننده (Consumer) | زیرسیستمی که Target Schema می‌دهد و نتیجهٔ موتور را ثبت می‌کند |
| Preview | نتیجهٔ پردازش بدون ثبت: ردیف‌های معتبر/نامعتبر/هشدار و شمارش‌ها (EXC-11) |
| Commit | ثبت نهایی توسط مصرف‌کننده پس از تأیید صریح کاربر (EXC-12) |

## ۴. جریان کامل Import (از انتخاب فایل تا ثبت نهایی)

وضعیت: `Proposed`؛ مراحل ۱ تا ۱۱ مفهومی‌اند و شکل API/UI در EXC-15 `Deferred` است.

1. **انتخاب فایل و مصرف‌کننده/Template.** کاربر در فرم مصرف‌کننده فایل را انتخاب می‌کند. Company از Context سرور تعیین می‌شود، نه از فایل (D-103 بند ۹، D-105 بند ۸).
2. **بررسی امنیتی فایل** پیش از هر Parse (بخش ۱۲، EXC-13): پسوند/نوع، اندازه، zip-bomb، لینک خارجی، ماکرو.
3. **Parse جریانی** سرستون‌ها و ردیف‌ها به مدل سلول (EXC-4)؛ فرمول اجرا نمی‌شود (EXC-6).
4. **جست‌وجوی Mapping ذخیره‌شده** با کلید جست‌وجوی EXC-8 (دامنهٔ سرور + Target Schema و نسخه + امضای Template/Sheet). **تا رفع مسدودی EXC-8 این گام و گام‌های ۵ و ۱۲ وجود ندارند** و هر Import از گام ۶ (پیشنهاد Mapping) شروع می‌شود.
5. **تشخیص تغییر ساختار** (EXC-9) پس از پیدا شدن Mapping: اثر انگشت سرستون‌های ذخیره‌شده با فایل جدید مقایسه می‌شود (بدون تغییر / فقط جابه‌جایی / تغییر مؤثر). این گام به Mapping ذخیره‌شده وابسته است، پس تا رفع مسدودی EXC-8 اجرا نمی‌شود.
6. **پیشنهاد Mapping** (EXC-7) برای ستون‌های نگاشت‌نشده یا Mapping تغییرکرده.
7. **اصلاح و تأیید Mapping توسط کاربر** (ترجیحاً Combobox مشترک؛ D-082). تغییر مؤثر ⇒ تأیید مجدد الزامی است.
8. **اعتبارسنجی** (EXC-10): نوع/قالب، اجباری، فرم، قواعد تجاری، محدودهٔ شرکت، تکراری.
9. **Preview** (EXC-11) و گزارش خطا (بخش ۱۱).
10. **تأیید صریح کاربر** بر Preview بدون خطای مسدودکننده.
11. **Commit** توسط مصرف‌کننده: تراکنش اتمی، Idempotent، همه‌یاهیچ (EXC-12).
12. **ثبت Mapping تأییدشده** برای استفادهٔ مجدد (EXC-8؛ **Blocked**: هیچ محل ذخیرهٔ ماندگاری پیشنهاد یا مجاز نیست).

موتور فقط گام‌های ۶ تا ۹ را انجام می‌دهد؛ گام ۵ (Mapping ذخیره‌شده) پس از رفع مسدودی EXC-8 به آن افزوده می‌شود. گام ۱۱ مسئولیت مصرف‌کننده است و موتور هیچ ثبتی ندارد. Commit فقط با شناسهٔ Preview مقید انجام می‌شود، نه ردیف‌های ارسالی کلاینت (بخش ۱۵).

## ۵. Canonical Schema

**EXC-3 (`Proposed`)** — Target Schema را مصرف‌کننده تعریف می‌کند و موتور آن را فقط می‌خواند. هر فیلد:

| ویژگی | توضیح |
|---|---|
| کلید فیلد | شناسهٔ ثابت و پایدار (انگلیسی)، مبنای Mapping ذخیره‌شده؛ نام نمایشی فارسی جدا نگهداری می‌شود (Alias فقط در ردیف Alias است و در این ردیف تکرار نمی‌شود) |
| نوع | متن، عدد صحیح، اعشاری/مبلغ، تاریخ، بولی، فهرست/Enum |
| اجباری/اختیاری | اجباری‌بودن فقط در Target Schema؛ نه در فایل |
| Alias | فهرست عنوان‌های متداول فارسی/انگلیسی برای پیشنهاد Mapping |
| علامت «شناسه متنی» | یعنی هرگز عدد نمی‌شود؛ صفرهای ابتدایی حفظ می‌شود (توافق ۱۳؛ EXC-5) |
| پرچم طول ثابت/رقم کنترل (پیشنهاد، NeedsApproval) | اگر برای فیلد شناسه طول ثابت یا رقم کنترل تعریف شده باشد، موتور می‌تواند تشخیص دهد صفر ابتدایی از دست رفته است (بخش ۹، پرسش مالک ۱) |
| اعتبارسنج‌ها | قواعد قالب (طول، الگو، رقم کنترل) و قواعد تجاری مستقل از DB |
| نسخه | شناسه و نسخهٔ Target Schema؛ تغییر ناسازگار ⇒ نسخهٔ جدید (بخش ۷) |

**مثال ساختگی (فقط برای توضیح):** فیلد `commodityCode` از نوع «شناسه متنی»، اجباری، Alias: «کد کالا»، «Commodity Code»، «HS»؛ فیلد `unitPrice` عددی اختیاری با Alias «قیمت واحد»، «Unit Price».

**مرز:** Target Schema شامل TenantId/CompanyId نیست؛ این دو هرگز فیلد مقصد Import نمی‌شوند (D-103 بند ۹).

## ۶. الگوریتم پیشنهاد Mapping

**EXC-7 (`Proposed`)** — قطعی، بدون ML/شبکه، قابل تست با ورودی ثابت.

1. **نرمال‌سازی عنوان ستون:** تبدیل `ي/ك` عربی به `ی/ک` فارسی؛ ارقام فارسی و عربی-هندی به لاتین (فقط برای مقایسهٔ عنوان، نه مقدار سلول؛ EXC-16)؛ حذف فاصله‌های اضافه و ZWNJ/ZWJ در مقایسه؛ حروف کوچک؛ حذف علائم نگارشی ابتدا/انتها.
2. **ترتیب تطبیق:** (الف) تطبیق دقیق با نام/Alias نرمال‌شده؛ (ب) Alias؛ (پ) شباهت با آستانه (مثلاً فاصلهٔ ویرایشی نسبت‌به‌طول). **آستانه مقدار پیشنهادی برای تعیین است**، نه قطعی.
3. **ابهام:** اگر یک ستون با چند فیلد، یا چند ستون با یک فیلد منطبق شد ⇒ «نگاشت‌نشده» برای انتخاب کاربر؛ هیچ انتخاب خودکار در ابهام وجود ندارد (توافق ۱۲).
4. **ستون ناشناخته** (بی‌تطبیق) و **ستون تکراری** (دو سرستون هم‌نام پس از نرمال‌سازی) در نتیجه گزارش می‌شوند.
5. **خروجی:** فهرست پیشنهادها با دلیل و رتبهٔ اطمینان (دقیق/Alias/شباهت) تا UI بتواند در Combobox نشان دهد؛ پیشنهاد، تأیید نیست.
6. **Sheet:** اگر فایل چند Sheet دارد، نگاشت Sheet→Target مستقل است؛ نام Sheet نیز نرمال‌سازی می‌شود. نسخه‌های ناهمسان یک Sheet «منبع مستقل» هستند و یکی جایگزین دیگری نمی‌شود (V3.2 §12).

## ۷. ساختار Mapping و Versioning

**EXC-8 (`NeedsApproval`؛ ذخیره‌سازی `Blocked` تا S3)** — کلید جست‌وجوی پیشنهادی Mapping فقط این سه جزء است:

`(دامنهٔ Company از سرور، شناسه + نسخهٔ Target Schema، امضای Template/Sheet)`

**اثر انگشت سرستون‌ها جزء کلید نیست.** آن یک ویژگی ذخیره‌شدهٔ همان Mapping است و پس از پیدا شدن Mapping با فایل جدید مقایسه می‌شود (EXC-9). اگر اثر انگشت جزء کلید بود، هر تغییر ساختار به «Mapping پیدا نشد» می‌انجامید و ردهٔ «جابه‌جایی/تغییر مؤثر» هرگز رخ نمی‌داد.

- توافق ۶ می‌گوید Mapping به Company و Sheet و Template/Version مربوط است؛ **جزئیات کلیدگذاری هنوز تصمیم‌نشده است** (بخش ۲۰).
- **مالکیت:** طبق D-105 بند ۱ پیش‌فرض Company-owned است؛ اشتراک Mapping بین Companyهای یک Tenant تصمیم مستقل لازم دارد (D-105 بند ۳). موتور مالکیت فرض نمی‌کند.
- **هیچ ذخیرهٔ ماندگاری وجود ندارد (تا رفع مسدودی EXC-8):** نه جدول (نه در جداول مصرف‌کننده و نه در schema `trade`)، نه `localStorage`/`sessionStorage`، نه فایل. این طراحی هیچ محل ذخیره‌ای پیشنهاد نمی‌کند. شرط رفع مسدودی: تعیین مالکیت (D-105) و بسته‌شدن گیت‌های S3-0 (`TRADE_S3_READINESS.md` خط 50 برای جدول Trade؛ گیت عام: AGENTS.md بخش ۵.۳).
- **پیامد:** هر Import از مرحلهٔ پیشنهاد Mapping (گام ۶ بخش ۴) شروع می‌شود. تا رفع مسدودی، توافق‌های ۵ (نگهداری Mapping)، ۷ (استفادهٔ مجدد خودکار)، ۸ (تشخیص تغییر ساختار) و ۹ (اعتبارسنجی/تأیید مجدد Mapping) اجرا **نمی‌شوند**؛ **EXC-9 در عمل به EXC-8 وابسته است.**
- موتور Mapping را فقط به‌عنوان ورودی همان فراخوانی می‌پذیرد (برای تست و قرارداد خالص)؛ نگه‌داری آن بر عهدهٔ موتور نیست و این سند محل نگه‌داری تعیین نمی‌کند.
- **نسخه‌گذاری (طراحی آینده):** هر Mapping نسخهٔ Target Schema را نگه می‌دارد؛ تغییر نسخه، Mapping قبلی را «نیازمند اعتبارسنجی مجدد» می‌کند؛ نسخهٔ جدید به‌جای بازنویسی ساخته می‌شود.

**پرسش‌های باز دربارهٔ EXC-8 (فقط پرسش؛ پاسخ حدس زده نشده است):**
1. آیا رکورد Mapping طبق D-105 بند ۱ هر دو شناسهٔ TenantId و CompanyId معتبر را دارد (Company-owned)، یا طبق بندهای ۳ و ۴ اشتراک‌پذیر است؟
2. Mapping «دادهٔ کسب‌وکاری مشتری» است یا «پیکربندی فنی/زیرساختی» که طبق D-105 بند ۷ جداگانه طبقه‌بندی می‌شود؟
3. موتور خنثی کدام DbContext/schema را دارد؟ نکتهٔ مرزی: `docs/DECISIONS.md` خطوط 996 و 1068 هیچ FK از schema `trade` به جداول تراکنشی حسابداری را مجاز نمی‌دانند؛ و D-090 هنوز `Proposed` است.
## ۸. تشخیص تغییر ساختار

**EXC-9 (`Proposed`؛ وابسته به EXC-8 و تا رفع مسدودی آن اجرا نمی‌شود)** — پس از پیدا شدن Mapping با کلید EXC-8 (که شامل اثر انگشت نیست)، «اثر انگشت سرستون‌های» ذخیره‌شده با فایل جدید مقایسه می‌شود:

| رده | شرط | رفتار |
|---|---|---|
| بدون تغییر | همان سرستون‌ها به همان ترتیب | Mapping پیشین خودکار پیشنهاد/اعمال می‌شود؛ اعتبارسنجی عادی |
| فقط جابه‌جایی ستون | مجموعهٔ عنوان‌ها یکی، ترتیب متفاوت، همهٔ عنوان‌ها منطبق | نگاشت خودکار بر مبنای عنوان؛ در Preview اعلام می‌شود |
| تغییر مؤثر | ستون افزوده/حذف/تغییرنام یا هر ابهام | Mapping دوباره اعتبارسنجی؛ **تأیید مجدد کاربر الزامی** (توافق ۹) |

نکته: تغییر «فقط ترتیب» تنها وقتی خودکار پذیرفته می‌شود که نگاشت بر عنوان استوار باشد، نه شمارهٔ ستون؛ در غیر این صورت رده «تغییر مؤثر» است. بدون Mapping ذخیره‌شده (وضعیت فعلی مسدودی) مقایسه‌ای وجود ندارد و هر Import به‌عنوان «اولین Import» رفتار می‌کند.
## ۹. اعتبارسنجی

**EXC-10 (`Proposed`)** — لایه‌ها به ترتیب؛ همه پیش از هر ثبت و بدون توقف در اولین خطا (چندخطایی در یک ردیف):

1. نوع/قالب (عدد، تاریخ، طول، الگو، Enum).
2. فیلدهای اجباری.
3. فرم (ساختار ردیف، ستون‌های لازم نگاشت‌شده).
4. قواعد تجاری مستقل از DB (مثلاً رقم کنترل، رابطهٔ بین فیلدها) که مصرف‌کننده تعریف می‌کند.
5. **محدودهٔ شرکت:** Company از Context سرور به موتور داده می‌شود؛ هیچ مقدار Tenant/Company از فایل خوانده یا پذیرفته نمی‌شود (Accepted: D-103 بند ۹، D-105 بند ۸).
6. تکراری داخل فایل (موتور) و تکراری نسبت به DB از طریق **پورت** که لایهٔ بالاتر پیاده می‌کند (موتور به DB دسترسی ندارد).

**EXC-5 (`NeedsApproval`) — سیاست سلول → مقدار برای شناسه‌ها:**
- سلول متنی: همان‌طور حفظ شود (شاهد Spike: «00123» در هر سه کتابخانه حفظ شد).
- **سلول عددی صفرپر:** فقط **عدد صحیح نامنفی** با رشتهٔ فرمتی که دقیقاً الگوی `0` تکرارشونده است (Allowlist دقیق، مثل `00000`)؛ طول متن خروجی = طول ماسک. هر مورد دیگر (از جمله فرمت‌های دیگر، مقدار اعشاری، منفی) ⇒ خطای `numeric_identifier_cell`. مثال: مقدار 123.5 با فرمت `00000` نباید «00124» شود؛ رد می‌شود.
- **ارقام:** اگر «تعداد کل ارقام بخش صحیح» بیش از ۱۵ باشد ⇒ رد (نه «ارقام معنادار»). عدد ۱۶رقمی و بلندتر فقط از **سلول متنی** معتبر است؛ ذخیرهٔ `double` در خود Excel دقت را از بین می‌برد (شاهد Spike: عدد ۱۹رقمی در فایل دقت از دست داده بود).
- **پرسش مالک ۱ (پرچم طول ثابت/رقم کنترل):** آیا هر فیلد شناسه در Target Schema بتواند پرچم «طول ثابت/رقم کنترل» داشته باشد؟ اگر داشت، عدد صحیح ≤۱۵ رقم پذیرفته و طول/رقم کنترل بررسی می‌شود تا صفر ابتدایی ازدست‌رفته (مثلاً HS هشت‌رقمی که هفت‌رقمی خوانده شده) تشخیص داده شود. تا پاسخ، این بررسی انجام نمی‌شود.
- **پرسش مالک ۲ (ارقام فارسی/عربی در شناسه و کلید طبیعی):** آیا نگاشت ارقام فارسی/عربی-هندی به لاتین در شناسه/کلید طبیعی «تبدیل مخرب» است؟ توضیح: بدون این نگاشت، «۰۰۱۲۳» و «00123» دو کلید متفاوت می‌شوند و Idempotency/تشخیص تکراری دور زده می‌شود؛ با نگاشت، مقدار ذخیره‌شده تغییر می‌کند. تا تصمیم، شناسه‌ها بدون تبدیل می‌مانند و ورود با ارقام غیرلاتین در ستون شناسه هشدار/خطای صریح می‌گیرد (پیشنهاد).
- هیچ قاعدهٔ دیگری برای ساخت مقدار شناسه از سلول عددی حدس زده نمی‌شود.

**مبلغ/اعشار (`Proposed`، NeedsApproval برای جزئیات):** مقدار از متن خام سلول با فرهنگ Invariant مستقیم به `decimal` تبدیل شود؛ هرگز `double→decimal`؛ اگر از scale/precision مقصد بیشتر باشد ⇒ رد، نه گرد‌کردن. (دقت اعشار در `TRADE_S3_READINESS.md` بخش ۴ هنوز تصمیم‌نشده است.)

**تاریخ و پنهان‌ها (`Proposed`):** قرارداد Parser باید `date1904` را بخواند و در نتیجه برگرداند (تبدیل سریال بدون آن خطای ۴ ساله می‌دهد). Sheet/ردیف/ستون پنهان در Preview هشدار/گزینهٔ صریح دارند و بی‌صدا حذف یا ورود نمی‌شوند.

**EXC-6 (`Proposed`)** — فرمول هرگز اجرا نمی‌شود؛ فقط مقدار cached خوانده می‌شود. فرمول بدون مقدار cached یا با خطا (`#REF!`، `#VALUE!` و ...) ردیف را با خطای صریح رد می‌کند (هم‌جهت `TRADE_DESIGN_V3_2.md` §12). برای **هر سلول فرمول‌دار** حتی با مقدار cached معتبر هشدار ثبت می‌شود: مقدار cached ممکن است از یک لینک خارجی نادیده‌گرفته‌شده بیاید و کهنه باشد. شکاف: ExcelDataReader فرمول بدون مقدار را با «خالی» یکی می‌کند (شاهد Spike) و برای EXC-6 ناکافی است.

**EXC-16 (`Proposed`)** — نرمال‌سازی ارقام فارسی/عربی-هندی و تاریخ شمسی/میلادی در یک لایهٔ مستقل (هم‌جهت V3.2 §12) فقط برای فیلدهای نوع عدد/تاریخ؛ اعمال آن بر شناسه/کلید طبیعی منوط به پاسخ پرسش مالک ۲ در EXC-5 است.

## ۱۰. تشخیص تکراری

- **داخل فایل:** بر اساس «کلید طبیعی» که Target Schema مشخص می‌کند (پس از نرمال‌سازی)؛ تکرار ⇒ خطا یا هشدار طبق تعریف مصرف‌کننده، هرگز حذف/ادغام بی‌صدا.
- **نسبت به DB:** از طریق پورت لایهٔ بالاتر، فقط در محدودهٔ Company/Tenant سرور؛ نتیجه «موجود/ناموجود/مبهم». ادغام خودکار رکوردهای مشابه بر اساس نام/کد/شباهت ممنوع است (D-105 بند ۹).
- **Idempotency ثبت:** «رکورد یکسان موجود ⇒ رد/خطا»، نه Upsert (D-105 بند ۹). دامنهٔ کلید طبیعی (Company یا Tenant) به تصمیم مالکیت D-105 بندهای ۳ و ۴ وابسته است. جزئیات در EXC-12 (بخش ۱۵).

**گره‌خوردن Preview به Commit (بخش ۱۲):** Commit هرگز ردیف را از کلاینت نمی‌پذیرد. Preview به این موارد گره می‌خورد: UserId، Company، Tenant (از Context سرور)، نسخهٔ Target Schema، hash فایل، hash Mapping. در Commit دوباره بررسی می‌شود: Company Context فعلی = Company زمان Preview (با hash)، مجوز، Entitlement و اعتبارسنجی کامل؛ hash فایل **سمت سرور** محاسبه می‌شود و hash ارسالی کلاینت پذیرفته نمی‌شود. هر عدم‌تطابق ⇒ رد با پاسخ یکسان (جلوگیری از جابه‌جایی Company بین Preview و Commit و TOCTOU). تا رفع مسدودی ذخیره‌سازی، تنها سد تکرار Commit همان Idempotency با قید یکتای دیتابیس است (مجوز جدا)؛ سازوکار تک‌مصرف‌بودن `NeedsApproval` است. **تک‌مصرف‌بودن و انقضای شناسهٔ Preview** state ماندگار سمت سرور می‌خواهد و تابع مسدودی ذخیره‌سازی است (بخش ۱۵، مورد ۳).

**پیش‌شرط «تکراری نسبت به DB»:** مجوز view موجودیت مقصد (الگوی D-084 بند ۲)، فقط در Company سرور و پشت Rate Limit؛ در غیر این صورت پورت تکراری می‌تواند وجود رکورد را نشت دهد.

## ۱۴. فایل‌های بزرگ و حافظه

- Parser جریانی است؛ موتور ردیف‌ها را به‌صورت دسته‌ای/جریانی می‌پذیرد و کل فایل را به‌صورت شیء در حافظه نگه نمی‌دارد، جز ساختارهای لازم (مجموعهٔ کلیدهای تکراری، شمارش خطاها).
- **سقف تعداد خطای ذخیره‌شده** در Preview (بیش از آن «و N خطای دیگر») تا حافظه کران‌دار بماند؛ مقدار تعیین‌نشده.
- **شاهد Spike (گزارش Lead؛ artifact قابل بازتولید در پیوست سند مقایسه):** Peak Working Set **کل فرایند** (شامل پایهٔ runtime حدود 47-57MB در فایل کوچک) و تولید فایل در فرایند جدا؛ فایل ساختگی ۲۰۰٬۰۰۰ ردیف × ۸ ستون، ۸٫۹ MB؛ ۱ اجرا، ۲ هسته، .NET 10.0.403؛ تقریبی و تک‌اجرایی، نه Benchmark. ExcelDataReader حدود ۲۹۴MB/۲٫۲s؛ Open XML SDK (`OpenXmlReader`) حدود ۳۰۲MB/۲٫۵s؛ ClosedXML (DOM) حدود ۵۹۰MB/۷٫۶s. **«جریانی = حافظهٔ کم» تأیید نشده است:** جدول shared strings و styles در Open XML SDK و ExcelDataReader در حافظه بار می‌شوند و باید بودجهٔ حافظه (EXC-13) برایشان سقف بگذارد. پیش از قطعی‌شدن EXC-17 Spike باید دوباره اجرا شود.
- تقسیم دستهٔ بزرگ هنگام Commit `Deferred` است (EXC-12).

## ۱۵. مدیریت خطا و جلوگیری از ثبت ناقص

**EXC-12 (`NeedsApproval`)** — سیاست ثبت: همه‌یاهیچ؛ فقط پس از تأیید صریح کاربر روی Preview بدون خطای مسدودکننده؛ تراکنش اتمی؛ Idempotency با کلید طبیعی؛ **ثبت جزئی (فقط ردیف‌های معتبر) ممنوع مگر مالک صریحاً تصویب کند**. شکست میانه ⇒ Rollback کامل (V3.2 §12). تقسیم دسته‌های بزرگ `Deferred`.

> **تفسیر Lead — نیازمند تأیید:** «همه‌یاهیچ در سطح کل دسته (فایل)» تفسیر Lead از توافق ۱۲ است، نه عین متن مالک؛ ممکن است مالک فقط سطح ردیف را مراد کرده باشد (ممنوعیت ثبت ردیف ناقص/مبهم).

**تکمیل‌های پیشنهادی (`Proposed`، NeedsApproval):**
1. **Commit دوباره کامل اعتبارسنجی می‌کند** (از جمله تکراری) داخل همان تراکنش؛ به نتیجهٔ Preview اعتماد نمی‌شود.
2. **گره‌خوردن Preview به Commit:** UserId، Company، Tenant (از Context سرور)، نسخهٔ Target Schema، hash فایل، hash Mapping (جزئیات امنیتی: بخش ۱۲، «گره‌خوردن Preview به Commit»).
3. **انتقال Preview→Commit** فقط دو راه دارد: (الف) آپلود دوبارهٔ فایل با تطبیق hash؛ (ب) فایل/نتیجهٔ موقت سمت سرور مقید به کاربر/Company؛ گزینهٔ (ب) state ماندگار سمت سرور است و **تا رفع مسدودی ذخیره‌سازی ممنوع است**؛ هیچ محلی برایش پیشنهاد نمی‌شود. **پیامد صریح:** با گزینهٔ (الف) نه «تک‌مصرف‌بودن شناسهٔ Preview» و نه «Idempotency سطح Import بین درخواست‌ها» قابل اجراست (هر دو state ماندگار می‌خواهند) و هر دو **Blocked**اند؛ اجرای آن‌ها فقط با یک استثنای جدا و NeedsApproval برای state موقت سمت سرور ممکن است. **در مدل بدون state دفاع در عمق:** اعتبارسنجی کامل دوباره در Commit + قید/بررسی یکتایی (پیشنهاد؛ مجوز جدا) + Company Context فعلی = Company زمان Preview با hash.
4. **سقف ردیف (EXC-13) عملاً مرز اتمی‌بودن است:** تراکنش بزرگ روی SQL Server خطر lock escalation، رشد log و Timeout دارد؛ تا وقتی «تقسیم دسته» Deferred است، سقف باید به آن آگاه تعیین شود.
5. **خطر تراکنش تودرتو:** اگر UseCaseهای موجود مصرف‌کننده خودشان `SaveChanges`/تراکنش داشته باشند، تراکنش اتمی بیرونی با آن‌ها تداخل می‌کند؛ باید پیش از پیاده‌سازی با شواهد کد بررسی شود (این گذر بررسی نکرد).
6. **Idempotency:** «رکورد یکسان موجود ⇒ رد/خطا»، نه Upsert (D-105 بند ۹). «کلید Idempotency سطح Import (شناسهٔ Preview)» وابسته به state ماندگار و **Blocked** است (مورد ۳)؛ در مدل بدون state حفاظت بین‌درخواستی فقط **قید یکتای دیتابیس به‌ازای دامنهٔ کلید طبیعی (Company یا Tenant، طبق D-105 بندهای ۳ و ۴؛ پیشنهاد، تغییر Schema، مجوز جدا)** است، همراه پورت.
7. **وابستگی Product:** Commit برای Product به D-085 وابسته است که تصمیمش `Proposed + NeedsApproval` است در حالی که پیاده‌سازی آن در `main` با PR #644 ادغام شده (طبق متن D-085).

- خطای Parse/امنیتی ⇒ توقف قبل از هر پردازش؛ پیام قابل‌فهم بدون افشای جزئیات داخلی.
- Exception بی‌صدا بلعیده نمی‌شود؛ `ILogger<T>` بدون محتوای سلول.
- لغو (Cancellation) در هر مرحلهٔ پیش از Commit بدون اثر جانبی.
- ابهام در Mapping یا نتیجهٔ اعتبارسنجی ⇒ هرگز ثبت.
