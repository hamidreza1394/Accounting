## ۱. مسئله و اهداف

کاربران برای شروع کار (اشخاص، کالاها، و در آینده اطلاعات پرونده‌ها و اسناد) از فایل‌های Excel با ساختار آزاد و ستون‌های متفاوت استفاده می‌کنند. ثبت مستقیم این داده‌ها بدون ساختار میانی سه خطر دارد: ثبت ناقص یا مبهم، از دست رفتن شناسه‌های متنی (صفر ابتدایی، ارقام بلند)، و ورود داده به شرکت یا مرز اشتباه.

**اهداف (برگرفته از ۱۵ توافق مالک؛ بند ۱ ADR D-106):**
- یک Canonical Schema داخلی استاندارد؛ تطبیق Sheet/ستون‌های فایل با فیلدهای آن؛ پیشنهاد Mapping بر اساس نام ستون؛ اصلاح Mapping توسط کاربر پیش از تأیید؛ نگهداری Mapping تأییدشده برای استفادهٔ مجدد؛ تشخیص تغییر ساختار فایل.
- اعتبارسنجی کامل پیش از ثبت، Preview با علت خطا، منع ثبت ناقص/مبهم، حفظ شناسه‌های متنی، خطا با شمارهٔ ردیف و نام فیلد.
- موتوری که به Party/Product محدود نباشد و برای موجودیت‌های مختلف Trade (Proforma، OrderRegistration و …) قابل استفاده باشد؛ کل Excel Import و Mapping متعلق به Trade است و به زیرسیستم مالی ربطی ندارد (EXC-2؛ اصلاح برداشت قبلی در بخش ۱۳).

## ۲. دامنه و خارج از دامنه

**در دامنهٔ این طراحی:** مفهوم و قرارداد موتور، الگوریتم پیشنهاد Mapping، اعتبارسنجی، Preview، سیاست امنیت فایل، سیاست ثبت، تعارض‌ها و تصمیم‌های باز، مراحل و PRهای آینده.

**خارج از دامنه (این PR و این سند):** هر کد؛ افزودن Package؛ Entity/جدول/Migration/Tenant Entity؛ API و UI؛ Sidebar؛ Excel پروندهٔ واردات (شاخهٔ جدا پس از تثبیت S3-2..S3-4)؛ خروجی Excel (گزارش خطا) به‌جز اشاره به ریسک Formula Injection؛ فرمت‌های `.xls`/`.xlsm`/`.csv` در نسخهٔ اول؛ مهاجرت داده تاریخی؛ هرگونه ادعای عدد مالی تجمیعی (AGENTS.md بخش ۵.۳).

## ۳. واژگان

| واژه | معنی |
|---|---|
| Target Schema | تعریف فیلدهای مقصد که **مصرف‌کننده** (مثلاً زیرسیستم طرف‌حساب) می‌دهد؛ شامل کلید فیلد، نوع، اجباری/اختیاری، Alias، علامت «شناسه متنی»، اعتبارسنج‌ها (EXC-3) |
| Canonical Schema | مجموعهٔ استاندارد داخلی فیلدهای مقصد که فایل به آن نگاشت می‌شود؛ در این طراحی هر Target Schema مصرف‌کننده، یک نمونه از آن است (توافق ۱) |
| Parser | مؤلفه‌ای که فایل را می‌خواند و سلول‌ها را به مدل ساده تبدیل می‌کند؛ جدا از موتور (EXC-4) |
| مدل سلول | قرارداد ورودی استاندارد موتور که در `Trade.Application` (پوشهٔ `Import`) تعریف می‌شود و Parser آن را تولید می‌کند: مقدار خام، نوع، رشتهٔ فرمت، وجود فرمول، مقدار cached/خطای cached (EXC-4) |
| موتور (Engine) | مؤلفهٔ خالص پیشنهاد Mapping، اعتبارسنجی، تشخیص تکراری و ساخت نتیجهٔ Preview؛ بدون ثبت (EXC-1) |
| Mapping | نگاشت «ستون/Sheet فایل ← فیلد Canonical» |
| اثر انگشت سرستون | امضای نرمال‌شدهٔ فهرست عنوان ستون‌های یک Sheet برای تشخیص تغییر ساختار |
| شناسه متنی | فیلدی مانند HS Code، GTIN، IRC که باید رشته بماند و صفر ابتدایی آن حفظ شود |
| مصرف‌کننده (Consumer) | Use Case/عملیات Trade (Party، Product، Proforma، OrderRegistration و …) که Target Schema می‌دهد و نتیجهٔ موتور را ثبت می‌کند |
| Preview | نتیجهٔ پردازش بدون ثبت: ردیف‌های معتبر/نامعتبر/هشدار و شمارش‌ها (EXC-11) |
| Commit | ثبت نهایی توسط مصرف‌کننده پس از تأیید صریح کاربر (EXC-12) |

## ۴. جریان کامل Import (از انتخاب فایل تا ثبت نهایی)

وضعیت: `Proposed`؛ مراحل ۱ تا ۱۱ مفهومی‌اند و شکل API/UI در EXC-15 `Deferred` است.

1. **انتخاب فایل و مصرف‌کننده/Template.** کاربر در فرم مصرف‌کننده فایل را انتخاب می‌کند. Company از Context سرور تعیین می‌شود، نه از فایل (D-103 بند ۹، D-105 بند ۸).
2. **بررسی امنیتی فایل** پیش از هر Parse (بخش ۱۲، EXC-13): پسوند/نوع، اندازه، zip-bomb، لینک خارجی، ماکرو.
3. **Parse** سرستون‌ها و ردیف‌ها به مدل سلول (EXC-4؛ Parser مبتنی بر ClosedXML جریانی نیست و کران حافظه فقط از Guard و سقف‌ها می‌آید)؛ فرمول اجرا نمی‌شود (EXC-6).
4. **جست‌وجوی Mapping ذخیره‌شده** با کلید جست‌وجوی EXC-8 (دامنهٔ سرور + Target Schema و نسخه + امضای Template/Sheet). **تا رفع مسدودی EXC-8 این گام و گام‌های ۵ و ۱۲ وجود ندارند** و هر Import از گام ۶ (پیشنهاد Mapping) شروع می‌شود.
5. **تشخیص تغییر ساختار** (EXC-9) پس از پیدا شدن Mapping: اثر انگشت سرستون‌های ذخیره‌شده با فایل جدید مقایسه می‌شود (بدون تغییر / فقط جابه‌جایی / تغییر مؤثر). این گام به Mapping ذخیره‌شده وابسته است، پس تا رفع مسدودی EXC-8 اجرا نمی‌شود.
6. **پیشنهاد Mapping** (EXC-7) برای ستون‌های نگاشت‌نشده یا Mapping تغییرکرده.
7. **اصلاح و تأیید Mapping توسط کاربر** (ترجیحاً Combobox مشترک؛ D-082). تغییر مؤثر ⇒ تأیید مجدد الزامی است.
8. **اعتبارسنجی** (EXC-10): نوع/قالب، اجباری، فرم، قواعد تجاری، محدودهٔ شرکت، تکراری.
9. **Preview** (EXC-11) و گزارش خطا (بخش ۱۱).
10. **تأیید صریح کاربر** بر Preview بدون خطای مسدودکننده.
11. **Commit** توسط Use Case مصرف‌کننده؛ سیاست Commit را همان Use Case تعیین می‌کند (پیشنهاد نسخهٔ اول: All-or-Nothing در سطح دسته، NeedsApproval؛ EXC-12). **تا رفع مسدودی کامل (گیت S3-0 و تصمیم مالکیت D-105، و نیز یکی از دو: state سمت سرور یا تأیید صریح گزینهٔ توکن Data Protection) Commit Blocked است** (بخش ۱۵).
12. **ثبت Mapping تأییدشده** برای استفادهٔ مجدد (EXC-8؛ **Blocked**: هیچ محل ذخیرهٔ ماندگاری پیشنهاد یا مجاز نیست).

موتور فقط گام‌های ۶ تا ۹ را انجام می‌دهد؛ گام ۵ (Mapping ذخیره‌شده) پس از رفع مسدودی EXC-8 به آن افزوده می‌شود. گام ۱۱ مسئولیت مصرف‌کننده است و موتور هیچ ثبتی ندارد. Commit تا رفع مسدودی Blocked است و هرگز ردیف کلاینت را نمی‌پذیرد؛ گزینه‌های آینده (NeedsApproval) در بخش ۱۵ آمده است.

## ۵. Canonical Schema

**EXC-3 (`Proposed`)** — Target Schema را مصرف‌کننده تعریف می‌کند و موتور آن را فقط می‌خواند. هر فیلد:

| ویژگی | توضیح |
|---|---|
| کلید فیلد | شناسهٔ ثابت و پایدار (انگلیسی)، مبنای Mapping ذخیره‌شده؛ نام نمایشی فارسی جدا نگهداری می‌شود (Alias فقط در ردیف Alias است و در این ردیف تکرار نمی‌شود) |
| نوع | متن، عدد صحیح، اعشاری/مبلغ، تاریخ، بولی، فهرست/Enum |
| اجباری/اختیاری | اجباری‌بودن فقط در Target Schema؛ نه در فایل |
| Alias | فهرست عنوان‌های متداول فارسی/انگلیسی برای پیشنهاد Mapping |
| علامت «شناسه متنی» | یعنی هرگز عدد نمی‌شود؛ صفرهای ابتدایی حفظ می‌شود (توافق ۱۳؛ EXC-5) |
| طول ثابت و قالب شناسه (پیشنهاد، NeedsApproval) | فقط اگر Target Schema برای فیلد شناسه طول ثابت و قالب را صریحاً تعریف کند، بازسازی صفر ابتدایی از سلول عددی ممکن است؛ در غیر این صورت عدد ⇒ خطا (بخش ۹، EXC-5) |
| اعتبارسنج‌ها | قواعد قالب (طول، الگو، رقم کنترل) و قواعد تجاری مستقل از DB |
| نسخه | شناسه و نسخهٔ Target Schema؛ تغییر ناسازگار ⇒ نسخهٔ جدید (بخش ۷) |

**مثال ساختگی (فقط برای توضیح):** فیلد `commodityCode` از نوع «شناسه متنی»، اجباری، Alias: «کد کالا»، «Commodity Code»، «HS»؛ فیلد `unitPrice` عددی اختیاری با Alias «قیمت واحد»، «Unit Price».

**مرز:** Target Schema شامل TenantId/CompanyId نیست؛ این دو هرگز فیلد مقصد Import نمی‌شوند (D-103 بند ۹).

## ۶. الگوریتم پیشنهاد Mapping

**EXC-7 (`Proposed`)** — قطعی، بدون ML/شبکه، قابل تست با ورودی ثابت.

1. **نرمال‌سازی عنوان ستون:** تبدیل `ي/ك` عربی به `ی/ک` فارسی؛ ارقام فارسی و عربی-هندی به لاتین (فقط برای مقایسهٔ عنوان، نه مقدار سلول؛ EXC-16)؛ حذف فاصله‌های اضافه و ZWNJ/ZWJ در مقایسه؛ حروف کوچک؛ حذف علائم نگارشی ابتدا/انتها.
2. **ترتیب تطبیق:** (الف) تطبیق دقیق با نام/Alias نرمال‌شده؛ (ب) Alias؛ (پ) شباهت با آستانه (مثلاً فاصلهٔ ویرایشی نسبت‌به‌طول). **آستانه مقدار پیشنهادی برای تعیین است**، نه قطعی.
3. **ابهام:** اگر یک ستون با چند فیلد، یا چند ستون با یک فیلد منطبق شد ⇒ «نگاشت‌نشده» برای انتخاب کاربر؛ هیچ انتخاب خودکار در ابهام وجود ندارد (توافق ۱۲).
4. **ستون ناشناخته** (بی‌تطبیق) و **ستون تکراری** (دو سرستون هم‌نام پس از نرمال‌سازی) در نتیجه گزارش می‌شوند.
5. **خروجی:** فهرست پیشنهادها با دلیل و رتبهٔ اطمینان (دقیق/Alias/شباهت) تا UI بتواند در Combobox نشان دهد؛ پیشنهاد، تأیید نیست.
6. **Sheet:** اگر فایل چند Sheet دارد، نگاشت Sheet→Target مستقل است؛ نام Sheet نیز نرمال‌سازی می‌شود. نسخه‌های ناهمسان یک Sheet «منبع مستقل» هستند و یکی جایگزین دیگری نمی‌شود (V3.2 §12).

## ۷. ساختار Mapping و Versioning

**EXC-8 (`NeedsApproval`؛ ذخیره‌سازی `Blocked` تا S3)** — کلید جست‌وجوی پیشنهادی Mapping فقط این سه جزء است:

`(دامنهٔ Company از سرور، شناسه + نسخهٔ Target Schema، امضای Template/Sheet)`

**اثر انگشت سرستون‌ها جزء کلید نیست.** آن یک ویژگی ذخیره‌شدهٔ همان Mapping است و پس از پیدا شدن Mapping با فایل جدید مقایسه می‌شود (EXC-9). اگر اثر انگشت جزء کلید بود، هر تغییر ساختار به «Mapping پیدا نشد» می‌انجامید و ردهٔ «جابه‌جایی/تغییر مؤثر» هرگز رخ نمی‌داد.

- توافق ۶ می‌گوید Mapping به Company و Sheet و Template/Version مربوط است؛ **جزئیات کلیدگذاری هنوز تصمیم‌نشده است** (بخش ۲۰).
- **مالکیت:** طبق D-105 بند ۱ پیش‌فرض Company-owned است؛ اشتراک Mapping بین Companyهای یک Tenant تصمیم مستقل لازم دارد (D-105 بند ۳). موتور مالکیت فرض نمی‌کند.
- **هیچ ذخیرهٔ ماندگاری وجود ندارد (تا رفع مسدودی EXC-8):** نه جدول (نه در جداول مصرف‌کننده و نه در schema `trade`)، نه `localStorage`/`sessionStorage`، نه فایل. این طراحی هیچ محل ذخیره‌ای پیشنهاد نمی‌کند. شرط رفع مسدودی: تعیین مالکیت (D-105) و بسته‌شدن گیت‌های S3-0 (`TRADE_S3_READINESS.md` خط 50 برای جدول Trade؛ گیت عام: AGENTS.md بخش ۵.۳).
- **پیامد:** هر Import از مرحلهٔ پیشنهاد Mapping (گام ۶ بخش ۴) شروع می‌شود. تا رفع مسدودی، توافق‌های ۵ (نگهداری Mapping)، ۷ (استفادهٔ مجدد خودکار)، ۸ (تشخیص تغییر ساختار) و ۹ (اعتبارسنجی/تأیید مجدد Mapping) اجرا **نمی‌شوند**؛ **EXC-9 در عمل به EXC-8 وابسته است.**
- موتور Mapping را فقط به‌عنوان ورودی همان فراخوانی می‌پذیرد (برای تست و قرارداد خالص)؛ نگه‌داری آن بر عهدهٔ موتور نیست و این سند محل نگه‌داری تعیین نمی‌کند.
- **نسخه‌گذاری (طراحی آینده):** هر Mapping نسخهٔ Target Schema را نگه می‌دارد؛ تغییر نسخه، Mapping قبلی را «نیازمند اعتبارسنجی مجدد» می‌کند؛ نسخهٔ جدید به‌جای بازنویسی ساخته می‌شود.

**پرسش‌های باز دربارهٔ EXC-8 (فقط پرسش؛ پاسخ حدس زده نشده است):**
1. آیا رکورد Mapping طبق D-105 بند ۱ هر دو شناسهٔ TenantId و CompanyId معتبر را دارد (Company-owned)، یا طبق بندهای ۳ و ۴ اشتراک‌پذیر است؟
2. Mapping «دادهٔ کسب‌وکاری مشتری» است یا «پیکربندی فنی/زیرساختی» که طبق D-105 بند ۷ جداگانه طبقه‌بندی می‌شود؟

**EXC-5 (`NeedsApproval`) — سیاست شناسه‌ها:**
- HS/GTIN/IRC و شناسه‌های مشابه در حالت استاندارد **رشته**اند؛ صفر ابتدایی حفظ می‌شود. سلول متنی همان‌طور حفظ می‌شود (شاهد Spike 2، ClosedXML: «00123»، «۰۰۱۲۳» با ارقام فارسی، «٠٠١٢٣» با ارقام عربی و سلول با `quotePrefix` همه `Text` با مقدار دست‌نخورده).
- **تبدیل عدد به شناسه بدون حدس:** سلول عددی با فرمت صفرپر (123 با فرمت `00000`؛ 12345678905 با فرمت ۱۳ صفر؛ 1012100 با فرمت ۸ صفر) در ClosedXML `Number` همراه رشتهٔ فرمت است، نه متن صفرپر؛ بازسازی «0012345678905» فقط با قاعدهٔ صریح طول ثابت ممکن است. عدد بدون فرمت (123) هیچ اثر صفر ابتدایی ندارد.
- **بازسازی صفرهای ابتدایی فقط برای فیلدی که طول ثابت و قالب آن صریحاً در Target Schema تعریف شده است.** اگر عدد ذخیره شده و اطلاعات بازسازی مطمئن نیست ⇒ خطای `numeric_identifier_cell`. پیشنهاد دقیق‌تر (NeedsApproval): فقط عدد صحیح نامنفی؛ در صورت وجود رشتهٔ فرمت صفرپر سلول، طول آن باید با طول Schema هم‌خوان باشد؛ مثلاً مقدار 123.5 با فرمت `00000` نباید «00124» شود و رد می‌شود.
- **ارقام:** اگر «تعداد کل ارقام بخش صحیح» بیش از ۱۵ باشد ⇒ رد. عدد ۱۶رقمی و بلندتر فقط از **سلول متنی** معتبر است. شاهد: در Spike 2 عدد 1234567890123456 در فایل ساختگی `Number` (double) خوانده شد؛ دقت Excel معمولاً ۱۵ رقم است (در اجرای قبلی Spike 1 عدد ۱۹رقمی در خود فایل دقت از دست داده بود)؛ پس سیاست «بیش از ۱۵ رقم ⇒ رد» همچنان لازم است.
- نرمال‌سازی ارقام فارسی/عربی فقط برای مقایسه و Duplicate Detection است (EXC-16)؛ هیچ تبدیل عمومی شناسه‌ها وجود ندارد.
- **پرسش مالک (NeedsApproval):** آیا تعریف صریح «طول ثابت/قالب» در Target Schema برای فیلدهای شناسه الزامی شود و رقم کنترل (در صورت وجود) هم بررسی شود؟ تا پاسخ، هیچ بازسازی انجام نمی‌شود و سلول عددی در ستون شناسه ⇒ خطا.
- هیچ قاعدهٔ دیگری برای ساخت مقدار شناسه از سلول عددی حدس زده نمی‌شود.

**مبلغ/اعشار (`Proposed`، NeedsApproval برای جزئیات):** مقدار از متن خام سلول با فرهنگ Invariant مستقیم به `decimal` تبدیل شود؛ هرگز `double→decimal`؛ اگر از scale/precision مقصد بیشتر باشد ⇒ رد، نه گرد‌کردن. (دقت اعشار در `TRADE_S3_READINESS.md` بخش ۴ هنوز تصمیم‌نشده است.)

**تاریخ و پنهان‌ها (`Proposed`):** قرارداد Parser باید `date1904` را بخواند و در نتیجه برگرداند (تبدیل سریال بدون آن خطای ۴ ساله می‌دهد). Sheet/ردیف/ستون پنهان در Preview هشدار/گزینهٔ صریح دارند و بی‌صدا حذف یا ورود نمی‌شوند.

**EXC-6 (`Proposed`)** — فرمول هرگز اجرا نمی‌شود؛ فقط مقدار cached خوانده می‌شود. فرمول بدون مقدار cached یا با خطا (`#REF!`، `#VALUE!` و ...) ردیف را با خطای صریح رد می‌کند (هم‌جهت `TRADE_DESIGN_V3_2.md` §12). برای **هر سلول فرمول‌دار** حتی با مقدار cached معتبر هشدار ثبت می‌شود: مقدار cached ممکن است از یک لینک خارجی نادیده‌گرفته‌شده بیاید و کهنه باشد. **اصلاح ادعای قبلی Lead (شاهد Spike 2؛ `results_formula_eval.jsonl`):** ادعای «ClosedXML هنگام خواندن `Value` فرمول را اجرا نمی‌کند و `Value` هم Blank می‌دهد» فقط برای فرمولی با عنصر `<v></v>` خالی درست بود. روی فایل‌هایی که عنصر `<v>` ندارند (`formulas_nov.xlsx`، `formulas_heavy_nov.xlsx`) خواندن `c.Value` فرمول را **اجرا کرد** (`B1 ⇒ Number:10`، `B4 ⇒ Text:ab`، `B5 ⇒ Error:#NAME?`)؛ روی 199 فرمول سنگین، خواندن ۵ سلول اول ≈4067ms و Peak 746MB (افزوده 712MB) شد و `A1` با `ArgumentOutOfRangeException` شکست؛ خواندن فقط `HasFormula`+`CachedValue` برای همان فایل 452ms و 81MB بود و هیچ محاسبه‌ای نشد. `GetFormattedString()` طبق کد منبع ClosedXML (گزارش Lead) از `Value` استفاده می‌کند و بازبین امنیتی (آزمون مستقل؛ خروجی خام در پیوست پ نیست) نشان داد `CachedValue` را هم تغییر می‌دهد (سلول `A50` با `<f>1+1</f>` بدون `<v>`: cached از blank به 2). **پیامد و قواعد (پیشنهادی؛ NeedsApproval):** این رفتار هم ریسک DoS است (اجرای فرمول سنگین بدون لغو و با حافظهٔ زیاد) و هم EXC-6 را دور می‌زند؛ (الف) **Allow-list، نه Deny-list:** برای سلول با `HasFormula` فقط `HasFormula`، `FormulaA1`، `CachedValue`، `DataType`، `Style.NumberFormat` و `Address` مجازند و هر API دیگر ممنوع است؛ فهرست ممنوعِ قبلی (`Value`، `GetFormattedString`، `GetString`، `GetText`، `TryGetValue`) ناکافی بود. شاهد (`apiprobe`؛ `results_api_eval.txt` در پیوست پ؛ فایل `formulas_nov.xlsx`، سلول‌های B1 و B4؛ شناسایی اجرا فقط با تغییر `CachedValue` از blank): 11 API فرمول را اجرا کردند (`GetString`، `GetText`، `TryGetValue<string>`، `GetFormattedString`، `GetBoolean`، `GetDateTime`، `GetError`، `GetValue<string>`، `GetDouble`، `Value`، `ws.Search`) و 5 مورد نه (خواندن `HasFormula`+`FormulaA1`+`CachedValue`+`DataType`+`Style.NumberFormat.Format`، `IsEmpty()`، `CopyTo`، `AsRange().FirstCellUsed`، `Range.CellsUsed(pred)`). محدودیت: دو سلول از یک فایل ساختگی و معیار فقط تغییر `CachedValue`؛ نبود تغییر اثبات نبود اجرا نیست و `Address` در این probe نبود (NotRun؛ در تست قرارداد Parser پوشش داده شود)؛ به همین دلیل قاعده Allow-list است. (ب) متن نمایشی فقط برای سلول بدون فرمول ساخته شود؛ (ج) `Evaluate` هرگز؛ `Search` و هر API دامنه‌ای که روی سلول‌های فرمول‌دار می‌چرخد استفاده نشود؛ (د) تست قرارداد Parser با «فرمول بدون عنصر `<v>`» در PR Parser الزامی است. شکاف: ExcelDataReader فرمول بدون مقدار را با «خالی» یکی می‌کند (شاهد Spike 1) و برای EXC-6 ناکافی است.

**EXC-16 (`Proposed`)** — نرمال‌سازی ارقام فارسی/عربی-هندی **فقط برای مقایسه و Duplicate Detection**، متناسب با نوع فیلد؛ مقدار اصلی ورودی حفظ می‌شود و مقدار نرمال‌شده جدا (تفکیک‌شده) نگه‌داری/گزارش می‌شود (مثلاً «۰۰۱۲۳» و «00123» در تشخیص تکراری یکی دیده شوند ولی مقدار ورودی تغییر نکند). **تبدیل عمومی همهٔ متن‌ها/شناسه‌ها مجاز نیست.** تاریخ شمسی/میلادی نیز در لایهٔ مستقل و فقط برای فیلد نوع تاریخ (جزئیات در PR موتور). این بند پرسش مالک ۲ قبلی (آیا نگاشت ارقام در شناسه «تبدیل مخرب» است) را به‌صورت پیشنهاد بسته است: خیر برای ذخیره، بله فقط برای مقایسه؛ تأیید نهایی با مالک.

## ۱۰. تشخیص تکراری

- **داخل فایل:** بر اساس «کلید طبیعی» که Target Schema مشخص می‌کند (پس از نرمال‌سازی)؛ تکرار ⇒ خطا یا هشدار طبق تعریف مصرف‌کننده، هرگز حذف/ادغام بی‌صدا.
- **نسبت به DB:** Use Case مجموعهٔ کلیدهای موجود را (با Store موجود، فقط در محدودهٔ Company/Tenant سرور) به‌صورت دادهٔ ورودی به موتور می‌دهد؛ موتور فقط مقایسه می‌کند و نتیجه «موجود/ناموجود/مبهم» است. ادغام خودکار رکوردهای مشابه بر اساس نام/کد/شباهت ممنوع است (D-105 بند ۹).
- **Idempotency ثبت:** «رکورد یکسان موجود ⇒ رد/خطا»، نه Upsert (تفسیر Lead؛ متن D-105 بند ۹ دربارهٔ تغییر مالکیت و ادغام خودکار است، نه Upsert). دامنهٔ کلید طبیعی (Company یا Tenant) به تصمیم مالکیت D-105 بندهای ۳ و ۴ وابسته است. جزئیات در EXC-12 (بخش ۱۵).

**ترتیب ثابت کنترل (مستقل از شکل API، `Proposed`):** نشست ← Company Context ← Entitlement/Permission (D-074 بند ۳) ← **فقط سپس** خواندن بدنه. Anti-forgery برای آپلود الزامی است (D-012) و توکن **فقط از هدر** پذیرفته می‌شود، نه از فیلد فرم multipart (اعتبارسنج برای یافتن توکن در فرم کل بدنه را می‌خواند)؛ **سقف بدنه پیش از اعتبارسنجی Anti-forgery** اعمال می‌شود.

**گره‌خوردن Preview به Commit (مفهومی؛ Commit تا رفع مسدودی کامل `Blocked` است):** Commit هرگز ردیف را از کلاینت نمی‌پذیرد و باید دقیقاً همان دادهٔ اعتبارسنجی‌شده را ثبت کند، مقید به UserId، Company، Tenant (از Context سرور)، نسخهٔ Target Schema، hash فایل (محاسبه‌شده در سرور) و hash Mapping. اما بدون state سمت سرور، مقدار مرجع «Company و hash زمان Preview» فقط از کلاینت می‌آید و دفاع در برابر جابه‌جایی Company بین Preview و Commit (TOCTOU) را **تضمین نمی‌کند**. تضمین فقط با یکی از دو راه است (هر دو `Proposed`/`NeedsApproval`): (۱) توکن Preview محافظت‌شده با Data Protection (purpose مشخص؛ شامل UserId، TenantId، CompanyId، نسخهٔ Schema، hash فایل محاسبه‌شده در سرور، hash Mapping، زمان صدور و انقضای کوتاه)؛ این state ماندگار نیست ولی تک‌مصرف هم نیست؛ یا (۲) Blocked ماندن Commit تا وجود state سمت سرور. **رفع مسدودی Commit:** S3-0 و D-105 و نیز (state سمت سرور یا تأیید صریح گزینهٔ توکن)؛ انقضا داخل توکن بی‌state ممکن است و Blocked نیست؛ فقط تک‌مصرف‌بودن و Idempotency سطح Import به state ماندگار نیاز دارند. **پیش‌شرط‌های گزینهٔ توکن (NeedsApproval):** (۱) Host فراخوانی صریح `AddDataProtection`/`PersistKeysTo*` ندارد (جست‌وجو در `Server`: فقط `Server/Infrastructure/DatabaseSetup/DatabaseConnectionSettingsStore.cs`، یکی `DataProtectionProvider.Create` برای کلید تنظیمات DB و یکی `AddDataProtection` قدیمیِ فقط‌خواندنی)؛ `WorkContextCookie` از `IDataProtectionProvider` تزریقی با protector محدود به زمان استفاده می‌کند؛ نگهداری/چرخش کلید و رفتار چندنمونه/راه‌اندازی مجدد ارزیابی نشده و باید جدا تصمیم شود؛ (۲) توکن فقط در حافظهٔ کلاینت (D-012؛ نه `localStorage`)؛ (۳) مقادیر Tenant/Company داخل توکن فقط برای تطبیق برابری با Context بازحل‌شده از `CompanyAccessService` است، نه مبنای دسترسی (D-013). مسیر «آپلود دوباره + hash» به‌تنهایی با همین محدودیت است (بخش ۱۵). تک‌مصرف‌بودن شناسهٔ Preview و Idempotency سطح Import به state ماندگار نیاز دارند و Blocked‌اند.

**پیش‌شرط «تکراری نسبت به DB»:** مجوز view موجودیت مقصد (الگوی D-084 بند ۲)، فقط در Company سرور و پشت Rate Limit؛ در غیر این صورت پورت تکراری می‌تواند وجود رکورد را نشت دهد.

**اصلاح برداشت قبلی Lead:** در متن قبلی این سند و ADR نوشته شده بود «پروژهٔ کتابخانهٔ خنثی تنها گزینهٔ سازگار با توافق ۱۵ است و فضای‌نام در `Trade.Application` با آن سازگار نیست». آن برداشت از متن توافق بیش از حد بود. مالک روشن کرد «فقط Party/Product نباشد» یعنی برای موجودیت‌های مختلف Trade (Proforma، OrderRegistration و …) قابل استفاده باشد (نقل از ابلاغ Lead؛ مستقل راستی‌آزمایی نشد). بنابراین فضای‌نام `Import` در `Trade.Application` با توافق ۱۵ سازگار است و پروژهٔ مستقل به‌عنوان پیشنهاد لازم دانسته نمی‌شود (NeedsApproval)؛ همهٔ جاهایی که آن را «لازم» می‌دانستند هماهنگ شد.

**تناقض احتمالی با `docs/ARCHITECTURE.md` خط 173 (فقط گزارش؛ آن سند تغییر نکرد):** خط 173 می‌گوید پروژه‌های Trade به پروژه‌های حسابداری، Server یا Infrastructure/Persistence حسابداری Reference نمی‌دهند. موتور در `Trade.Application` و Parser در `Trade.Infrastructure` با این خط تناقضی ندارد (جهت وابستگی Infrastructure ← Application ← Domain همان است که در `.csproj`ها دیده شد). شرط: هیچ Reference به حسابداری/Server افزوده نشود. نکتهٔ باز: افزودن PackageReference کتابخانهٔ Excel به `Trade.Infrastructure` تغییر وابستگی است و به تأیید EXC-17 و ثبت نسخه در `Directory.Packages.props` وابسته است.

**تشخیص تکراری نسبت به DB:** موتور فقط تکراری داخل فایل را می‌سنجد؛ Use Case مجموعهٔ کلیدهای موجود را (با Store موجود) به‌صورت دادهٔ ورودی به موتور می‌دهد. interface جدید «پورت تکراری» فقط با نیاز اثبات‌شده افزوده شود (YAGNI). پیش‌شرط view موجودیت مقصد در بخش ۱۲.


**EXC-4 (`Proposed`)** — قرارداد Parser جدا از موتور و مستقل از کتابخانه: مدل سلول (در `Trade.Application/Import` تعریف و توسط Parser در `Trade.Infrastructure` تولید می‌شود): مقدار خام، نوع، رشتهٔ فرمت عدد، متن نمایشی (**فقط برای سلول بدون فرمول**)، وجود فرمول، مقدار cached و خطای cached؛ فرمول هرگز ارزیابی نمی‌شود (EXC-6). قواعد مخصوص ClosedXML (Allow-list برای سلول فرمول‌دار: فقط `HasFormula`، `FormulaA1`، `CachedValue`، `DataType`، `Style.NumberFormat` و `Address`؛ هر API دیگر و `Evaluate` ممنوع) شرط پیاده‌سازی Parser با آن کتابخانه‌اند (بخش ۱۸)، نه بخشی از قرارداد. «جریانی» فقط برای API موتور (پذیرش ردیف‌های دسته‌ای) است؛ Parser مبتنی بر ClosedXML جریانی نیست (DOM). انتخاب کتابخانه EXC-17 است.

## ۱۴. فایل‌های بزرگ و حافظه

- «جریانی» فقط برای API موتور است: موتور ردیف‌ها را به‌صورت دسته‌ای می‌پذیرد و کل فایل را به‌صورت شیء در حافظه نگه نمی‌دارد، جز ساختارهای لازم (مجموعهٔ کلیدهای تکراری، شمارش خطاها). **Parser مبتنی بر ClosedXML جریانی نیست (DOM):** کران حافظه فقط از Guard و سقف‌ها می‌آید (Spike 2: افزوده ≈270MB روی ≈18MiB بازشده).
- **سقف تعداد خطای ذخیره‌شده** در Preview (بیش از آن «و N خطای دیگر») تا حافظه کران‌دار بماند؛ مقدار تعیین‌نشده.
- **شاهد Spike 2 (2026-11-19؛ جزئیات و جدول‌ها: [`EXCEL_IMPORT_LIBRARY_COMPARISON.md`](EXCEL_IMPORT_LIBRARY_COMPARISON.md) §۳):** فایل ساختگی واقع‌نما 20,001 ردیف × 14 ستون، 253,347 سلول، 2.2MB (بازشده 18,865,100 بایت ≈18MiB)، .NET SDK 10.0.403، ۲ هسته، سقف heap مدیریت‌شده 1.5GB، ۳ تکرار؛ **نه Benchmark رسمی**. ClosedXML 0.105.1: 1841/1995/1818ms، Peak کل 304–307MB (افزوده 270–273MB)؛ ExcelDataReader 3.9.0: 581–635ms و 142MB؛ Open XML SDK 3.5.1 (فقط شمارش عنصر، بدون مادی‌سازی مقدار؛ پس کم‌برآورد است): 733–767ms و 217MB. ClosedXML هر Import را DOM‌وار بار می‌کند؛ بودجهٔ حافظه (EXC-13) و هم‌زمانی ≤ 2 (پیشنهادی؛ پیش از تثبیت باید اندازه‌گیری شود) ضروری است. برآورد بدترین حالت (برون‌یابی خطی فقط برای محتوای واقع‌نما) در سقف مؤثر «جمع بازشده ≤ 40MB»: ≈600MB افزوده و ≈4.1–4.4s برای یک Import و ≈1.2GB برای دو Import هم‌زمان (اندازه‌گیری نشده؛ بدترین حالت ترکیبی NotRun). «جریانی = حافظهٔ کم» برای Open XML SDK/ExcelDataReader تأیید نشده است. اجرای قبلی Spike 1 (200k ردیف) شرایط متفاوت و تک‌اجرایی داشت و با Spike 2 مستقیم قابل‌مقایسه نیست.
- تقسیم دستهٔ بزرگ هنگام Commit `Deferred` است (EXC-12).

## ۱۵. مدیریت خطا و جلوگیری از ثبت ناقص

**EXC-12 (`NeedsApproval`)** — موتور فقط **خطاهای ردیفی و دسته‌ای** (ساختاری و تجاری تفکیک‌شده، هرکدام با شمارهٔ ردیف و نام فیلد) را گزارش می‌کند؛ **هیچ ثبتی نمی‌کند و دربارهٔ Commit تصمیم نمی‌گیرد.** سیاست Commit را Use Case هر عملیات Trade تعیین می‌کند. پیشنهاد نسخهٔ اول: **All-or-Nothing در سطح دسته**؛ ثبت ردیفی در v1 پیاده نمی‌شود و بعداً فقط برای موجودیت‌هایی که قواعد تجاری اجازه می‌دهد بررسی می‌شود. **Commit تا رفع مسدودی کامل (گیت S3-0 و تصمیم مالکیت D-105، و نیز یکی از دو: state سمت سرور یا تأیید صریح گزینهٔ توکن Data Protection) Blocked است.** شکست میانه ⇒ Rollback کامل (V3.2 §12). تقسیم دسته‌های بزرگ `Deferred`.

> **تفسیر Lead — نیازمند تأیید:** «همه‌یاهیچ در سطح کل دسته (فایل)» تفسیر Lead از توافق ۱۲ است، نه عین متن مالک؛ ممکن است مالک فقط سطح ردیف را مراد کرده باشد (ممنوعیت ثبت ردیف ناقص/مبهم).

**تکمیل‌های پیشنهادی (`Proposed`، NeedsApproval):** قرارداد **مفهومی** برای Use Case مصرف‌کننده، نه موتور. موارد وابسته به state ماندگار سمت سرور (تک‌مصرف‌بودن Preview، Idempotency سطح Import؛ انقضا داخل توکن بی‌state ممکن است، بند ۳) **Blocked** تا گیت S3-0 و تصمیم مالکیت (D-105)‌اند و هیچ ذخیرهٔ Mapping/Preview (جدول، `localStorage`، فایل) پیشنهاد نمی‌شود؛ توافق‌های ۵، ۷، ۸، ۹ تا رفع مسدودی عملاً اجرا نمی‌شوند.
1. **Commit دوباره کامل اعتبارسنجی می‌کند** (از جمله تکراری) داخل همان تراکنش؛ به نتیجهٔ Preview اعتماد نمی‌شود.
2. **گره‌خوردن Preview به Commit:** قرارداد مفهومی در بخش ۱۲؛ بدون state سمت سرور جابه‌جایی Company بین Preview و Commit را تضمین نمی‌کند.
3. **انتقال Preview→Commit (همهٔ گزینه‌ها `NeedsApproval`؛ تا رفع مسدودی Commit Blocked است):** (الف) توکن Preview محافظت‌شده با Data Protection (purpose مشخص؛ شامل UserId، TenantId، CompanyId، نسخهٔ Schema، hash فایل محاسبه‌شده در سرور، hash Mapping، زمان صدور و انقضای کوتاه)؛ state ماندگار نیست ولی تک‌مصرف نیست و پیش‌شرط‌های بند «گره‌خوردن Preview به Commit» (key ring، حافظهٔ کلاینت، تطبیق برابری با Context سرور) را دارد؛ (ب) آپلود دوبارهٔ فایل با تطبیق hash: بدون state سمت سرور مقدار مرجع «Company و hash زمان Preview» فقط از کلاینت می‌آید و جابه‌جایی Company را تضمین نمی‌کند مگر همراه (الف)؛ (پ) فایل/نتیجهٔ موقت سمت سرور مقید به کاربر/Company: state ماندگار است و تا رفع مسدودی ذخیره‌سازی ممنوع؛ هیچ محلی برایش پیشنهاد نمی‌شود؛ (ت) Blocked ماندن Commit. **پیامد:** تک‌مصرف‌بودن شناسهٔ Preview و Idempotency سطح Import فقط با state ماندگار (استثنای جدا و NeedsApproval) ممکن‌اند و تا آن زمان Blocked‌اند. دفاع در عمق (به‌تنهایی ناکافی): اعتبارسنجی کامل دوباره در Commit + قید/بررسی یکتایی (پیشنهاد؛ مجوز جدا).
4. **سقف ردیف (EXC-13) عملاً مرز اتمی‌بودن است:** تراکنش بزرگ روی SQL Server خطر lock escalation، رشد log و Timeout دارد؛ تا وقتی «تقسیم دسته» Deferred است، سقف باید به آن آگاه تعیین شود.
5. **تراکنش و Store موجود (شواهد با خواندن کد؛ اجرا نشد):** `PartyStore.AddAsync` (`Modules/Trade/Trade.Infrastructure/Parties/PartyStore.cs` خطوط 76–89) و `ProductStore.AddAsync` (`Products/ProductStore.cs` از خط 65) هرکدام `SaveChangesAsync` می‌زنند و در تکرار کد `ChangeTracker.Clear()` می‌کنند؛ پس Commit همه‌یاهیچ دسته‌ای به متد/مسیر جدید Store و تراکنش صریح نیاز دارد (بدون تغییر Schema) و تراکنش بیرونی با این Storeها تداخل می‌کند. اعتبارسنج‌های Target Schema باید قواعد موجود Application/Domain را دوباره به کار گیرند، نه از نو بنویسند (`PartyService.Validate` فعلاً private است).
6. **Idempotency:** «رکورد یکسان موجود ⇒ رد/خطا»، نه Upsert (تفسیر Lead؛ متن D-105 بند ۹ دربارهٔ تغییر مالکیت و ادغام خودکار است). برای Party/Product ایندکس‌های یکتای فیلترشده از قبل هست: `(TenantId, Code)` در `PartyConfiguration`/`ProductConfiguration` (`UX_Parties_Tenant_Code_Active`، `UX_Products_Tenant_Code_Active`) و `(TenantId, Gtin)`/`(TenantId, Irc)` در `ProductIdentifierConfiguration`، با `TenantId` تاریخی (عملاً CompanyId؛ ایندکس‌ها از خواندن کد دیده شدند). «تغییر Schema» فقط برای موجودیت‌های آینده (Proforma/OrderRegistration) صدق می‌کند و تغییر دامنهٔ کلید طبیعی (Company یا Tenant) به D-105 بندهای ۳ و ۴ و S3-0 وابسته است. «کلید Idempotency سطح Import (شناسهٔ Preview)» وابسته به state ماندگار و **Blocked** است (مورد ۳).
7. **وابستگی Product:** Commit برای Product به D-085 وابسته است که تصمیمش `Proposed + NeedsApproval` است در حالی که پیاده‌سازی آن در `main` با PR #644 ادغام شده (طبق متن D-085).

- خطای Parse/امنیتی ⇒ توقف قبل از هر پردازش؛ پیام قابل‌فهم بدون افشای جزئیات داخلی.
- Exception بی‌صدا بلعیده نمی‌شود؛ `ILogger<T>` بدون محتوای سلول.
- لغو (Cancellation) در هر مرحلهٔ پیش از Commit بدون اثر جانبی. توجه: ClosedXML 0.105.1 لغو بارگذاری ندارد؛ `CancellationToken` فقط بین مراحل (پیش از Guard/بازکردن و پس از بارگذاری) بررسی می‌شود؛ لغو سطح Host/درخواست فقط پاسخ کلاینت را قطع می‌کند و به‌تنهایی CPU/حافظهٔ بارگذاریِ در جریان را آزاد نمی‌کند (استنتاج از نبود لغو در API؛ آزمون نشده)؛ توقف قطعی حین بارگذاری فقط با Parse در فرایند جدا و kill ممکن است (NeedsApproval؛ EXC-13).
- ابهام در Mapping یا نتیجهٔ اعتبارسنجی ⇒ هرگز ثبت.

## ۱۷. عملکرد و هزینه

- هزینهٔ اصلی: Parse فایل (O(n)؛ در ClosedXML DOM)، نرمال‌سازی و اعتبارسنجی ردیف‌ها، و نگه‌داری کلیدهای تکراری. تشخیص تکراری نسبت‌به DB باید دسته‌ای (Batch) باشد، نه یک پرس‌وجو به‌ازای هر ردیف (طراحی دقیق با مصرف‌کننده).
- هزینهٔ توسعه: ClosedXML (گزینهٔ اول فعلی مالک) ساده‌ترین API را می‌دهد (نوع سلول و رشتهٔ فرمت آماده؛ برای سلول فرمول‌دار فقط `HasFormula`/`CachedValue`، بخش ۹)؛ Open XML SDK کد Parser بیشتر می‌خواهد (SharedStrings، InlineString، Styles، تاریخ) و رشتهٔ فرمت عدد را باید خودمان از `styles.xml` بسازیم؛ ExcelDataReader ساده ولی فرمول بدون cached را از خالی جدا نمی‌کند (سند مقایسه).
- اعداد حافظه/زمان بخش ۱۴ و سقف‌ها از Spike 2 با ۳ تکرار (فایل اصلی) و ۱ تکرار (بقیه) روی یک ماشین ۲ هسته‌ای‌اند و برای ظرفیت‌گذاری قطعی قابل‌اتکا نیستند؛ Benchmark رسمی `NotRun`.
