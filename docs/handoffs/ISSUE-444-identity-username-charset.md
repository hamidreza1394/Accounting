# تحویل وظیفه — ISSUE-444-identity-username-charset

- **Issue:** #444 (بستهٔ B1: هویت و چرخهٔ عمر کاربر)
- **Agent/مسئول:** Backend Wave-1 mission
- **تاریخ:** 2026-11-05
- **وضعیت:** انجام‌شده (در انتظار CI و Merge با اجازهٔ مالک)

## هدف و معیارهای پذیرش
- [x] API دیگر نمی‌تواند سیاست نام کاربری Razor VM (`^[a-zA-Z0-9._@+-]{3,20}$`) را دور بزند.
- [x] پوشش تست مجوزدهی create/update (403 برای غیرمدیر نصب) و 409 نام کاربری تکراری به‌صورت case-insensitive افزوده شد.
- [x] هیچ تستی حذف یا تضعیف نشد؛ هیچ DTO/Route/Migration ای تغییر نکرد.

## خلاصه تغییرات
- **نقص واقعی:** `CreateUserAsync`/`UpdateUserAsync` فقط طول نام کاربری (۳..۲۰) را بررسی می‌کردند؛ Regex سیاست (`Constants.RegularExpression.Username`) فقط روی ViewModelهای Razor اعمال می‌شد. ستون `Username` از نوع `varchar(20)` (`IsUnicode(false)`) است؛ نام‌هایی مثل `ali;drop` یا متن فارسی می‌توانستند از API ذخیره شوند (ناسازگاری داده و ناسازگاری سیاست).
- **اصلاح:** افزودن یک شرط Regex به زنجیرهٔ اعتبارسنجی هر دو مسیر (400 با همان پیام استاندارد). الگوریتم hash، Audit، DTO و رفتار موفق بدون تغییر.
- **ممیزی B1 — نقص‌هایی که عمداً تغییر داده نشدند (نیازمند تصمیم مالک):**
  - بازیابی/تنظیم رمز فراموش‌شده: هیچ مسیری برای forgot-password یا reset توسط مدیر وجود ندارد؛ در اسناد محصول (Issue #444) خارج از scope فعلی است؛ ساخت endpoint جدید نیازمند تصمیم محصولی و ADR است.
  - ناسازگاری حداقل طول رمز (۸ در مسیرهای عادی در برابر ۱۲ در provisioning): تغییر آن یکی از دو مسیر را می‌شکند یا سیاست را تضعیف می‌کند؛ نیازمند تصمیم.
  - فیلدهای ساعت محلی قدیمی (`LastLoginDateTime`/`InsertDateTime`) در کنار فیلدهای UTC در یک DTO: تصمیم D-067 هنوز `Proposed` است و بدون مجوز تغییر نمی‌کند.
  - رویداد مجزای `UserDeactivated`: رویداد `UserUpdated` فعلی قبلی/جاریِ IsActive را ثبت می‌کند؛ رویداد جدید تغییر قرارداد Audit است و نیازمند تأیید است.

## فایل‌های مهم تغییرکرده
- `Server/Api/UserAdministrationEndpoints.cs` — شرط Regex نام کاربری در Create و Update.
- `tests/Template.Tests/UserAdministrationMutationTests.cs` — ۵ تست جدید (۲ تای قرمز→سبز charset؛ ۳ تای تثبیت رفتار موجود: 403 create، 403 update، 409 تکراری).

## تصمیم‌های فنی
- تصمیم معماری جدیدی گرفته نشد؛ هم‌سوسازی API با سیاست تثبیت‌شدهٔ ViewModelها و `Constants.RegularExpression.Username`.
- ریسک سازگاری بررسی شد: حساب‌های provisioning به سقف ۶۴ کاراکتر در payload اجازه دارند، اما ستون ۲۰ کاراکتری است؛ نام‌های >۲۰ روی SQL Server نمی‌توانند ذخیره شوند، پس اثر عملی روی حساب‌های موجود دیده نشد. اگر حسابی با نام خارج از الگو موجود باشد، فقط ویرایشِ آن حساب 400 می‌گیرد (fail-closed) — ثبت در ریسک‌ها.

- سازگاری: فقط نام‌های خارج از الگوی موجودِ Razor رد می‌شوند؛ رفتار موفق بدون تغییر.
