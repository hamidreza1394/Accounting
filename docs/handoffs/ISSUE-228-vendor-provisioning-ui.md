# تحویل وظیفه — ISSUE-228-vendor-provisioning-ui

- **Issue:** https://github.com/hamidreza1394/Accounting/issues/228
- **وضعیت:** UI و آزمون‌های کلاینت در شاخه؛ منتظر CI و بازبینی

## تغییرات
- افزودن فرم فارسی RTL برای انتخاب نصب مشتری، نام شرکت حسابداری، نوع شرکت، نام کاربری مدیر اولیه و زیرسیستم‌های خریداری‌شده.
- پیش‌فرض نوع شرکت «مستقل» و اولین زیرسیستم «مالی» است؛ نصب اولِ در دسترس به‌صورت پیش‌فرض انتخاب می‌شود.
- اتصال فرم به API provisioning با توکن Anti-forgery تازه، RequestId برای retry/idempotency و نمایش وضعیت‌های ثبت‌شده.
- افزودن دکمه «راه‌اندازی اولیه» در فهرست مشتریان، فقط وقتی مجوزهای مشاهده/مدیریت مشتری و نصب موجود باشند.
- افزودن آزمون UI که payload ارسالی را بررسی می‌کند و نبود فیلد password/passwordHash را اثبات می‌کند.

## مرزهای امنیتی
- هیچ رمز عبور یا راز bootstrap در UI دریافت، نگهداری یا ارسال نمی‌شود.
- فرم صریحاً نشان می‌دهد درخواست فعلی فقط در Vendor ذخیره شده؛ تا اتصال امضاکننده و تأیید مصرف‌کننده مشتری، بسته‌ای تحویل نشده و شرکت/مدیر مشتری ایجادشده محسوب نمی‌شوند.
- وضعیت فعلی backend «AwaitingSigner» است. UI، API یا این PR امضای واقعی، انتقال آفلاین، تأیید مشتری یا جلوگیری از replay در مصرف‌کننده را ادعا نمی‌کند.
- تغییرات فقط در Vendor/Vendor.Web و مستندات Vendor هستند؛ Server/** و دیتابیس مشتری تغییر نمی‌کنند.

## وضعیت بازبینی مجدد — 2026-10-31

- فرم در main شامل نصب فعال، لایسنس معتبر، نام شرکت، نوع رابطهٔ سازمانی، دوره مالی، شرکت مادر تأییدشده، نام کاربری/ایمیل مدیر اولیه و زیرسیستم‌های مشتق از entitlement امضاشده است.
- اولین نصب فعال و اولین لایسنس معتبر به‌صورت پیش‌فرض انتخاب می‌شوند؛ شماره/کد/محصول/sequence کنار انتخاب‌ها نمایش داده می‌شود تا اپراتور قبل از ثبت مقصد را بررسی کند.
- نوع شرکت پیش‌فرض «مستقل» است. مقادیر مستقل/مادر/تابعه عمداً enum بسته‌اند؛ این مقادیر ساختار سلسله‌مراتب را تعیین می‌کنند و گزینهٔ دلخواه admin بدون تغییر قرارداد و اعتبارسنجی مشتری می‌تواند دادهٔ ناسازگار بسازد. برای دسته‌بندی‌های سفارشی باید فیلد metadata جدا طراحی شود.
- رمز عبور در Vendor دریافت یا ذخیره نمی‌شود؛ مدیر مشتری در Enrollment رمز خود را تعیین می‌کند. این مرز امنیتی حفظ شده است.
- PR جاری [#368](https://github.com/hamidreza1394/Accounting/pull/368) فقط helper text، توضیح defaultهای انتخاب و دسترس‌پذیری aria-describedby را بهبود می‌دهد؛ منطق provisioning و قرارداد تغییر نمی‌کند.
- باقی‌مانده‌های Issue #228 اکنون وابستگی‌های عملیاتی مستقل‌اند: HSM واقعی برای امضای Production (#236)، checkpoint مستقل Audit (#107)، anti-rollback و call-site نهایی revocation (#214/#364)، و آزمون میدانی دو میزبان مستقل (#235).
