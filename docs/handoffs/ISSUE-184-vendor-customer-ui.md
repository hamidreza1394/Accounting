# Issue #184 — رابط کاربری ثبت و ویرایش مشتری تجاری Vendor

## هدف و محدوده
این تغییر عملیات ثبت و ویرایش رکورد `VendorCustomer` را به فهرست مشتریان تجاری در UI مستقل Vendor اضافه می‌کند. این موجودیت مشتری تجاری سامانه مرکزی است و به‌معنی ایجاد شرکت حسابداری یا provision دیتابیس مشتری نیست.

## تغییرات
- فرم فارسی RTL با labelهای صریح، محدودیت طول، حالت busy، پیام خطای دسترس‌پذیر و چیدمان واکنش‌گرا.
- درخواست POST/PUT هم‌مبدأ با `credentials: same-origin` و `cache: no-store`.
- دریافت توکن antiforgery تازه از `/api/auth/antiforgery` برای هر عملیات نوشتن.
- ارسال RowVersion فعلی در ویرایش و نمایش پیام مشخص برای `stale_row_version`.
- دکمه‌های ثبت/ویرایش فقط در صورت وجود `vendor.customers.manage` در نمای نشست نشان داده می‌شوند؛ مجوز نهایی همچنان توسط endpoint و بررسی DB سمت سرور اعمال می‌شود.
- `GET /api/auth/me` فهرست مرتب و یکتای permission claimهای نشست را برای کنترل‌های UI برمی‌گرداند.

## تست و اعتبارسنجی
- Vitest: ایجاد موفق، ارسال CSRF، conflict شماره مشتری، stale RowVersion و نمایش/پنهان‌سازی عملیات براساس مجوز.
- .NET integration test: قرارداد permissions در `/api/auth/me`.
- CI این شاخه پس از آخرین commit باید Vendor CI و .NET CI را کامل کند؛ تا پیش از نتیجه نهایی وضعیت `Implemented / Not yet Verified` است.
- اجرای محلی در این اتصال در دسترس نیست؛ نتیجهٔ CI مرجع اعتبارسنجی است.

## امنیت و مرز دیتابیس
- سرور منبع نهایی مجوز است و هر درخواست تغییردهنده با antiforgery بررسی می‌شود.
- RowVersion از پاسخ API استفاده می‌شود تا نوشتن با نسخهٔ stale رد شود.
- هیچ تغییر در دیتابیس حسابداری مشتری، Migration مشترک، راز، رمز پیش‌فرض یا اتصال مستقیم UI به دیتابیس انجام نشده است.
- provisioning شرکت/نصب مشتری و ساخت کاربر/رمز مشتری خارج از این Issue است و به طراحی مستقل provisioning نیاز دارد.
