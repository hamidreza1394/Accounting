# OD-15 — نام قیدهای legacy پس از Pin

**سؤال:** پس از Pin کردن نام قیدها، نام‌های حاوی `TenantId` حفظ شوند یا در PR جدا تغییر نام یابند؟

| معیار | الف) حفظ در طول مهاجرت | ب) تغییر نام در Migration مستقل | ج) حفظ دائمی فیزیکی + نام منطقی `CompanyId` در کد |
|---|---|---|---|
| **امنیت** | بدون اثر مستقیم؛ نام گمراه‌کننده برای DBA | بدون اثر مستقیم؛ نام درست | مانند الف اما دائمی؛ با قاعدهٔ مستند کاهش می‌یابد |
| **سازگاری** | کامل با نسخه‌های قدیمی و Rollback | نسخهٔ قدیمی که نام قید را در SQL دستی/اسکریپت دارد می‌شکند؛ EF خودش نام قید را در Query به‌کار نمی‌برد | کامل |
| **هزینه** | صفر | بالا: عملیات تازه در Guard (Allowlist قید)، `HAND_WRITTEN_SQL`، Mutation، اجرای SQL Server، یک Migration | کم: یک قاعدهٔ مستند |
| **پیچیدگی** | کم؛ ولی تعارض نام با قیدهای Tenant واقعی را باید با Pin نام متمایز حل کرد (1913 اجرا شد) | بالا (هم‌زمانی تغییر Pin و نام فیزیکی؛ ترتیب با Rename ستون) | کم |
| **اثر بر نسخه‌های قدیمی** | هیچ | ناسازگاری احتمالی با ابزار/اسکریپت خارجی | هیچ |
| **Rollback** | بی‌نیاز | `sp_rename` معکوس؛ Identity حفظ می‌شود (D1c) ولی Guard و Down جدید لازم است | بی‌نیاز |
| **ریسک** | بدهی ظاهری؛ تعارض نام با Tenant واقعی اگر نام‌گذاری متمایز نشود | شکست Migration روی ابزار/کار خارجی؛ پنجرهٔ قفل | بدهی دائمی؛ ابزار DBA گمراه می‌شود |

**هزینهٔ مخفی مهم (همهٔ گزینه‌ها):** پس از Rename، یک ستون واقعی جدید `TenantId` روی همان جدول‌ها اضافه می‌شود (OD-18). Index/AK پیش‌فرض آن همنام قیدهای legacy حفظ‌شده می‌شود (مثلاً `IX_FiscalPeriods_TenantId_Status`). پس در الف و ج نام قیدهای Tenant واقعی باید **صریحاً و متفاوت Pin شوند**؛ این باید در تست SQL Server پیش از PR-4 اثبات شود.

**توصیه (پیشنهاد؛ تصمیم با مالک):** الف در طول مهاجرت، سپس ج به‌عنوان وضعیت دائمی با ثبت قاعدهٔ نام‌گذاری در `docs/DATABASE.md`. ب فقط با دلیل عملیاتی مشخص (درخواست DBA/مشتری) و پس از پایان کامل مهاجرت. دلیل: هزینه و ریسک ب با فایدهٔ ظاهری آن نمی‌خواند و Guard فعلی آن را نمی‌پذیرد.

**NotRun:** اثر تغییر نام قید روی ابزارهای خارجی مشتری قابل اندازه‌گیری نیست؛ اجرای ب روی دیتابیس با حجم واقعی انجام نشده.

# OD-16 — سیاست استقرار چندنمونه‌ای (Shared)

**سؤال:** در Shared Deployment، مسئول اجرای Migration کیست و ترتیب استقرار چیست؟

| معیار | الف) اپراتور پیش از انتشار | ب) یک نمونهٔ کنترل‌شده | ج) Deployment Pipeline |
|---|---|---|---|
| **قفل همزمانی** | `--migrate` با `sp_getapplock`؛ اجرای دوم کد ۳ (اجرای واقعی) | همان قفل؛ ولی انتخاب «کدام نمونه» به پیکربندی/Leader نیاز دارد که وجود ندارد | همان قفل؛ Pipeline باید کد ۳ را شکست بداند |
| **مجوز** | اپراتور با مجوز جدا (G5) | نمونه باید اعتبار DDL داشته باشد (اعتبار دائمی برنامه ≠ اعتبار Migration) | Secret دیتابیس مشتری در Pipeline؛ مجوز و محدودهٔ آن باید تعریف شود |
| **Backup** | گیت دستی قبل از اجرا | بدون گیت خودکار؛ خطرناک | قابل خودکارسازی ولی ساخته نشده |
| **Recovery** | بازیابی Backup + اجرای مجدد از مرحلهٔ ناموفق (تست #665) | همان؛ ولی نمونه‌های دیگر با کد قدیمی روی Schema ناقص | همان |
| **شکست جزئی** | کد ۲ (Core موفق، Trade ناموفق) و ادامه از مرحلهٔ شکست‌خورده؛ Trade بدون Core شروع نمی‌شود | مانند الف؛ ولی نمونه‌های در حال اجرا ممکن است نیمه‌کاره بخوانند | مانند الف |
| **ثبت Audit** | امروز فقط خروجی کنسول/Runbook؛ ممیزی پیاده نیست | همان | Pipeline Log (خارج از دیتابیس) |
| **سازگاری با Production فعلی** | کامل | **ناسازگار**: Production روی دیتابیس موجود خودکار Migrate نمی‌شود (طراحی عمدی) | نیازمند زیرساخت جدید |
| **هزینه/پیچیدگی** | کم | متوسط/بالا (Leader، پیکربندی، تغییر رفتار Production) | بالا (Pipeline، Secret، Audit) |

**ناسازگاری ذاتی با نمونه‌های قدیمی (مستقل از گزینه):** Rename فیزیکی ستون و NOT NULL نسخهٔ قدیمی را می‌شکنند (D-091؛ تست PR-D: `ALTER COLUMN`/`sp_rename` روی ستون وابسته). برنامه هنگام شروع فقط هشدار Pending می‌دهد و ناسازگاری را نمی‌گیرد. پس در Shared باید **همهٔ نمونه‌ها متوقف، Migration یک‌بار اجرا، سپس نمونه‌های نسخهٔ جدید شروع شوند.** مراحل Expand-only (P، ستون nullable) بدون توقف ممکن است.

**توصیه (پیشنهاد؛ تصمیم با مالک):** الف با گیت‌ها: Backup تأییدشده ← توقف نمونه‌ها (برای مراحل ناسازگار) ← یک `--migrate` (با `--include-trade` فقط طبق D-094) ← بررسی کد خروج ← ثبت رکورد عملیاتی ← شروع نسخهٔ جدید ← تأیید. ج بعد از وجود رویهٔ Secret/Audit؛ ب رد.

**NotRun:** رویهٔ توقف/شروع چندنمونه‌ای واقعی با چند فرایند Server و دیتابیس مشترک اجرا نشده؛ فقط قفل و شکست جزئی روی Host آزموده شده. Audit اجرای Migration و Backup خودکار وجود ندارد.
