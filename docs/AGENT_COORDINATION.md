# گردش کار هماهنگی چند Agent

## هدف
Codex، Copilot و Agentهای دیگر می‌توانند در یک مخزن مشارکت کنند، اما Git باید منبع حقیقت باشد. حافظه گفت‌وگو یا خلاصه تولیدشده توسط یک Agent، جای فایل‌های ثبت‌شده در مخزن را نمی‌گیرد.

## قواعد هماهنگی
0. **نقطه شروع:** `docs/INDEX.md`. ترتیب منابع حقیقت و واژگان وضعیت (`Accepted`/`Implemented`/`Verified`/`Proposed`/`NeedsApproval`/`Deprecated`/`Blocked`/`NotImplemented`) در D-030 است؛ قابلیت لایسنس/زیرسیستم را `Implemented` فرض نکن (همه `NotImplemented`‌اند). ADR جدید از D-031 شروع می‌شود؛ شماره‌های موجود را تغییر نده.
1. **یک وظیفه = یک Issue = یک شاخه = یک PR.** نام شاخه پیشنهادی: `agent/<issue-number>-<short-name>`.
2. **یک مالک ادغام تعیین کن.** فقط مسئول ادغام یا Maintainer، PRها را بازبینی و merge کند.
3. **از اجرای موازی روی یک working tree مشترک اجتناب کن.** Agentهای هم‌زمان باید شاخه‌ها/working treeهای جداگانه داشته باشند و فایل‌های هم‌پوشان را هماهنگ کنند.
4. **کار بعدی از Git شروع می‌شود.** Agent بعدی ابتدا مستندات و کد فعلی را از شاخه هدف بخواند؛ به پیام تحویل به‌تنهایی اعتماد نکند.
5. **تغییرات کوچک و مستقل باشند.** تغییر هم‌زمان معماری، احراز هویت، دیتابیس و UI در یک PR، مگر با ضرورت مستند، ممنوع است.
6. **هر تحویل باید قابل بازتولید باشد.** Issue، شاخه، commit، PR، فایل‌ها، تصمیم‌ها، تست‌های اجراشده/نشده، ریسک‌ها و کار بعدی ثبت شود.
7. **عدم قطعیت را صریح ثبت کن.** اگر build، تست، SQL Server یا مرورگر در دسترس نیست، نتیجه را «اجرا نشده» بنویس، نه موفق.
8. **هیچ Agentی خودسرانه کار دیگری را بازنویسی نکند.** قبل از تغییر فایل‌های مشترک یا حل تعارض، diff و مالکیت تغییر را بررسی کند.
9. **مستندات وضعیت را دقیق نگه دار.** `WORK_LOG.md` تاریخچه افزایشی است؛ `PROJECT_STATUS.md` فقط وضعیت تأییدشده را نشان می‌دهد؛ `REPOSITORY_AUDIT.md` یافته‌های بررسی و محدودیت‌ها را نگه می‌دارد.
10. **عدم وابستگی خارجی زمان اجرا.** فایل‌های CSS/JS/فونت/آیکون باید محلی باشند؛ لینک CDN جدید پذیرفته نیست.

## چرخه یک وظیفه
1. انتخاب Issue و معیارهای پذیرش.
2. مطالعه `AGENTS.md` و اسناد مرتبط؛ بررسی وضعیت Git.
3. نوشتن برنامه کوتاه و شناسایی ریسک‌ها.
4. پیاده‌سازی محدود به Issue.
5. اجرای تست‌های مرتبط و کنترل دارایی‌های استاتیک.
6. بازبینی diff، اجرای `git diff --check` و بررسی نبود secret/فایل تولیدی.
7. تکمیل handoff و ثبت خلاصه در `WORK_LOG.md`.
8. بازکردن PR با شواهد تست و محدودیت‌ها.
9. بازبینی مستقل و ادغام توسط Maintainer.
10. Agent بعدی از وضعیت به‌روز شاخه اصلی شروع می‌کند.

## جلوگیری از تداخل
- برای فایل‌هایی که دو Issue به آن‌ها نیاز دارند، یک Issue مالک تغییر مشترک باشد یا تغییرات به ترتیب ادغام شوند.
- اگر PR پایه تغییر کرده، قبل از ادامه شاخه را به‌روز کن و تست‌ها را دوباره اجرا کن.
- هنگام conflict، تغییرات را بدون بررسی معنا انتخاب نکن؛ هیچ‌وقت برای رفع conflict، تغییر کاربر را کورکورانه حذف نکن.
- اگر معیار پذیرش یا تصمیم معماری مبهم است، متوقف شو و سؤال/Issue بگذار؛ حدس نزن.

## تقسیم کار بین Subagentهای Claude Code
**وضعیت: `Accepted` به‌عنوان رویهٔ کاری** (دستور کارفرما، 2026-10-22؛ PR #50، ادغام‌نشده). این یک رویهٔ کاری است، نه ADR، و ادعای «بهینه‌بودن اثبات‌شده» نیست؛ در این پروژه هنوز اندازه‌گیری نشده است. منبع اصلی متن، بخش «قاعدهٔ الزامی تقسیم کار بین Agentها» در `CLAUDE.md` است و در صورت اختلاف همان مرجع است. این بخش فقط مخصوص Claude Code است و جایگزین قواعد عمومی بالا (مثلاً مالکیت فایل و یک شاخه برای هر Issue) نیست.

### الف) سطح تقسیم بر اساس اندازهٔ کار
| اندازه | روش |
|---|---|
| خیلی کوچک (تایپو، یک متن، تنظیم جزئی تک‌فایلی) | مستقیم توسط Lead؛ بدون Subagent، چون هر Agent زمینه را از نو می‌خواند |
| متوسط (یک قابلیت متصل: سرور + کلاینت + تست) | یک Agent پیاده‌ساز برای کل برش عمودی (نه چند Agent جدا) + بازبینی مستقل |
| بزرگ یا حساس (Schema، احراز هویت، Multi-Tenancy، چند برش مستقل) | `architect` برای طرح، سپس پیاده‌سازی، سپس بازبینی‌های مستقل |

### پ) پروتکل جلوگیری از ناهماهنگی
1. **قرارداد اول:** Lead پیش از فراخوانی هر Agent، قرارداد مشترک (شکل API، نام فیلدها، قواعد دامنه، معیارهای پذیرش) را می‌نویسد؛ Agent قرارداد را تغییر نمی‌دهد و نیاز به تغییر را گزارش می‌کند.
2. **ابلاغ کامل:** Agent سابقهٔ گفتگو را نمی‌بیند؛ پرامپت باید هدف، قرارداد، فایل‌های مالک، فایل‌های ممنوع، معیار پذیرش، فرمان‌های تست و ارجاع به `AGENTS.md` داشته باشد.
3. **مالکیت فایل:** هر فایل در هر لحظه یک مالک دارد؛ کارهای وابسته پشت‌سرهم و فقط کارهای مستقل بدون فایل مشترک هم‌زمان اجرا شوند (قاعده ۳ بالا).
4. **تلفیق توسط Lead:** پس از هر Agent، Lead Diff را با قرارداد می‌سنجد؛ پس از همهٔ Agentها یک Build و Test کامل یکپارچه اجرا می‌شود.
5. **بازبین فقط‌خواندنی:** `code-reviewer` برای هر تغییر عادی؛ `security-reviewer` و `architect` علاوه بر آن فقط برای تغییر حساس. بازبین‌ها کد را تغییر نمی‌دهند؛ اصلاح با Agent پیاده‌ساز است.
6. **شاهد، نه گفته:** گزارش Agent شاهد نیست؛ نتیجهٔ Build/Test از خروجی واقعی گرفته می‌شود و هرچه اجرا نشده «اجرا نشد» ثبت می‌شود.
7. **یک شاخه:** همهٔ Agentها روی شاخهٔ همان Issue کار می‌کنند؛ Commit/Push/Merge بدون تأیید صریح ممنوع است.

### ث) دروازهٔ بازبینی پیش از PR
پیش از ایجاد PR برای کار تقسیم‌شده، Lead بازبینی نهایی می‌کند و تا پایان آن PR ساخته نمی‌شود. دامنه: فقط Diff نهایی و خروجی واقعی Build/Test (نه بازخوانی کل کار). عمق به نسبت ریسک: کار ساده را خود Lead می‌خواند؛ کار عادی `code-reviewer`؛ کار حساس (احراز هویت، Tenant، Schema، ورودی کاربر، اسرار) با افزودن `security-reviewer` و `architect` (opus). «بازبین قوی» یعنی فراخوانی Agent با مدل opus، نه تغییر مدل جلسهٔ Lead. یافتهٔ مهم توسط Agent پیاده‌ساز اصلاح می‌شود و فقط همان بخش دوباره بازبینی می‌شود. سطح بازبینی و یافته‌ها در گزارش پایانی و handoff ثبت می‌شود. متن مرجع: `CLAUDE.md`.

### ت) اندازه‌گیری
Lead در گزارش پایانی هر کار تقسیم‌شده می‌نویسد: کدام Agent چه کرد، چند توکن مصرف کرد (عددی که ابزار Agent گزارش می‌دهد؛ در نبود آن «نامشخص»)، چند رفت‌وبرگشت لازم شد و آیا تقسیم کار صرفه داشت. تا کنون داده‌ای برای تأیید یا رد صرفهٔ این رویه در این پروژه جمع نشده است.

### چرا همه‌چیز با بالاترین مدل نه
- **مزایای استفاده از بالاترین مدل برای همه‌چیز:** ناهماهنگی کمتر (یک مدل، یک برداشت از قرارداد) و کیفیت بهتر در کار دشوار.
- **معایب:** هزینهٔ چند برابر، کندی، سود ناچیز در کار ساده، و پرشدن سریع‌تر زمینه.
- **راه میانهٔ توصیه‌شده:** مدل جلسهٔ قوی برای تصمیم و تلفیق؛ کارهای حجیم/تکراری به مدل ارزان‌تر؛ فقط کار حساس به بالاترین مدل.
- **محدودیت‌ها:** Claude نمی‌تواند مدل جلسه را وسط کار عوض کند و مدل جلسه را کارفرما/تنظیمات تعیین می‌کند. این توصیه‌ها بر اساس رویهٔ عمومی است و در این پروژه هنوز اندازه‌گیری نشده است.
