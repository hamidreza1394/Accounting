# طراحی مالکیت دیتابیس و محدودسازی مقصد SQL در Provisioning توسعهٔ Vendor

- **تاریخ:** 2026-11-27
- **Issue:** #802 (بخش PR-1؛ ادامهٔ Issue #797 / PR #800)
- **وضعیت:** پیاده‌سازی‌شده در شاخه؛ تا CI و اجرای واقعی روی SQL Server، `Implemented / Not yet Verified`. تصمیم معماری در DECISIONS.md با شناسهٔ D-122 به‌صورت `Proposed` ثبت شده است و تا تأیید مالک، وضعیت تصمیم تغییر نمی‌کند.

## مسئله

جریان راه‌اندازی خودکار دیتابیس Vendor باید روی ماشین توسعهٔ اپراتور، دیتابیس مستقل Vendor را بسازد و Migrationهای موجود را اجرا کند، بدون آنکه:

- دیتابیسی که برای هدف دیگری (از جمله دیتابیس خالی Customer) ساخته شده، تصاحب شود؛
- Migration روی دیتابیس ناشناس اجرا شود؛
- صفحهٔ Development به ابزار اجرای SQL علیه میزبان‌های دلخواه یا شبکهٔ داخلی تبدیل شود؛
- توقف فرآیند بین `CREATE DATABASE` و ثبت نشانهٔ مالکیت، یک دیتابیس یتیم و بی‌صاحب پشت سر بگذارد.

## تصمیم طراحی

### ۱) اعتبارسنجی نام دیتابیس و شناسهٔ SQL (`VendorDatabaseName` / `VendorSqlIdentifier`)

قواعد تأییدشدهٔ مسیر مشتری حفظ می‌شود: حرف/رقم/`_`/`-`/`.`/فاصلهٔ میانی؛ بدون نویسهٔ کنترلی یا قالب‌بندی (ZWNJ)؛ بدون نقطه/فاصلهٔ ابتدا-انتها و `..` متوالی؛ حداکثر ۱۲۳ نویسه (تا نام فایل `_log` در حد ۱۲۸ نویسهٔ SQL Server بماند)؛ نرمال‌سازی NFKC و رد نام‌های سیستمی و هم‌ریخت (مثل «ｍａｓｔｅｒ»). نام تأییدشده فقط با Bracket-quote (و escape سهوی `]`) به SQL می‌رود؛ هیچ ورودی خام الحاق نمی‌شود.

### ۲) محدودسازی مقصد SQL (`VendorSqlServerTarget`)

- شکل‌های پذیرفته‌شده: `host`، `host[,port]`، `host\instance[,port]` و پیشوند `tcp:`؛ بقیهٔ شکل‌ها رد می‌شوند.
- مقصد پیش‌فرض فقط مقصدهای محلی است: `localhost`، `127.0.0.1`، `::1`، `.`، `(local)`، `(localdb)` و نام خودِ ماشین.
- IP غیر-loopback فقط از طریق Allow-list دقیق مجاز می‌شود؛ Lookup با مقایسهٔ کامل نام است و wildcard (`*`، `?`، `%`) چه در ورودی و چه در خودِ Allow-list هرگز گسترش نمی‌دهد.
- میزبان‌های اضافه فقط از `FARANO_VENDOR_Development__Provisioning__AllowedSqlHosts` (محیط) یا کلید پیکربندی `Faranou:Development:Provisioning:AllowedSqlHosts` خوانده می‌شود؛ هیچ نام ماشینی در کد Hardcode نشده است.
- DNS rebinding/SSRF در حد این ابزار: ابزار Development روی ماشین اپراتور است، فقط مقصد Allow-list دقیق (نام، نه IP محاسبه‌شده) می‌پذیرد و هیچ endpoint عمومی SQL Execution وجود ندارد؛ ریسک باقی‌مانده فقط اتصال به همان مقصد ثبت‌شدهٔ مالک است که آگاهانه در Allow-list گذاشته شده.

### ۳) نشانهٔ مالکیت (`VendorOwnershipMarker`)

- Extended Property سطح دیتابیس با نام `FaranouVendorOwnership` و مقدار ثابت Vendor؛ نوشتن آن فقط از مسیرهای دارای اثبات مالکیت انجام می‌شود.
- خواندن سه‌حالته است: `Valid` (نام + مقدار دقیق)، `InvalidValue` (نشانهٔ جعلی/خارجی) و `Absent`. **نشانهٔ جعلی Fail Closed می‌شود** حتی اگر تاریخچهٔ Migration فارنو هم وجود داشته باشد، چون ناسازگاری نشانه یعنی شخص دیگری دیتابیس را ادعا یا دستکاری کرده است.
- تصمیم مالکیت تابع خالص و تست‌شده است: Marker معتبر ⇒ پذیرش؛ تاریخچهٔ Migration اعمال‌شدهٔ فارنو بدون نشانه ⇒ پذیرش (دیتابیس‌های قدیمی) و Backfill نشانه؛ هر حالت دیگر (جدول بدون نشانه، تاریخچهٔ خالی، دیتابیس خالی بی‌نشان) ⇒ رد با پیام فارسی قابل اقدام. **هیچ مسیری DROP یا بازسازی انجام نمی‌دهد.**

### ۴) پنجرهٔ شکست و Recovery کنترل‌شده (`VendorProvisioningIntent`)

اگر فرآیند بین `CREATE DATABASE` و نوشتن نشانهٔ مالکیت متوقف شود، دیتابیس خالی و بی‌نشان می‌ماند. رفتار طراحی:

1. پیش از CREATE، یک «رکورد قصد راه‌اندازی» به‌صورت Extended Property روی `master` با نام `FaranouVendorProvisioningIntent` و مقدار `VendorDb=<name>;IssuedUtc=<UTC>` ثبت می‌شود.
2. پس از نوشتن موفق نشانهٔ مالکیت، رکورد حذف می‌شود.
3. در اجرای بعدی، دیتابیس همچنان به‌عنوان «ناشناس/بی‌نشان» گزارش می‌شود و **حذف نمی‌شود**؛ اما اگر رکورد قصدِ تازه (≤۲۴ ساعت) دقیقاً هم‌نام آن باشد، این اثبات می‌کند که خودِ این جریان (نه سرویس دیگری) آن را ساخته است و Recovery کنترل‌شده مجاز است: نوشتن نشانهٔ مالکیت و ادامهٔ جریان.
4. بدون رکورد هم‌نام، با رکورد منقضی، با رکورد مربوط به دیتابیس دیگر یا با مقدار خراب، دیتابیس Fail Closed می‌ماند و فقط با تصمیم مدیر سرور قابل بررسی است.
5. اگر دیتابیس هم‌نام رکورد، محتوا (جدول یا تاریخچه) داشته باشد، Recovery رد می‌شود.

### ۵) جایگاه این PR در مجموعهٔ #802

این PR فقط primitives و تصمیم‌های خالص + تست‌ها را تحویل می‌دهد؛ «بازرسی امن، ایجاد امن و قفل عملیات هم‌زمان» در PR-2 (pipeline هفت‌مرحله‌ای) روی همین primitives پیاده می‌شود و «هویت Runtime» در PR-3، «Endpointها و Bootstrap اپراتور» در PR-4 و «UI فارسی» در PR-5 می‌آیند.

## گزینه‌های بررسی‌شده

- **Registro intent در فایل محلی یا Credential Manager:** وابسته به هویت کاربر/محل اجرا است و در جابه‌جایی اجرا با هویت دیگر خوانده نمی‌شود؛ Extended Property روی `master` روی خودِ سرور ماندگار است و به هیچ منبع بیرونی وابسته نیست. رد شد.
- **پذیرش دیتابیس خالی بی‌نشان با تأیید صریح اپراتور:** یک دیتابیس خالی ممکن است Customer باشد؛ تأیید اپراتور مالکیت را اثبات نمی‌کند و ریسک تصاحب را می‌پذیرد. رد شد — فقط Recovery مبتنی بر رکورد قصد.
- **Marker بدون اعتبارسنجی مقدار:** هر کسی می‌توانست Extended Property هم‌نام با مقدار دلخواه بنویسد و مالکیت جعل شود. رد شد — مقدار دقیق اعتبارسنجی می‌شود.

## آزمون

- تست واحد خالص: ماتریس مالکیت (۶ حالت)، ماتریس Recovery، پارس رکورد قصد، اعتبارسنجی نام دیتابیس/Login، Quote شناسه، Allow-list (شکل‌های محلی، ماشین واقعی، Allow-list دقیق، رد wildcard و شکل‌های بد).
- تست SQL گیت‌دار (`FARANO_VENDOR_TEST_SQLSERVER`، فقط اشیای یکتای خودش را می‌سازد و پاک می‌کند): Roundtrip نشانهٔ مالکیت شامل مقدار جعلی، Roundtrip رکورد قصد (ثبت/دسته‌بندی/حذف)، دیتابیس خالی بی‌نشان بدون رکورد ⇒ رد.
