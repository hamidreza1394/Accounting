# طراحی راه‌اندازی خودکار دیتابیس Vendor در Development

- **Issue:** UNNUMBERED (ابزار ساخت Issue در جلسه در دسترس نبود؛ به محض باز شدن، Issue متصل می‌شود)
- **تاریخ:** 2026-11-27
- **وضعیت:** پیاده‌سازی‌شده در شاخه `agent/vendor-db-provisioning`؛ تا CI سبز نشده Verified نیست.
- **ADR:** D-122 در `docs/DECISIONS.md`

## مسئله

صفحهٔ محلی Development (Issue #797 / PR #800) صراحتاً DB نمی‌ساخت و Migration اجرا نمی‌کرد؛ اپراتور باید `VendorDb` را دستی در SSMS می‌ساخت و سپس از فرم، اتصال را آزمون و ذخیره می‌کرد.

## تصمیم طراحی

همان صفحه با یک بخش «راه‌اندازی خودکار دیتابیس» گسترش یافته است (نه رابط دوم). جریان هفت‌مرحله‌ای: اتصال مدیریتی → بررسی وضعیت دیتابیس → ایجاد در صورت نیاز → اجرای مهاجرت‌های موجود → آماده‌سازی دسترسی اجرای محدود → آزمون اتصال اجرا (endpoint موجود `test`) → ذخیرهٔ اتصال اجرا (endpoint موجود `save`). مراحل سمت سرور در چهار endpoint جدا هستند تا هر مرحله مستقلاً قابل تکرار و گزارش باشد.

## مرز امنیت

- همهٔ مرزهای موجود حفظ شده‌اند: فقط Development و ویندوز با پروفایل صریح، فقط loopback، HTTPS محلی، Origin هم‌میزبان، antiforgery، rate limit، هدرهای امنیتی/CSP؛ در حالت برنامهٔ کامل همان سیاست fallback (مدیر MFA).
- **تفکیک هویت:** اطلاعات مدیریتی Provisioning فقط در بدنهٔ درخواست می‌آید و فقط در حافظهٔ همان درخواست استفاده می‌شود؛ هرگز ذخیره، log، بازگردانی به مرورگر یا تبدیل به اتصال اجرا نمی‌شود. اتصال ذخیره‌شده فقط از مسیر موجود (Credential Manager) و فقط برای هویت اجراست.
- **حداقل مجوز اجرا:** گزینهٔ ساخت login اختصاصی SQL با فقط db_datareader/db_datawriter؛ بررسی `IS_SRVROLEMEMBER('sysadmin')` پیش از هر اعطای مجوز و رد fail در صورت عضویت؛ `sa` ممنوع؛ مهاجرت فقط با هویت Provisioning اجرا می‌شود.
- **ایمنی شناسه‌ها و SQL:** شناسه‌ها با regex سخت‌گیرانهٔ ASCII اعتبارسنجی و سمت سرور با QUOTENAME نقل‌قول می‌شوند؛ چون `CREATE DATABASE`/`CREATE LOGIN` پارامترپذیر نیستند، SQL پویا فقط با QUOTENAME (و QUOTENAME(رمز، ''') برای گذرواژه) و با دلیل مستند استفاده شده است. بقیهٔ مقادیر پارامتری هستند.
- **ایمنی دیتابیس هدف:** دیتابیس‌های سیستمی ممنوع؛ اگر دیتابیس موجود جدول‌ها بدون تاریخچهٔ Vendor یا شناسه‌های مهاجرت ناشناخته داشته باشد «بیگانه» است و هیچ تغییری نمی‌پذیرد (تشخیص عمومی؛ نام دیتابیس Customer را هم می‌پوشاند)؛ هیچ drop/recreate وجود ندارد؛ اجرای مجدد ایدمپوتنت است.
- **هم‌زمانی و خطاها:** `sp_getapplock` Exclusive/Session روی دیتابیس هدف؛ خطاهای SQL با شماره به پیام فارسی امن نگاشت می‌شوند و log فقط نوع استثنا/شماره خطا را دارد (بدون connection string یا رمز).
- **قرارداد اتصال:** `FARANO_VENDOR_ConnectionStrings__VendorDb` تنها منبع حقیقت اجرا باقی می‌ماند؛ بدون fallback به Customer؛ بدون نمونهٔ دوم SQL Server.

## گزینه‌های بررسی‌شده

- **CLI جدا:** رابط دوم می‌ساخت و تجربهٔ setup را پراکنده می‌کرد؛ رد شد.
- **استفاده از credential فرم اصلی برای مهاجرت:** نقض تفکیک هویت Provisioning/Runtime؛ رد شد.
- **db_owner برای هویت اجرا:** نقض حداقل مجوز؛ رد شد.
- **تشخیص دیتابیس Customer با نام ثابت:** شکننده و وابسته به نام؛ تشخیص عمومی «بیگانه» جایگزین شد.

## قرارداد endpointها

- `POST /api/development/database-setup/provision/check` — اتصال مدیریتی و طبقه‌بندی دیتابیس (`missing|empty|vendor|foreign`) با شمار مهاجرت‌های اعمال‌شده/باقی‌مانده.
- `POST /api/development/database-setup/provision/create` — ایجاد ایدمپوتنت؛ روی دیتابیس موجود هیچ تغییری نمی‌کند.
- `POST /api/development/database-setup/provision/migrate` — اجرای مهاجرت‌های موجود با IMigrator و تأیید تاریخچه؛ روی دیتابیس بیگانه fail-safe.
- `POST /api/development/database-setup/provision/runtime` — ساخت/اتصال هویت اجرا با حداقل مجوز و تأیید اتصال اجرا.
- خطای هر مرحله → HTTP 400 با پیام فارسی امن؛ موفقیت → HTTP 200 با جزئیات مرحله.

## مواردی که پس از پیاده‌سازی باید بررسی شوند

Vendor CI روی PR باید Restore/Build/Test کامل (شامل تست‌های یکپارچگی SQL با SQL Server موقت) و `has-pending-model-changes` را سبز کند. اجرای واقعی این جریان روی یک نمونهٔ SQL Server واقعی توسعه (Windows) آزمون دستی اپراتور است و در CI ادعا نمی‌شود.
