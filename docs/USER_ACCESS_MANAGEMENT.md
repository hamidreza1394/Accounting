# مدیریت یکپارچه کاربران، ساختار سازمانی و دسترسی‌ها

- Issue: #444
- وضعیت: S0 تکمیل‌شده؛ S1 در حال اجرا. PRهای #445 و #447 ادغام شده‌اند؛ #449 رابط self-service آماده بازبینی است؛ #450 API فهرست/جزئیات و #451 رابط فهرست/جزئیات در حال توسعه‌اند.
- اصل تغییر: ابتدا استفاده مجدد از مدل موجود؛ هیچ Migration یا موجودیت جدید پیش از تکمیل ممیزی و تصمیم داده‌ای.

## 1. هدف
ایجاد مرکز مدیریت هویت و دسترسی برای نصب فرانو. مدیر مجاز بتواند کاربران را جستجو و مدیریت کند، سمت‌ها و گروه‌های دسترسی بسازد و مجوزها را تا سطح فرم و عملیات تنظیم کند. کاربر عادی فقط پروفایل، امنیت حساب و سوابق ورود خودش را ببیند.

## 2. منوی نهایی مدیریت سیستم
صفحات تخصصی در منوی مستقل مدیریت سیستم قرار می‌گیرند؛ فرم کاربر فقط خلاصه و میانبر مدیریت تخصیص‌های همان کاربر را ارائه می‌کند.

| آیتم | مسئولیت |
|---|---|
| مدیریت کاربران | جستجو، فهرست صفحه‌بندی‌شده، ایجاد/ویرایش، وضعیت حساب و جزئیات |
| ساختار سازمانی و سمت‌ها | واحدها، سمت‌ها، مدیر مستقیم و ارتباط با پرسنل |
| گروه‌های دسترسی | الگوهای حسابدار، خزانه‌دار، انباردار و گروه سفارشی |
| کاتالوگ و جزئیات مجوزها | درخت زیرسیستم/منو/فرم/عملیات و ماتریس مجوزها |
| گزارش امنیت و سوابق | ورود/خروج، نشست‌ها و تغییرات دسترسی |
| سیاست‌های امنیتی | سیاست رمز، MFA، قفل و نشست؛ فقط پس از ممیزی قابلیت فعلی |

### موارد حذف یا ادغام
- «لیست کاربران فعال» صفحه مستقل نیست؛ فیلتر داخل مدیریت کاربران است.
- «مشاهده ورود و خروج کاربران» به گزارش امنیت و تب سوابق ورود کاربر منتقل می‌شود.
- «مدیریت دسترسی‌ها» به دو مسئولیت گروه‌های دسترسی و کاتالوگ/ویرایشگر مجوز تقسیم می‌شود.
- هیچ لینک نمایشی نباید به صفحه یا API ناموجود متصل شود؛ تا آماده‌شدن مسیر واقعی، آیتم با برچسب در حال آماده‌سازی غیرفعال می‌ماند.

## 3. تجربه کاربری
### مدیریت کاربران
- فهرست سمت راست در RTL و پنل جزئیات در بخش اصلی.
- جستجوی server-side روی نام، نام کاربری، شماره پرسنلی، ایمیل و موبایل.
- فیلتر وضعیت، شرکت، نقش/گروه، زیرسیستم، MFA و آخرین ورود.
- صفحه‌بندی، مرتب‌سازی، حفظ فیلترها و نمایش تعداد نتایج.
- عملیات فقط بر اساس مجوز مؤثر مدیر نمایش داده شوند.
- پیمایش اولین/قبلی/بعدی/آخرین فقط روی نتایج فیلترشده.
- کاربر عادی هیچ فهرست، جستجو، انتخاب شناسه یا پیمایش بین کاربران ندارد.

### تب‌های فرم کاربر
1. مشخصات پرسنلی: تصویر، شماره پرسنلی، شناسه پایدار EmployeeId، نام، واحد، سمت، مدیر مستقیم، وضعیت همکاری و اطلاعات تماس.
2. حساب و امنیت: نام کاربری، وضعیت فعال/قفل/انقضا، تأیید تماس، MFA، الزام تغییر رمز و نشست‌ها. رمز و hash هرگز خوانده/نمایش داده نمی‌شود.
3. شرکت‌های مجاز: عضویت، نقش شرکتی، تاریخ اعتبار و محدوده‌های مجاز.
4. زیرسیستم‌ها: وضعیت دسترسی با تفکیک entitlement مشتری از مجوز عملیاتی کاربر.
5. گروه‌ها و مجوزها: گروه‌های تخصیص‌یافته، مجوز مؤثر، منبع مجوز، تخصیص مستقیم و لینک ویرایشگر جزئی.
6. سوابق ورود و خروج: رویدادهای احراز هویت و نشست.
7. سوابق تغییرات: رویدادهای مدیریتی و تغییر داده/مجوز؛ مستقل از login history.

### Self-service
کاربر غیرمدیر فقط داده‌های خودش را می‌بیند و فقط مجاز به تغییر رمز خودش و پروفایل محدود است. API شناسه کاربر را از هویت احراز‌شده استخراج می‌کند، نه از پارامتر ورودی.

## 4. سمت‌ها و واحدهای سازمانی
سمت سازمانی جایگاه شغلی است و مجوز امنیتی نیست. واحد سازمانی ساختار گزارش‌دهی را بیان می‌کند. هر سمت می‌تواند گروه‌های دسترسی پیشنهادی داشته باشد، اما انتساب مجوز فقط با سیاست صریح و تأیید مدیر انجام می‌شود. تغییر سمت نباید مجوزهای قبلی را کورکورانه با مجوزهای جدید جمع کند.

## 5. گروه‌های دسترسی
گروه دسترسی یک الگوی قابل استفاده مجدد است؛ نمونه‌ها: حسابدار، حسابدار ارشد، خزانه‌دار، مسئول انبار، کارشناس فروش و کارشناس بازرگانی خارجی.

قابلیت‌ها: ایجاد، کپی، نسخه‌بندی، فعال/غیرفعال‌سازی، مشاهده اعضا، انتخاب الگوی پایه، اصلاح مجوزها، پیش‌نمایش کاربران و مجوزهای متأثر، اعمال کنترل‌شده و ثبت Audit. تخصیص موقت با تاریخ شروع/انقضا و دلیل می‌تواند در مرحله بعد اضافه شود.

سمت و گروه دسترسی دو مفهوم مستقل‌اند؛ عنوان شغلی حسابدار الزاماً به معنی گروه مجوزی حسابدار نیست.

## 6. کاتالوگ و ویرایشگر مجوز
کاتالوگ مجوزها پایدار، کددار و تحت کنترل نسخه است؛ مدیر نمی‌تواند مجوزی بسازد که endpoint/عملیات واقعی ندارد.

ساختار نمایشی: زیرسیستم ← منو ← فرم ← عملیات. ویرایشگر سه نما دارد:
- درختی برای پیمایش ساختار.
- جدولی/ماتریسی برای مقایسه عملیات.
- جستجوی سریع بر اساس عنوان و کد مجوز.

عملیات بر اساس ماهیت فرم تعریف می‌شوند؛ همه فرم‌ها الزاماً CRUD یکسان ندارند. نمونه‌ها: List، View، Create، EditDraft، DeleteDraft، Submit، Approve، Reject، Post، Reverse، Print، Export و Manage. عملیات حساس مانند ابطال، ثبت قطعی، مشاهده اطلاعات محرمانه و مدیریت امنیتی با هشدار و کنترل مجزا ارائه می‌شوند.

برای هر مجوز مؤثر، منبع (گروه/نقش/تخصیص مستقیم)، شرکت و محدوده، وضعیت نهایی و دلیل محدودیت نمایش داده شود. پیش‌نمایش تغییرات قبل/بعد الزامی است.

## 7. مدل امنیت و مجوزدهی
الگوی هدف ترکیبی از RBAC و کنترل محدوده داده است:
- RBAC: CompanyRole، RolePermissions و الگوهای دسترسی.
- Scope/ABAC: شرکت، شعبه/واحد/انبار/مرکز هزینه و شرایط رکورد، فقط در صورت پشتیبانی واقعی دامنه.

### مدل موجود برای بازاستفاده
- Users و Role سراسری legacy
- Permission و ApplicationHandler قدیمی (ارتباط Role → Permission → ApplicationHandler)
- UserCompanyMemberships
- CompanyRoles
- PermissionDefinitions
- CompanyRolePermissions
- CompanyAccessService
- LoginLogs
- SecurityAuditEvents

دو مسیر موجود از هم مستقل‌اند: Users.RoleId به Domain.Role سراسری اشاره می‌کند و UserCompanyMemberships به CompanyRole شرکتی با کلید مرکب RoleId/TenantId متصل است. تفکیک scope مدیر سراسری نصب از مدیر شرکتی در D-064 به‌صورت Proposed ثبت شده است. Role قدیمی به Permission و آن به ApplicationHandler وصل است؛ اما جستجوی call-siteهای تولیدی نشان نداد که این Permissionها در runtime برای مجوزدهی endpoint یا handler بررسی شوند. ApplicationHandler نیز از PageModelهای Razor با RouteFinder کشف می‌شود و پوشش APIهای React را ندارد. بنابراین این ساختار فعلاً کاتالوگ/داده legacy است، نه مرجع امنیتی قابل اتکا. CompanyRolePermissions/PermissionDefinitions در CompanyAccessService و Trade واقعاً enforce می‌شوند. از ادغام بی‌بررسی یا ساخت موتور موازی پرهیز شود؛ برای مدیریت سراسری نصب، مرز مجوز جداگانه باید در ADR تعیین شود. اگر AccessGroup صرفاً الگوی بسته‌بندی نقش‌های موجود است، بدون نیاز به موجودیت مستقل مدل شود؛ اگر نسخه‌بندی/مالکیت/تخصیص آن نیاز داده‌ای جدید می‌خواهد، ADR و طرح داده جدا لازم است.

### تفکیک scope پیشنهادی (D-064 — Proposed)
- مدیر سیستم سراسری با Role.Admin می‌تواند همه حساب‌های همان نصب را مدیریت کند؛ در API جدید نقش فعال باید از DB بررسی شود، نه Claim قدیمی.
- مدیر شرکتی فقط کاربران دارای عضویت در همان Company و مجوزهای CompanyRole را مدیریت می‌کند.
- CompanyRole خودِ گروه دسترسی شرکتی است؛ فعلاً AccessGroup جدا نمی‌سازیم.
- سمت/واحد سازمانی مستقل از مجوز است و در S2 مدل می‌شود.

### قواعد قطعی
- Company در مدل فعلی همان مرز Tenant است؛ Tenant entity جدید نسازید.
- TenantId/CompanyId ارسالی کلاینت یا Claim مرجع مجوز داده نیست؛ عضویت و مجوز از CompanyAccessService و دیتابیس معتبر بررسی شود.
- UserId هدف در self-service از هویت احراز‌شده استخراج شود.
- لایسنس با مجوز عملیاتی کاربر متفاوت است. بخشی از customer-side license import/signature/revocation در کد موجود است، اما Trade فعلاً از DenyAllTradeModuleEntitlement استفاده می‌کند؛ entitlement مؤثر زیرسیستم هنوز به مجوزدهنده فعال و آزمون‌شده متصل نیست. این Issue فقط قرارداد اتصال را بررسی می‌کند و entitlement جعلی ایجاد نمی‌کند.
- FiscalPeriod از Core مشترک باقی می‌ماند؛ دوره مستقل برای زیرسیستم ساخته نمی‌شود.
- کنترل‌ها fail-closed، عملیات تغییردهنده دارای Anti-forgery و Audit.
- خودافزایی نقش/مجوز و تفویض اختیاراتی که مدیر خودش ندارد ممنوع.
- گروه شرکتی به‌تنهایی مجوز داده‌ای ایجاد نمی‌کند؛ تصمیمات D-033..D-035 رعایت شوند.

## 8. سوابق و امنیت حساب
مدل User فعلی شامل نام، نام خانوادگی، ایمیل، موبایل، نام کاربری و فیلدهای وضعیت/تأیید است؛ بنابراین UserProfile جداگانه یا EmployeeId/Position جدید فقط پس از بررسی کامل مدل و نیاز اتصال Payroll پیشنهاد می‌شود. LoginLog فعلی فقط UserId و IP را نگه می‌دارد و در مسیر ورود موفق ساخته می‌شود؛ شکست‌های ورود در SecurityAuditEvents ثبت می‌شوند (برای نام کاربری ناشناخته UserId می‌تواند null باشد). Logout API فعلی فقط کوکی و work-context را پاک می‌کند و رویداد خروج/نشست ثبت نمی‌کند. SecurityAuditEvent شامل UserId/TenantId، نوع رویداد، نوع/شناسه موجودیت، زمان UTC، CorrelationId، IP و DetailsJson است. این ساختار برای رخدادهای Audit مفید است، اما بدون قرارداد event و lifecycle نشست نباید از آن duration یا logout استنتاج کرد.

رویدادهای موردنیاز: ورود موفق/ناموفق، خروج صریح، انقضای نشست، ابطال توسط مدیر و پایان نامشخص نشست. نباید خروج قطعی یا مدت نشست را از داده ناقص حدس زد. Audit Trail مستقل از Login History است و تغییر نقش، مجوز، عضویت و وضعیت حساب را ثبت می‌کند. رمز، hash، token یا secret در Audit/Log ممنوع است. IP و metadata دستگاه نیازمند دسترسی محدود و retention مشخص‌اند.

### وضعیت self-service حساب شخصی (پس از PR #447 و #449)
APIهای GET /me/profile، GET /me/login-history و POST /me/password در PR #447 ادغام شده‌اند. UI سه‌تب مشخصات، امنیت و سوابق ورود در PR #449 آماده بازبینی است. UserId فقط از principal استخراج می‌شود و رمز/hash در DTO خروجی نیست. صفحه‌های Razor قدیمی تا جایگزینی کامل حفظ می‌شوند.

## 9. قرارداد API و فرانت‌اند
API هم‌مبدأ با Cookie HttpOnly و Anti-forgery موجود حفظ شود؛ توکن نشست در localStorage ذخیره نشود. DTO از Entity جدا، جستجو/صفحه‌بندی سمت سرور، CancellationToken، پاسخ‌های 401/403/404 و authorization server-side رعایت شوند.

فرانت‌اند React + TypeScript strict + Tailwind/shadcn، RTL و دارایی محلی است. حالت‌های loading/empty/error/forbidden/success لازم‌اند. پنهان‌سازی دکمه صرفاً UX است و کنترل واقعی در API انجام می‌شود. API client از الگوی anti-forgery موجود پیروی کند.

نکته: App.tsx در ممیزی اولیه جریان تک‌صفحه‌ای دارد و routing مستقل آن باید بررسی شود؛ href به صفحات ناموجود اضافه نشود. AppShell فعلی فقط /app/ را route فعال می‌کند و زیرمنوی تنظیمات سیستم placeholder است.

## 12. ریسک‌ها و خارج از دامنه
- Users.RoleId و CompanyRole هم‌زمان وجود دارند؛ یکپارچه‌سازی بدون tracing ممکن است رفتار فعلی را بشکند.
- LoginLog فعلی چرخه عمر نشست را پوشش نمی‌دهد.
- routing فعلی ClientApp باید پیش از فعال‌سازی لینک‌ها بررسی شود.
- نقش قدیمی Admin در claims از Role.Name برای کاربران و به‌صورت ثابت برای Infrastructure master صادر می‌شود؛ صفحات Razor مدیریت کاربران همه Users را بدون فیلتر شرکت فهرست می‌کنند. قبل از جایگزینی این صفحات، محدوده مدیر سراسری و مدیر شرکتی باید صریح و با تست cross-company تثبیت شود.
- customer license import/signature/revocation در بخشی از کد پیاده‌سازی شده، اما Trade entitlement در DI با DenyAllTradeModuleEntitlement بسته است؛ اتصال entitlement مؤثر خارج از فازهای اولیه این Issue است.
- هیچ Migration تا پایان S0 و تصویب طرح داده ساخته نمی‌شود.
- صفحات Razor قدیمی تا جایگزینی کامل و تست‌شده حذف نمی‌شوند.
