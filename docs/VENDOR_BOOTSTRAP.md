# راهنمای عملیاتی راه‌اندازی اولین مدیر Vendor

وضعیت: **Implemented in branch / Not yet Verified** تا عبور CI کامل و ادغام PR.

## پیش‌نیازها
- این راهنما فقط برای کنترل‌پلین مستقل Vendor است؛ برای دیتابیس حسابداری مشتری استفاده نشود.
- ابتدا دیتابیس Vendor را با Migrationهای ثبت‌شدهٔ Vendor و فرایند انتشار استاندارد آماده کنید. فرمان bootstrap خودش Migration اجرا نمی‌کند.
- مقدار `FARANO_VENDOR_ConnectionStrings__VendorDb` باید به دیتابیس اختصاصی Vendor اشاره کند؛ از connection string مشتری استفاده نکنید.
- یک راز تصادفی حداقل ۳۲ بایتی در Secret Store یا محیط اجرای فرایند قرار دهید و با نام `FARANO_VENDOR_Bootstrap__Secret` به فرایند تزریق کنید. مقدار واقعی را در مخزن، فایل تنظیمات، آرگومان خط فرمان، ticket، log یا history پوسته ذخیره نکنید.
- پیش از اجرا، از روش مورد تأیید سازمان برای تولید راز تصادفی قوی استفاده کنید. راز را فقط به اپراتور مجاز منتقل کنید.

## اجرا
از پوشهٔ انتشار مستقل Vendor اجرا کنید:

```powershell
dotnet Faranou.Vendor.Host.dll bootstrap-admin
```

این فرمان وارد command mode می‌شود و HTTP listener را راه‌اندازی نمی‌کند. نام فرمان تنها آرگومان است؛ راز، نام کاربری، ایمیل و گذرواژه به‌صورت تعاملی وارد می‌شوند. ورودی گذرواژه در ترمینال echo نمی‌شود.

مراحل:
1. راز یک‌باره را وارد کنید.
2. نام کاربری و ایمیل مدیر را وارد کنید. راز bootstrap و گذرواژه در ورودی مخفی تایپ می‌شوند و echo نمی‌شوند.
3. گذرواژه‌ای مطابق سیاست Identity (حداقل ۱۴ نویسه، حروف کوچک/بزرگ، عدد، نویسهٔ ویژه و تنوع کافی) وارد و تکرار کنید.
4. URI نمایش‌داده‌شده را فقط در برنامهٔ authenticator مورد اعتماد ثبت کنید؛ URI شامل راز TOTP است و باید مانند رمز نگهداری شود. اگر خروجی ترمینال redirect شده باشد، فرمان نمایش URI را رد می‌کند تا راز به فایل/log هدایت نشود.
5. کد شش‌رقمی جاری را وارد کنید. تا زمانی که کد معتبر تأیید نشود، حساب غیرفعال می‌ماند.
6. پس از پیام موفقیت، راز bootstrap را از محیط اجرا پاک کنید و اجرای مجدد را انجام ندهید.

## تضمین‌های امنیتی
- هیچ route ثبت‌نام یا bootstrap عمومی در HTTP ایجاد نشده است.
- مقایسهٔ راز با `CryptographicOperations.FixedTimeEquals` روی هش‌های SHA-256 هم‌اندازه انجام می‌شود.
- SQL Server application lock با مالکیت transaction، اجرای هم‌زمان bootstrap را بین فرایندها سریال می‌کند.
- حساب ابتدا `IsEnabled=false` و `TwoFactorEnabled=false` است؛ فقط پس از تأیید TOTP فعال می‌شود.
- وضعیت pending در Vendor DB می‌ماند تا قطع فرایند در مرحلهٔ enrollment قابل بازیابی باشد. اجرای مجدد با همان نام کاربری و گذرواژه می‌تواند enrollment را از نو آغاز کند؛ اجرای پس از موفقیت رد می‌شود.
- رویدادهای شروع pending، رد کد TOTP و تکمیل موفق در زنجیرهٔ ممیزی Vendor نوشته می‌شوند. راز bootstrap، گذرواژه و کد TOTP در رخدادها قرار نمی‌گیرند.

## بازیابی
- اگر فرایند پیش از فعال‌سازی قطع شود، حساب باید همچنان غیرفعال باشد. همان فرمان را دوباره اجرا و همان نام کاربری و گذرواژه را وارد کنید؛ کلید TOTP جدید نمایش داده می‌شود و باید آن را در authenticator ثبت کنید.
- اگر bootstrap با پیام موفقیت پایان یافته است، اجرای مجدد باید رد شود. برای تغییر مدیر، از فرایند مدیریت هویت/بازیابی تأییدشده استفاده کنید؛ رکورد کاربر را مستقیم در SQL فعال نکنید.
- اگر راز bootstrap گم یا افشا شد، فرایند را متوقف کنید، راز را در Secret Store rotate کنید و ابتدا وضعیت DB و رخدادهای ممیزی را بازبینی کنید. این راز نباید در log یا audit ظاهر شود.

## Data Protection و استقرار
- Data Protection keys را در مسیر persistent با دسترسی محدود نگه دارید و نسخهٔ پشتیبان رمزگذاری‌شده و آزمون‌شده تهیه کنید؛ حذف آن‌ها می‌تواند نشست‌ها و توکن‌های محافظت‌شده را نامعتبر کند.
- راز bootstrap فقط برای فرایند command-mode و مدت کوتاه در دسترس باشد. پس از موفقیت آن را از environment/secret injection حذف کنید.
- در محیط Cloud و Dedicated Server، این runbook را با سازوکار Secret Store، حساب سرویس کم‌دسترسی، پشتیبان Data Protection و فرایند تغییرات سازمان تطبیق دهید.

## محدودیت‌ها و معیار Production
این قابلیت به‌تنهایی Vendor را Production-ready نمی‌کند. پیش از استفادهٔ تجاری باید RBAC default-deny، مجوزدهی resource-based، maker-checker، audit checkpoint مستقل، مدیریت مشتری/نصب/قرارداد/لایسنس، کلید امضای KMS/HSM، مانیتورینگ و runbook بازیابی تکمیل و با تست/CI تأیید شوند. هیچ Migration یا دیتابیس مشتری در این تغییرات دست‌کاری نمی‌شود.

## آزمون‌ها
- CI باید آزمون Integration واقعی SQL Server را اجرا کند؛ اجرای SQLite یا صرفاً unit test جایگزین آن نیست.
- تست هم‌زمانی باید ثابت کند از دو تلاش هم‌زمان فقط یک مدیر فعال ایجاد می‌شود.
- تست باید زنجیرهٔ ممیزی را با `VendorAuditChainVerifier` اعتبارسنجی کند.
- تا پایان Vendor CI، EF snapshot gate و publish مستقل، وضعیت این تغییر **Verified نیست**.
